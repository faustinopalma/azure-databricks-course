1. Architecture and Execution

Before we write a pipeline, we need a map of the platform: which pieces take part and what each one does. Azure Databricks is made of four parts with independent lifecycles. The workspace is the working environment where notebooks, jobs, and configurations live. Compute is the processing capacity that runs code, and it starts and stops as needed. Cloud storage keeps data durably. Unity Catalog decides who can access which data. A notebook stays in the workspace even when no compute is running; compute starts, processes, and stops; the table it wrote stays in storage. In this chapter we follow one concrete workload through these four pieces and see how they fit together.

1.1 Follow One Workload

Let's take an example that will accompany us through the whole course. An order management system writes JSON files to a cloud storage container. Every night a process reads the new files, checks that identifiers and amounts are valid, updates the analytical tables, and publishes daily revenue. The table shows which component handles each part of the work.

Responsibility Component in this example Mechanism
Store source files and table data Cloud object storage Persists the bytes; Delta Lake adds the transaction log that defines table versions.
Execute reads and transformations Databricks compute Runs code under an identity authorized to access the sources.
Register tables and govern their use Unity Catalog Resolves object names and evaluates privileges on the registered assets.
Define processing logic SQL, Python, or declarative pipeline definitions Describes the operations executed interactively or as a scheduled workload.
Schedule work and handle task dependencies Lakeflow Jobs Starts tasks in dependency order and records their execution outcomes.

This division of work becomes valuable when something goes wrong, because each type of error points to a specific component. To read a file, a request must cross the network to storage, be authorized by storage and by Unity Catalog, run on available compute, and finally pass the data checks. A timeout usually indicates a network connectivity problem; an access-denied error indicates that one of the authorization checks rejected the identity; a malformed record is a problem with the incoming data. Recognizing the type of error already tells us where to look.

1.2 Account, Workspace, and Metastore

Let's look at how resources are organized. Two hierarchies coexist. The first is Azure's: a subscription contains Azure resources, including the Databricks workspace resource, and Azure RBAC decides who can create, change, or delete them. The second is Databricks': a Databricks account groups workspaces, account-level identities (users, groups, and service principals), and shared configuration such as metastores. The two hierarchies have separate permissions. An Azure administrator can delete the workspace resource without any permission on the data, and a Databricks account administrator can manage groups without being able to touch the subscription.

The workspace is the environment we work in every day: it contains notebooks, files, jobs, dashboards, and compute configurations. Teams often use separate workspaces for development and production, so each environment has its own notebooks and jobs, and a developer editing a test notebook leaves the scheduled production notebook untouched. Separating workspaces separates working artifacts. Data is governed by Unity Catalog, and its separation depends on how we configure permissions, as we see next.

The Unity Catalog metastore is the top-level container for metadata: it registers catalogs, schemas, tables, volumes, and their permissions. Each workspace attaches to one metastore, and several workspaces in the same region can attach to the same metastore. It follows that workspaces attached to the same metastore see the same objects. Suppose development and production share a metastore: the name sales_prod.gold.daily_revenue refers to exactly the same table from both workspaces. The name says what the table is for, while grants decide who can read or change it. Workspace bindings, which we cover in chapter 4, can also make a catalog reachable only from certain workspaces.

Objects in Unity Catalog have three-level names of the form catalog.schema.object. The catalog is the broadest scope and often matches an environment or a business domain, such as sales_prod. The schema groups related objects, such as the tables of the gold layer. The last level is the name of the table, view, function, or volume. The metastore sits above these three levels and does not appear in the name.

Older workspaces may also contain tables registered in the legacy Hive metastore. These appear under the special catalog hive_metastore, for example hive_metastore.default.orders, and follow the old workspace permission model. Migrating them to Unity Catalog means registering them in the new metastore and redefining their permissions with Unity Catalog grants.

1.3 Control Plane and Compute Plane

We said that compute runs the code. But where does it physically run? Databricks splits the platform into two planes. The control plane is the part managed by Databricks that provides the web interface, the APIs, the job scheduler, and resource coordination. The compute plane is where data is actually processed. When we run a query, the control plane receives it and coordinates execution, while the compute plane reads and transforms the rows. Depending on the feature, the control plane can also keep results and operational metadata, such as notebook cell output.

The compute plane comes in two variants. In the classic model, clusters are virtual machines created in the customer's Azure subscription, in a virtual network managed by Databricks or in a customer network. The customer chooses the runtime version, machine types, and network settings, and pays Azure for the machines in addition to Databricks consumption units (DBUs). In the serverless model, the machines live in an environment managed by Databricks: the customer uses them without seeing them, configures only the parameters the service exposes, and gets much faster startup. Which workloads support serverless, and with what connectivity to private resources, depends on the workload type and the region.

The same workspace can use both models: an interactive notebook on serverless, a job on a classic cluster, a dashboard on a SQL warehouse. To understand how a task behaves we therefore need three pieces of information: where it runs, under which identity, and through which network path it reaches what it needs. These three answers explain most of the behaviors, and errors, we will meet.

1.4 Storage Is Independent of Running Compute

An important consequence of this architecture is that data and computation live apart. A Delta table written to storage stays there when the cluster that created it stops, and any authorized compute can later read or change it. Everything that exists only in compute memory disappears with it. If we compute a DataFrame in a notebook, cache it, or assign a value to a Python variable, that work has to be redone after a restart. A result that must survive belongs in a table.

Storage itself comes in two kinds. The workspace keeps its own files: notebook code, revisions, cell results, and operational information generated by the system. Business data lives in storage governed by Unity Catalog, in locations configured by administrators. The physical placement of these two kinds of storage depends on the workspace model and the storage configuration.

The same separation guides recovery after an incident. A lost notebook comes back from version control. Lost data comes back through time travel, retention, or backups. An interrupted streaming pipeline resumes from its checkpoint, helped by the run logs. Rebuilding a pipeline can require all three mechanisms together.

To access data, Unity Catalog offers two kinds of objects. Tables provide governed access to tabular data; volumes provide governed access to files of any type, such as incoming CSV files, images, or PDFs. Both replace the older approaches based on the DBFS root and mounts, which sat outside Unity Catalog governance. In practice we meet three kinds of path: a workspace path such as /Workspace/Users/... identifies code and working files; a volume path such as /Volumes/sales_prod/bronze/landing/ identifies governed files; a cloud URI such as abfss://... identifies a physical storage location.

1.5 Understand What Executes

Let's look at what happens when we run code. A notebook is a document made of code cells and text. On its own it is just a document: to run it we attach it to compute, which supplies the engine, the languages, and the available libraries. If the chosen compute lacks Scala support, a Scala cell fails even when the code is correct.

The processing engine is Apache Spark, which distributes work across several machines. In a multi-node cluster a driver plans the work and coordinates execution, while several executors process the data. Spark splits data into partitions and assigns each partition to a task on an executor: more partitions allow more work in parallel. The word "partition" has two meanings here that we keep apart. A Spark partition is a piece of data processed in memory by one task; a storage partition, which we see in chapter 7, is a way of organizing files on disk. The number of Spark partitions depends on how files are read and on operations such as the shuffle, the redistribution of data between executors.

Spark runs code lazily. When we write df.filter(...).join(...), Spark only builds a plan describing the operations. Work starts when we ask for a result with an action, such as writing a table, counting rows, or showing a preview. As a consequence, a conversion error introduced in a filter can surface only at the final write, many cells after the point where we wrote it.

The plan also explains what an operation costs. A join between two large tables may require reading both and moving records between executors, so that rows with the same key end up on the same machine. The optimizer tries to reduce this work: with filter pushdown, for example, it moves filters as close as possible to the read, so Spark reads fewer rows from the start. The query plan and task metrics, which we explore in chapter 11, show where time is spent.

One last terminology note concerns the word "job", which means two things in Databricks. A Lakeflow Job is a scheduled workflow made of tasks, such as "every night run the ingestion notebook and then the aggregation notebook". A Spark job is an execution unit inside Spark, created whenever an action starts a computation. A single notebook task can therefore generate many Spark jobs, each divided into stages and tasks. Lakeflow monitoring shows the workflow; the Spark UI shows distributed execution.

1.6 The Platform Components in Context

We have met several product names; let's place them in the orders pipeline. Delta Lake is the format that gives tables transactions and versions on top of files. Unity Catalog registers tables, volumes, and other objects and governs access to them. Spark and the other Databricks engines, such as Photon, run the queries. Databricks SQL provides an environment for SQL analytics, with an editor, dashboards, and SQL warehouses, which are compute optimized for SQL queries.

The Lakeflow family covers the pipeline lifecycle. Lakeflow Connect provides managed connectors to bring in data from databases and applications. Lakeflow Spark Declarative Pipelines lets us describe the tables to produce and their relationships, leaving execution order, incremental updates, and error handling to the service. Lakeflow Jobs schedules and runs tasks with dependencies, including notebooks and pipeline updates. In our pipeline they can all work together: a connector captures customer changes, a declarative pipeline updates the derived tables, and a job finally runs a validation notebook.

Machine learning builds on this work too. MLflow tracks experiments and models, but a model is reliable only if the data used to train and serve it is correct, governed, and reproducible. Data engineering supplies exactly that: quality data, controlled permissions, and the ability to trace every value back to its origin.

1.7 Reason Through the Boundaries

We close with three common situations in the orders pipeline that what we have seen explains.

  1. A developer opens the notebook without problems but gets an error when reading sales_prod.bronze.orders. Opening the notebook depends on workspace permissions; reading the table depends on Unity Catalog privileges, evaluated against the identity running the code. These are two separate checks, and the developer passed only the first.
  2. A result computed in a notebook disappears after the cluster restarts. It existed only in compute memory; written to a table, it would have survived.
  3. The same code works when the production job runs it under a service principal and fails when the developer runs it. The operation is identical, but the two identities hold different privileges.

2. Storage and Unity Catalog Objects

When we save data in Databricks we make three separate decisions, often without noticing. The first is who is responsible for the file lifecycle: Databricks (managed objects) or whoever owns the external storage (external objects). The second is the format, for example Delta. The third is how the data is read: as rows and columns through a table, or as files through a volume. The three choices combine freely: a Delta table can be managed or external, and a volume can hold CSV, Parquet, or any other file. In this chapter we examine them one at a time, starting with how we organize names.

2.1 Establish the Namespace Before Loading Data

Let's return to the orders pipeline. To separate environments we use two catalogs, sales_dev and sales_prod, and in each one three schemas that match the stages of data processing, following the so-called medallion architecture. The bronze schema keeps data as it arrives from the source; silver holds checked and cleaned data; gold holds datasets ready for business use, such as daily revenue. The names make each stage recognizable, while the transformation code is what guarantees that each schema's data really has the promised quality.

CREATE CATALOG IF NOT EXISTS sales_dev;
CREATE SCHEMA IF NOT EXISTS sales_dev.bronze;
CREATE SCHEMA IF NOT EXISTS sales_dev.silver;
CREATE SCHEMA IF NOT EXISTS sales_dev.gold;

Running these statements requires create privileges and available managed storage, which we discuss in the next section; in some environments the storage location must be given explicitly when the catalog is created. The IF NOT EXISTS clause makes the script repeatable: if the object is missing it creates it, and if it already exists it leaves it as it is, with its owner, location, and permissions. Rerunning the script after a permission change therefore leaves the changed permissions in place.

The full name of an object removes ambiguity. If code simply writes to orders, Databricks completes the name with the session's current catalog and schema, which can vary with who runs the code and how. Writing sales_prod.silver.orders makes the destination explicit. A common compromise passes the catalog name as a deployment parameter: the same code writes to sales_dev during development and to sales_prod in production, while schema and table stay the same in every environment.

Stable names are an interface for data consumers: they communicate environment, stage, and purpose. Descriptions and version control tell how the object changed over time, and privileges govern access. Unity Catalog normalizes identifiers to lowercase, so two names that differ only in letter case refer to the same object.

2.2 Managed Storage Resolution

When we create a managed table without saying where to store it, Unity Catalog has to choose a storage location. It looks for the most specific configuration available: first the schema's managed location, then the catalog's, and finally the metastore default. Configuring storage at catalog level is a frequent choice because it aligns the physical placement of data with an environment or a domain: sales_prod data lands in a different storage account from sales_dev data. A schema-level location serves a part of the catalog with its own needs, for example sensitive data kept in a separate account.

Inside that root, Unity Catalog gives each object its own folder and coordinates its files with the metadata, including deletions. For this reason the files of a managed table are touched only through Databricks. Registering an external table that points to the same folder, or moving files by hand, introduces a second manager of the same data and breaks the coordination.

The location says where the data lives, but reaching it takes two authorizations. The platform accesses storage with its own identity, typically an Azure managed identity configured in Unity Catalog. Users, in turn, receive privileges on the registered objects. A read succeeds only when both authorizations are in place.

There is also a third option, default storage: storage managed entirely by Databricks, without a customer storage account. According to the archived course, catalogs on default storage are created in serverless workspaces and their data is read only with serverless compute. Managed tables on customer storage also support classic compute and the other documented configurations. The chosen storage mode therefore determines which compute and which direct access will be possible.

2.3 Managed Versus External Tables

We have seen where managed tables end up. When does an external table make sense? The difference concerns responsibility for the files, as the comparison shows.

Decision Managed table External table
Who manages table metadata? Unity Catalog Unity Catalog
Who controls the underlying data lifecycle? Databricks manages it with the table The external storage owner retains responsibility
How is the location selected? The applicable managed storage configuration An explicit registered external location/path
What does dropping the object mean? Metadata removal and managed data deletion according to the supported recovery/lifecycle rules Registration removed; underlying files retained
Why choose it? Databricks is the primary data manager and supported automated maintenance is useful Existing or independently managed data must remain at a controlled external location

In both cases the table consists of metadata in Unity Catalog and files in cloud storage, and anyone going through the registered table is governed by Unity Catalog. With an external table there is also a second route: anyone with direct permissions on the cloud storage can read or change the files without going through Unity Catalog. This route belongs in any security reasoning.

Let's look at a minimal managed table:

CREATE TABLE sales_dev.silver.orders (
  order_id BIGINT NOT NULL,
  customer_id BIGINT,
  order_total DECIMAL(18,2),
  order_timestamp TIMESTAMP
) USING DELTA;

There is no LOCATION clause, so the table lands in the managed storage resolved as we saw. An external Delta table instead names an approved path explicitly:

CREATE TABLE sales_dev.bronze.orders_external
USING DELTA
LOCATION 'abfss://landing@examplestorage.dfs.core.windows.net/orders_delta/';

The URI is an example and must point to an existing Delta table, complete with its transaction log. Registration works only if a storage credential and an external location covering that path are already configured, which we discuss in section 2.4, and if the user holds the required privileges. If the folder contained raw JSON files, this statement would leave them as JSON: converting them takes a read of the JSON and a write to a Delta table.

The difference between the two types shows above all at deletion time. DROP TABLE on a managed table removes the registration and starts managed deletion of the files; for a few days the table can still be recovered with UNDROP. On an external table, DROP TABLE removes only the registration, and the files stay in storage under their owner's control. Then there is CREATE OR REPLACE TABLE, which where supported replaces definition and data while keeping the same table: history and permissions stay attached. A DROP followed by a CREATE instead produces a new table, and the queries, permissions, and history tied to the old one must be rebuilt.

2.4 Files Belong in Volumes When the Interface Is File-Based

Some data is naturally a set of files. Incoming JSON files, PDF invoices, product images, or model artifacts are files, and we want to read them as files. For this Unity Catalog offers volumes: a volume is an object with a three-level name, catalog.schema.volume, that exposes a folder of files with governed permissions. A table is queried over rows and columns; a volume is used with file operations such as listing, reading, and writing.

CREATE VOLUME IF NOT EXISTS sales_dev.bronze.order_files;

Once created, the volume is reachable through paths such as /Volumes/sales_dev/bronze/order_files/..., usable from Spark, Python, and command-line tools. Permissions are granted on the whole volume and apply to all its subfolders. If invoices must stay private and product images public, we therefore need two separate volumes, each with its own grants.

Volumes can also be managed or external, with the same logic as tables. A managed volume lives in managed storage, and its files are deleted when it is dropped. An external volume registers a folder that exists independently, and when it is dropped the files stay where they are. Tables and volumes still have their own deletion and recovery rules.

Creating external objects requires two supporting objects. A storage credential represents the identity Databricks uses to access cloud storage, for example a managed identity through an access connector. An external location associates a storage path with that credential and becomes the object on which permissions are granted: whoever holds CREATE EXTERNAL TABLE on an external location can register tables in that path. The full chain is therefore an identity (the credential), an authorized path (the external location), and finally the object used to access the data (the external table or volume).

2.5 Tables, Views, Materialized Views, and Streaming Tables

Besides tables and volumes, Unity Catalog offers objects that derive their data from others. They differ in when they compute, and therefore in the trade-off between cost and freshness.

A standard view stores only the text of a query. Every time someone queries it, Databricks runs the query against the underlying data. The view is therefore always current and serves to offer a stable projection, reuse a business rule, or expose a governed subset of data; the price is that every read pays for the whole computation.

A materialized view stores the query result instead and updates it with a refresh. Reads reuse the precomputed result and are fast, while the computation moves to refresh time. The trade-off is freshness: between refreshes the data can lag behind the source. For a dashboard updated every hour that lag is acceptable; a fraud system that must react within seconds needs something fresher. Refresh frequency is the dial that balances read cost and freshness.

When possible, the refresh is incremental: Databricks processes only the changes that reached the source since the last update. Whether it can do so depends on the source's features, the shape of the query, and an assessment by the service. When an incremental refresh is impossible or unprofitable, Databricks recomputes everything. Refresh history shows which strategy was used each time.

A streaming table is incremental by construction. It remembers how far it has read and, on every update, processes only the new records. It suits sources that grow by appending, such as the files arriving in the orders volume. If the source changes or deletes records already read, the streaming table on its own misses those changes, and explicit change handling is needed, such as the CDC of chapter 6. The checkpoint, the record of progress, makes it possible to resume after an interruption; a full refresh rebuilds the table from scratch.

Materialized views and streaming tables are defined declaratively: we describe the desired result and the service takes care of refreshes, inside a pipeline or on a schedule.

2.6 Foreign Catalogs and Remote Queries

Sometimes the data we need lives in another database, for example a SQL Server holding customer master data. With query federation we can query it without copying it first. A connection stores the remote database address and the credentials to access it. A foreign catalog, created on top of the connection, exposes the remote database's schemas and tables in Unity Catalog, where they become queryable with the usual three-level name. When we run a query, Databricks pushes down to the remote database the operations that system can perform, such as filters and projections, and retrieves only the result.

A foreign catalog is quite different from an external table. The external table registers files in a cloud path; the foreign catalog exposes an entire remote system. Every federated query therefore depends on that system: it must be reachable over the network, the credentials must be valid, and its processing capacity and the operations it accepts determine performance.

This guides the choice between federation and ingestion. Federation reads the source at query time, which makes it convenient for exploring data or running occasional cross-system queries. Ingestion creates a local, durable analytical copy: later processing no longer depends on source availability, and repeated reads stay off the operational database.

Permission management follows the same split. The connection holds the technical credentials, while users receive privileges on the foreign catalog. An analyst can thus query remote tables without ever knowing the database password.

2.7 Check the Design

Let's apply what we have seen to the orders system. The source team owns the incoming files, Databricks produces and manages the validated analytical tables, and analysts want a daily summary. The incoming files already sit in independent storage managed by the source team, so we expose them with an external volume. The silver and gold tables are produced by Databricks and live only there, so we create them as managed. For the daily summary we choose a standard view if the query is light, or a materialized view if it is expensive and a delay until the next refresh is acceptable.

Let's check the consequences. If we drop the landing volume, the source files remain intact, because the volume was external. The silver and gold tables stay available between runs, because they are persistent. Who can use them from other workspaces is decided by grants and workspace bindings. The object type establishes lifecycle responsibility; permissions establish access.

The catalog objects lab provides hands-on work. Basic managed objects may fit a supported learning workspace; external storage, connections, and specific refresh capabilities require their own prerequisites.

3. Compute Selection and Configuration

In chapter 1 we saw that compute is the part of the platform that runs code. In practice Databricks offers many kinds of compute, and the right choice depends on what we need to run. A job that runs ten minutes every night and a dashboard queried all day by dozens of analysts may read the same tables, yet their needs are opposite: the first wants to pay only for its ten minutes, the second wants to answer every click immediately. In this chapter we look at the characteristics that distinguish one compute from another and how to choose them for a workload. Two criteria guide the whole reasoning. The first is compatibility: the compute must support the APIs, libraries, identity, and connectivity the code needs. The second is total cost, which includes startup, processing, idle time, and retries after an error.

3.1 Separate the Selection Axes

The words used to describe compute mix choices that are independent of one another. It helps to separate them into five axes, each answering a different question.

Axis Question Examples
Infrastructure management Who manages the execution infrastructure and its configuration? Serverless or classic
Workload interface What kind of work is submitted? Notebooks, job tasks, SQL queries, declarative pipeline updates
Access mode on applicable classic compute How are identities and workloads isolated? Standard or dedicated
Resource shape What execution resources are available? Single-node or multi-node, worker family, memory/core ratio
Lifecycle How long does compute exist? Interactive session, job-associated compute, warehouse lifecycle

The choices combine freely. A job can run on serverless or on a classic cluster; a classic cluster can use standard or dedicated access mode; a dedicated cluster can have one node or many. When someone says "a job cluster", for example, they are naming only the lifecycle, and every other axis is still open. In the next sections we examine them one at a time.

3.2 Match the Workload

Let's start with infrastructure management. With serverless, Databricks starts, sizes, and configures the machines, and we pay for the work actually done. How much work that is depends on the data volume, the query plan, the dependencies, and the chosen performance mode. Classic compute instead leaves to us the choice of runtime version, machine type, initialization scripts, and available APIs. That control serves workloads with particular runtime, hardware, or system needs, such as a native library or a specific GPU. Which workloads are compatible with each model changes as the service evolves.

Next comes the workload interface. A SQL warehouse is compute dedicated to SQL queries and business intelligence clients such as Power BI; it comes in serverless, pro, and classic variants that differ in management and features. Notebook compute instead runs the languages and APIs the cells use, such as Python, SQL, or Scala. The type of work submitted therefore points to the right interface.

The lifecycle has practical consequences too. A job can have compute of its own, which starts with the job, installs the declared dependencies, and stops at the end. A shared interactive cluster instead stays on between sessions, and all its users share capacity, libraries, and restarts: if someone restarts the cluster to install a library, they also interrupt everyone else's work. Job-dedicated compute removes this coupling, at the price of a startup and a dependency installation on every run.

Serverless jobs and pipelines offer one more choice of mode. Performance optimized mode starts compute quickly; standard mode accepts a slower start in exchange for lower consumption. For a nightly job nobody is waiting for, a few extra minutes of startup are often a good deal.

3.3 Access Mode Is a Security and Compatibility Decision

Access mode decides who can use a classic cluster and under which identity the code runs. In standard mode several users share the same cluster, and Databricks isolates their executions: each works under their own identity and sees only the data their privileges allow. This isolation costs some compatibility, because a few low-level APIs are unavailable. In dedicated mode the cluster is assigned to a single user or, where supported, to a group, and it offers broader compatibility. There is also an old shared mode without isolation, which lacks the same protections and is considered legacy.

The group-assigned cluster deserves an example. Suppose the cluster is dedicated to the data-engineers group and that Anna, a member of the group, also has personal access to the hr.salaries table. On the group cluster the code runs with the group's permissions, so Anna cannot read hr.salaries from there, while she can read it from personal compute. The same code gives different results because it runs under two different identities.

Language support also depends on context: notebook cells, task types, and libraries each have their own compatibility rules for every kind of compute. The archived course contains conflicting statements about Scala support on serverless; for that combination, the serverless limitations page listed in the sources is the reference.

3.4 Size for the Limiting Resource

Now the resource shape. Sizing a cluster well means understanding which resource limits the workload, because adding a different resource leaves the time unchanged. Each resource has a precise role. Executor cores run tasks, one per core. Memory serves joins, aggregations, streaming state, and caching. Local disk holds data that does not fit in memory (the spill), the intermediate shuffle files, and some caches. The driver has a separate role: it coordinates the work and gathers results. It can therefore run out of memory while executors sit nearly empty, for example when code uses collect() to bring millions of rows to the driver.

Adding workers increases executor capacity, which helps only when there are enough independent tasks to run in parallel. Let's look at three cases where more workers leave the time unchanged. If the bottleneck is a large Python object on the driver, the extra workers sit idle. If one key is far more frequent than the others, a single partition holds most of the work and a single task processes it. If the source caps requests per second, the input rate stays the same. CPU, memory, disk, network, source, and task distribution each impose their own limit, and the workload moves as fast as the tightest of them.

At equal total cores and memory, the shape of the cluster matters. Many small nodes spread resources over more machines: a failure loses a smaller share, but shuffles generate more network traffic. A few large nodes concentrate memory, which helps state-heavy operations, and reduce traffic between machines. Finding the better shape for a specific workload takes a comparison with the same data and the same concurrency.

For small workloads there is also single-node compute, which runs everything on one machine. On a small dataset the startup and coordination time of a large cluster can exceed the processing time, making a larger cluster both slower and more expensive.

3.5 Autoscaling, Pools, and Termination

Load is rarely constant, and a few mechanisms help match compute to demand. Autoscaling adds or removes workers between a configured minimum and maximum. Each setting has a precise effect: adding machines takes a few minutes, the maximum caps capacity during peaks, and the minimum determines what we pay while the cluster is idle. The added workers help only if the work can spread across them; a query with few partitions or a stream with a lot of state gains little.

To shorten classic cluster startup we can use an instance pool, a set of virtual machines kept ready. A cluster drawing from the pool starts faster because it skips VM creation. Idle machines in the pool cost Azure the same as running VMs, while Databricks charges (DBUs) apply only when a cluster uses them. The pool's maximum caps how many machines it can supply in total.

A pool is sized by counting the machines requested at the same time. A pool supplies drivers and workers to the clusters that request them: ten notebooks attached to the same four-node cluster request four machines, while a single job on a twenty-node cluster requests twenty.

Then there is shutdown. Automatic termination stops an interactive cluster after a configured period of inactivity, so we stop paying when nobody uses it. Job compute instead stops when the job ends. The pool has its own rule: idle machines above the configured minimum are released after a set time, while the minimum stays on even when no cluster uses it.

A last cost lever is spot machines, unused Azure capacity sold at a discount that Azure can reclaim at any moment. When a spot machine is reclaimed, the tasks running on it must be recomputed and the job takes longer. For this reason the driver usually stays on a regular machine, and supported decommissioning moves data before the worker disappears. The real saving is the machine discount minus the cost of recomputation and delay.

3.6 Runtime, Photon, and Libraries

On a classic cluster we also choose the Databricks Runtime version, which fixes the Spark version and the set of preinstalled libraries. LTS (Long Term Support) versions receive updates for a longer period. Each new version can change dependency compatibility and, in some cases, query behavior; for this reason a version upgrade is validated with representative tests of both correctness and performance.

Photon is a native execution engine that runs supported SQL and DataFrame operations faster. The gain depends on how much of the workload's time goes into those operations. If a job spends half its time in Python code on the driver or waiting for an external service, Photon speeds up only the other half. The executed plan shows which operations Photon handled.

There are also runtimes for machine learning, with ML libraries preinstalled. Their value depends on whether the workload actually uses those libraries.

That leaves dependency management, the additional libraries the code needs. Where we declare them determines how reproducible the environment is and who is affected by a change.

Scope Consequence Appropriate use
Notebook/session dependency Limited to the supported session environment Exploration with explicit versions
Job/task dependency Declared with the workload Repeatable production execution
Compute-scoped dependency Affects workloads sharing the cluster; installation is reapplied at startup Intentionally shared environment
Initialization script Executes startup configuration and can prevent startup if it fails Required system configuration not handled by normal library mechanisms

The table shows a progression. A library installed in a notebook with %pip install applies only to that session: it is convenient for exploration, and pinning its exact version makes the experiment repeatable. A dependency declared in the job travels with the job, and every run rebuilds the same environment. A library installed on the cluster affects everyone using it and is reinstalled at every start. Initialization scripts act at the operating-system level during startup, and if they fail the cluster does not start. Any installation done by hand in a session, and never declared in one of these places, disappears when the environment is recreated.

On standard-mode clusters a security check is added. JARs, Maven coordinates, and init scripts must be approved in an allowlist by the metastore admin before they can run. If the package sits in a volume, READ VOLUME is also needed to read it, and installing it on the cluster requires cluster management permissions. Loading a library can therefore require three separate authorizations: artifact approval, file read, and compute management.

3.7 Compute Permissions and Entitlements

Who can use a classic cluster? Three increasing permission levels decide. CAN ATTACH TO lets a user attach a notebook to the cluster and run code. CAN RESTART adds the ability to start, stop, and restart it. CAN MANAGE adds changing the configuration and the permissions themselves. These workspace permissions concern compute only: Azure roles govern Azure resources, and Unity Catalog grants govern data. Holding CAN MANAGE on a cluster grants no access to tables at all.

Who can create new clusters depends on two other tools. An entitlement is a capability granted to a user or group in the workspace, such as unrestricted cluster creation. A compute policy limits the allowed configurations: for example, it imposes maximum sizes, machine types, or automatic termination. Putting together entitlements, policies, compute permissions, and data grants gives the complete picture of what an identity can create and run.

One last point concerns driver logs. They contain everything applications and libraries print, and can therefore expose sensitive data. Databricks redacts secrets read through its APIs when they appear verbatim in output, but a transformed secret, for example encoded or split, escapes redaction. Restricting who can read the logs and keeping credentials out of printed output reduces this risk.

And if the code still uses a legacy API that serverless does not support, a classic cluster remains the only option until the code is updated.

4. Identity and Authorization

When a query reads a table, the request passes through a chain of checks. An identity submits the query, compute runs it, Unity Catalog verifies that the identity holds the necessary privileges, and finally a storage identity reaches the files over a network that must allow the connection. Each link has its own permission system. The Azure Contributor role lets someone manage the workspace resource; the Unity Catalog SELECT privilege lets someone read the table; the storage firewall decides whether the connection can pass. The request succeeds only if it passes every check along the path, and an access-denied error tells us that at least one of them stopped it. In this chapter we walk the chain link by link.

4.1 Identify the Principals in the Request

A principal is an identity that can receive permissions: a user, a group, or a service principal, which is an identity meant for automated processes. Four of them take part in the orders pipeline, each with a different task.

Identity Responsibility Typical authorization surface
Interactive developer Authors and tests code Workspace objects, compute, and Unity Catalog
Deployment principal Creates or updates job and pipeline definitions Workspace APIs and resource permissions
Job execution principal Runs the production workload Input/output objects, secrets, and execution resources
Storage identity Authenticates the governed storage connection to Azure Azure storage data-plane roles and applicable storage controls

These identities can coincide or be separate, each with its own grants. Separating them has consequences worth anticipating. Suppose the release pipeline uses a service principal allowed to edit jobs, and the job runs under another service principal. The release can succeed perfectly while the first run fails because the execution principal lacks SELECT on the source. Whoever writes the code, whoever deploys it, and whoever runs it each act under their own authority.

Service principals come in two variants. Databricks-managed ones are automation identities created and managed entirely in the platform. Microsoft Entra ID-managed ones correspond to an application registered in Entra and can therefore also authenticate to other Azure services, which is useful for automation that spans several services. In both cases authentication produces a token intended for a specific API.

The storage identity is usually an Azure managed identity, an identity whose credentials are managed by Azure itself, with no password to store or rotate. A Unity Catalog storage credential uses it to authenticate requests to storage. This identity works for the platform and stays distinct from the job's principal, which supplies the authority for the run's operations: the job asks to read the table, Unity Catalog checks the principal's privileges, and then the managed identity fetches the files.

4.2 Grant the Complete Privilege Combination

Reading a table requires three privileges together: USE CATALOG on the catalog and USE SCHEMA on the schema, which let the principal enter the namespace, and SELECT on the table, which lets it read. With these grants we give analysts access to the published revenue:

GRANT USE CATALOG ON CATALOG sales_prod TO `revenue-analysts`;
GRANT USE SCHEMA ON SCHEMA sales_prod.gold TO `revenue-analysts`;
GRANT SELECT ON TABLE sales_prod.gold.daily_revenue TO `revenue-analysts`;

The example assumes that the group and the objects exist and that whoever runs the grants has the authority to do so. The group gets access to the revenue table only: USE SCHEMA lets it enter the gold schema, while the other tables in the schema stay invisible until it also receives SELECT on them.

A transformation needs something more, because it reads some tables and writes others. On the sources it needs read privileges; on the target it needs MODIFY, which authorizes inserts, updates, and deletes. If the transformation also creates the target table, it needs the create privilege on the containing schema, such as CREATE TABLE. The list of privileges therefore follows from the operations the workload actually performs.

The same reasoning applies to files. Reading from a volume requires namespace access privileges and READ VOLUME; writing also requires WRITE VOLUME. Creating an external object additionally requires the corresponding privilege on the external location that contains the path.

4.3 Inheritance, Ownership, and Administration

Privileges in Unity Catalog are inherited down the hierarchy. If we grant SELECT on a schema, the group can read every table in the schema, both existing ones and those created in the future. This is convenient, because a new table automatically enters the read perimeter already decided, but it calls for care: whoever creates a table in that schema makes it readable to everyone holding the schema grant. When different data has different audiences, we separate it into different schemas or grant privileges table by table.

Inheritance also complicates revocations. A user's effective access is the sum of direct grants, grants received through groups, grants inherited from containers, ownership, and policies. Suppose we revoke Marco's direct SELECT on sales_prod.gold.daily_revenue: if Marco belongs to a group with SELECT on the gold schema, he can still read the table. Understanding who sees what means looking at the whole hierarchy.

Every object also has an owner, who holds full administrative authority over its lifecycle. If the owner is a person and that person changes role or leaves the company, the object is left without an active responsible party. Assigning ownership to an operational group, such as data-platform-owners, lets responsibility survive staff changes.

The MANAGE privilege allows administering an object, for example managing its permissions, without owning it. By itself it does not allow reading data, which requires a privilege such as SELECT. Whoever holds MANAGE can, however, grant SELECT to anyone, themselves included, so permission administrators are in practice part of the data's trust perimeter.

Finally, ALL PRIVILEGES grants at once all the privileges applicable to the object type. A few privileges stay outside it and must be granted explicitly: according to the current reference they are MANAGE, EXTERNAL USE SCHEMA, EXTERNAL USE LOCATION, and READ METADATA.

4.4 Workspace Bindings and the Storage Boundary

In chapter 1 we saw that several workspaces can share the same metastore and therefore see the same catalogs. Sometimes, however, we want a catalog reachable only from certain workspaces. Workspace bindings add exactly this condition: access to a bound object requires both the privilege and a request coming from an allowed workspace. With a binding that limits sales_prod to production workspaces, a developer who holds SELECT on a production table still cannot read it from the development workspace.

There is also a path that bypasses Unity Catalog: direct access to cloud storage. Anyone with an Azure role on the storage can read the files with Azure APIs, without going through Databricks. This path is governed by Azure credentials and roles, and Unity Catalog privileges have no effect on it. Restricting direct storage access therefore closes an alternative route to the same data.

Let's see how access to Azure storage is configured with a managed identity. Each step adds a link to the chain:

  1. An Azure Databricks access connector references a system-assigned or user-assigned managed identity.
  2. Azure storage data-plane roles authorize that identity to read or write the chosen storage scope.
  3. A Unity Catalog storage credential refers to the connector and the applicable identity.
  4. An external location associates the credential with a storage path.
  5. Object and location grants authorize operations by Databricks principals.
  6. Network rules allow the compute-to-storage connection needed by those operations.

The managed identity can be system-assigned, in which case it is born and dies with the access connector, or user-assigned, in which case it has an independent Azure lifecycle and can outlive the connector. This chain also explains a class of failures that often surprises people: a pipeline can stop working although nobody touched the Unity Catalog grants, because someone deleted the connector, revoked the storage role, or changed a firewall rule.

Ingestion based on file events, which we see in chapter 6, adds another path. To discover new files without listing folders over and over, Databricks relies on Azure notifications: Event Grid publishes an event for each new file and an Azure Storage queue holds it. The identity must therefore be able to manage the event resources, read the queue, and read the blobs, and each of these accesses requires a separate role.

4.5 Row Filters, Column Masks, and Views

So far we have decided who can read a whole table. Often, though, we need finer control: a regional manager should see only their region's orders, and only customer support should see email addresses. Row filters decide which rows a query can see; column masks transform the values of a protected column at read time. Both act when the query goes through Unity Catalog on compute that supports them. Protecting the underlying files remains the job of encryption and storage permissions.

Let's look at a mask that shows a customer's email only to the members of one group:

CREATE FUNCTION sales_prod.silver.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('customer-support') THEN email
  ELSE '[masked]'
END;

ALTER TABLE sales_prod.silver.customers
ALTER COLUMN email SET MASK sales_prod.silver.mask_email;

The function receives the original value and returns a value of the same type: the real email for members of customer-support, the string [masked] for everyone else. Once attached to the column, the mask applies to every query on the table, with nothing required from the person querying. Running the example requires the table, permissions on the function and the table, and compatible compute. The mask also changes query results: whoever cannot see the email also cannot filter or join on its real values, and two different customers both appear as [masked].

An alternative is the dynamic view, a view that selects columns and rows based on the identity of whoever queries it and can combine several tables. Consumers receive SELECT on the view and query it as a controlled interface. If someone also receives SELECT on the base tables, however, they can read them directly and bypass the view's rules. Row filters and column masks avoid this problem, because the rule lives on the table itself.

Two identities take part in these mechanisms. The body of the function or view runs with its owner's rights, while functions such as current_user() and is_account_group_member() return the identity of whoever is running the query. The most reliable way to check what a consumer actually sees is to run the query under their identity and observe the rows and values returned.

When there are many tables, attaching filters and masks one by one becomes hard to maintain. Attribute-based access control (ABAC), which we see in the next chapter, lets us define policies once and apply them to every column carrying a given tag.

4.6 Secrets Are a Separate Authorization Surface

Some dependencies need credentials that Unity Catalog does not manage, such as the password of an external database or an API key. We keep them in a secret scope, a container of secrets with its own permissions. Two checks come into play here: the scope decides who can retrieve the secret, and the remote service decides what whoever presents that credential can do. Where the integration supports it, authenticating with an identity, such as a managed identity, leaves credential management to the platform and removes the secret to guard.

Secret scopes come in two variants. A Databricks-backed scope keeps secrets in the platform, and we write them with the Databricks CLI or APIs. A scope linked to Azure Key Vault is instead a read-only window onto an existing vault: secrets are created and rotated in Key Vault, and Databricks reads them from there. This link has its own requirements on the vault's permission model and network configuration, which determine which vaults can be used.

Anyone who can read a Key Vault-backed scope can retrieve every secret that vault exposes. If developers and production operators must see different secrets, they therefore need separate vaults and scopes.

Databricks redacts secrets when they appear verbatim in cell output, replacing them with [REDACTED]. Code that can read a secret can, however, also transform it, print it character by character, or send it elsewhere, and in those cases redaction does not recognize it. Logs, URLs, cluster configurations, and environment variables are where a secret most often ends up exposed beyond the scope's perimeter.

Rotating a secret takes three steps: create the new credential, have consumers start using it, and only then retire the old one. A running cluster may have read the value at startup, for example into an environment variable, and keep using the old one until it restarts. Rotation is complete when a connection with the new credential succeeds and the old one is no longer in use.

4.7 Diagnose an Authorization Failure

Let's summarize the chapter by following the orders job reading the landing volume. When something fails, we walk the chain in the same order:

  1. Which identity does the task run under? It is the execution principal, which can differ from whoever wrote or deployed the job.
  2. Do workspace permissions let that identity use the notebook and the compute?
  3. Does the identity hold USE CATALOG, USE SCHEMA, and READ VOLUME, directly, through a group, or by inheritance?
  4. Does the request come from a workspace allowed by the bindings, and does the compute support this kind of access?
  5. Does the storage credential still hold its Azure role on the storage, and does the network let the connection through?
  6. If the task also connects to a database with a secret, can the identity read the scope, and is the credential still valid for the remote service?

The security lab lets us try these controls. A complete check has two sides: an authorized principal reads successfully and an unprivileged principal is rejected, so we know that access works and that the restriction is really enforced. Managed identity and Key Vault exercises require Azure resources; Free Edition covers a narrower administration scope.

5. Governance, Retention, and Sharing

The previous chapter answered the question "who can access this data?". Governance widens the view to other questions about the same data: what it means, who is responsible for it, how long it must be kept, who uses it downstream, and with whom we share it outside the organization. In the orders pipeline these questions have concrete answers: the exact definition of "revenue", the people allowed to classify a field as sensitive, the days during which a deleted order can still be recovered, the reports that depend on a column, the partners who receive regional data. In this chapter we take them in order.

5.1 Metadata and the Data Contract

Let's start with meaning. A table schema says that order_total is DECIMAL(18,2), a number with two decimals, but leaves many questions open: which currency it is in, whether it includes tax, how refunds are represented. A data contract collects these answers, together with the table's grain, the source it comes from, and how often it is refreshed. Without this information two analysts can sum the same column and get incompatible numbers, one in euros with VAT and the other in dollars without.

Take the daily_revenue table. The word "day" can mean the order date or the payment date, and it changes with the timezone: an order placed at 23:30 in Rome already falls on the next day in UTC. The contract also states which order statuses count toward revenue and what happens when an order is cancelled after publication: does that day's total change or stay as it was? A query is correct when it implements exactly this definition, and that holds for queries generated automatically by an assistant too.

Metadata is also part of what we deliver. Descriptions, grants, owner, and dependencies are attached to the table, and a release that drops and recreates it can lose them all at once, even if the reloaded data is identical. A correct release therefore preserves both the rows and these properties.

Databricks can generate table and column comments with AI. The model derives meaning from the context it receives, such as column names and sample values, and can therefore get details like currency or tax treatment wrong. A generated comment becomes reliable metadata after it has been checked against the source definitions and the transformation rules.

5.2 Attribute-Based Policy Selection

In chapter 4 we saw how to mask an email column with a function attached to the column. Now suppose emails appear in hundreds of tables: attaching the mask one column at a time becomes unmanageable, and every new table risks staying unprotected. Attribute-based access control (ABAC) turns the approach around. We classify data with tags and write a policy that says: "every column tagged pii=email is masked for anyone outside customer support". A new table with a classified column receives the protection automatically.

Four elements take part in the evaluation, which we follow with the email example. The governed tag pii is defined at account level, with its allowed values, such as email or phone, and the list of who can assign it. The classification is the assignment of the tag to a concrete column, for example customers.email. The policy, defined on a catalog or schema, states which columns it applies to (those tagged pii=email), which principals it affects (everyone except customer-support), and which control to use. The function, finally, contains the mask or filter logic, like the mask_email of chapter 4.

The tag classifies the data, the policy chooses the control, and the function applies it. All of this happens after the privilege check: a user without SELECT on the table is rejected before policies come into play. An important security consequence follows. If someone removes the pii=email tag from a column, the mask stops applying, so whoever can assign and remove tags belongs to the security perimeter just as much as whoever grants privileges.

To find out whether policies really cover what they should, we observe the results: a newly classified column should appear masked to an ordinary user and in clear to a support member. Conflicts can also arise. If two policies apply different masks to the same column for the same user, Databricks rejects the query with an error. These cases surface as the catalog grows and policies overlap.

Policy functions run inside every query, so they add cost. A simple expression, such as a CASE on group membership, is easy to optimize; a function that looks up other tables for every row can slow reads considerably.

5.3 Retention Has Several Independent Clocks

Now the lifecycle. "How long do we keep orders?" sounds like a single question, but it actually concerns different kinds of information, each with its own lifetime and mechanism, as the table shows.

Retained information Why it matters Mechanism to inspect
Current business records Business/legal record retention Explicit lifecycle rules and row-level changes
Older table versions and data files Time travel and recovery Delta log/file retention and maintenance
Streaming progress and state Correct continuation after restart Checkpoint storage and source retention
Audit and lineage evidence Investigation and impact analysis System table/API/export retention
Copies held by consumers or backups Deletion and recovery obligations Separate downstream policies and contracts

Let's dwell on the second row, the one that causes most misunderstandings. Reading a past version with time travel requires two things: that version's metadata in the Delta log and the data files it references. Each has its own retention: the log keeps versions for a period set by delta.logRetentionDuration, thirty days by default, while files removed from the current version stay available for the period set by delta.deletedFileRetentionDuration, seven days by default, after which VACUUM can delete them. The recovery window ends when the shorter of the two expires. If the business wants to be able to go back 30 days, both properties must cover at least 30 days.

Let's look more closely at what VACUUM deletes. The command removes only files that no recent version uses any more and that are older than the retention threshold. A file containing 2019 orders stays in place as long as the current version of the table uses it, because the VACUUM threshold is measured from the moment the file left the table. Deleting old orders according to a business rule therefore first needs a statement such as DELETE, which removes them from the current version; only later does VACUUM reclaim the space of files no longer used.

Three commands let us observe this situation on a table:

SHOW TBLPROPERTIES sales_prod.silver.orders;
DESCRIBE HISTORY sales_prod.silver.orders;
VACUUM sales_prod.silver.orders DRY RUN;

The first shows the table properties, including retention. The second lists the commits, with date, operation, and user. The third, thanks to DRY RUN, lists the files VACUUM would delete without touching them. The retention threshold protects whoever is still using older files: a long query started on a previous version, a writer preparing a commit, a stream that needs to resume, a rollback. Shortening it too much can make files disappear while someone still needs them.

5.4 Logical Deletion and Physical Erasure

Suppose a customer asks for their data to be deleted. A DELETE on the customers table removes their rows from the current version, and from that moment no ordinary query sees them. The data still exists, though: previous versions, reachable through time travel, still reference the files that contain it. Moreover, if the table uses deletion vectors, the DELETE only marks the rows as deleted, and the original files stay intact until they are rewritten.

A complete deletion therefore takes a sequence of steps. We identify all of the subject's data; we delete it logically with DELETE; we propagate the deletion to derived tables; we rewrite files to physically remove the rows marked by deletion vectors, for example with REORG TABLE ... APPLY (PURGE); we wait for retention to expire and run VACUUM to delete the old files; and finally we check that no copies remain elsewhere. With deletion vectors, rewriting and cleanup are two separate operations, each one necessary.

Propagation to derived tables deserves attention, because the archived course contains a misleading example. A stream reading from a Delta table fails when the source receives updates or deletes, and the skipChangeCommits option lets it continue by ignoring those commits. Rows already copied downstream stay where they are, though: skipChangeCommits avoids the error and leaves the deletion still to be done. Propagating it really takes other routes: read the deletes from the change data feed and apply them downstream, coordinate a DELETE on every derived table, or recompute the derived tables from the current state of the source.

Behavior also depends on the kind of downstream table. A materialized view recomputed from the source reflects the deletion at the next refresh; a table fed only by appends keeps the old rows until someone deletes them explicitly. And beyond tables there are exports, checkpoints that may contain sensitive data, recipient copies, and backups, each with its own lifecycle that the deletion must pass through.

What must be proved, and which exceptions are allowed, is decided by legal and governance owners. The technical process produces the records of the deletions performed and verified for that scope.

5.5 Maintenance and Storage Lifecycle

On Unity Catalog managed tables, predictive optimization runs maintenance automatically: it compacts small files, runs VACUUM, and updates statistics. Automatic cleanup also respects the retention configured on the table, so the considerations of section 5.3 apply even when nobody runs VACUUM by hand.

Then there is the temptation to use Azure storage lifecycle policies, which move files to the archive tier or delete them based on age. On a Delta table this is risky. Delta versions and streaming checkpoints reference specific files: if a policy deletes a file still in use, reads and recoveries fail; if it moves it to the archive tier, which is offline, the file becomes readable again only after a rehydration that can take hours.

A file's age also says little about the age of the data inside it. File age records when it was written; the order date describes when the event happened. Yesterday's compaction may have written five-year-old orders into a new file. To archive old data safely we move it with table operations, for example copying it to an archive table and then deleting it from the operational one, so both remain queryable.

5.6 Lineage, History, and Audit Answer Different Questions

When something changes or goes wrong, we want to know what happened. Databricks offers three sources of information, each suited to a different question. Lineage answers "what depends on what?": it records the observed dependencies between tables, views, notebooks, jobs, and dashboards. If we want to change the type of order_total, lineage shows which consumers will be affected. Table history answers "what changed in the data?": it records every Delta commit with operation, user, and version. Audit answers "who did what?": it records user actions on the service surfaces, such as opening a table or changing a permission.

Each source records a precise fact, and we need to avoid asking it for more. The getTable audit event, for example, records that someone looked up a table's metadata, which is quite different from reading its data. And none of the three sources proves that a transformation is correct: data validation proves that, while audit and execution events document who read what and when.

This information is consulted in different ways. Catalog Explorer shows each object's owner, dependencies, and history. Lineage system tables allow analysis with SQL queries, and audit logs, available in system tables or delivered to external destinations, support investigations of activity. What we see depends on each source's retention, the region, the execution paths the platform can trace, and our own permissions. In the lineage graph, a masked node indicates an object that exists but that we lack permission to see.

Back to the type change of order_total. The impact includes downstream tables, jobs, views, and dashboards. Lineage shows the dependencies it observed; code and data contracts add references that escape capture, such as an external script reading the table. Compatibility tests finally tell how consumers behave with the new definition.

One last note concerns verbose audit logging, which also records the text of executed commands. It increases the detail available for an investigation, but it can contain sensitive data written into queries, so these logs also need appropriate permissions and retention. Delivering logs to Azure Monitor, a storage account, or a SIEM is configured separately with Azure diagnostic settings.

5.7 Share Deliberately

One question remains: how do we give data to someone outside our organization? Delta Sharing is the protocol Databricks uses for this. The provider creates a share, a package of tables and other objects to share, and a recipient, which represents the receiving party, and then grants the recipient access to the share. Sharing comes in two modes. In Databricks-to-Databricks sharing the recipient also uses Databricks with Unity Catalog, and access relies on their metastore identity. In open sharing the recipient uses any client and authenticates with a token or a supported federation. The shareable objects and available features depend on the mode.

In the orders example we share approved regional revenue with a partner. We could share the whole gold schema, but then tables created in the schema in the future could also end up in the share, and exposure would grow with the schema without anyone deciding it. Sharing the approved table explicitly keeps the scope clear and stable.

With token-based open sharing we must manage the token's lifecycle: deliver it securely, set its expiry, rotate it, and revoke it when needed. If the same dataset must show different rows to different recipients, we can share a view that filters on recipient properties, such as country. To check what a recipient receives, we run the query in their context and observe the result.

Revoking access closes the share for the future. Data the recipient has already copied into their own systems stays under their control, though, and its retention and deletion follow the agreement made with them. If the recipient is in another cloud or region, every read also carries data transfer costs.

5.8 Governance Exercise

Let's recap with the orders pipeline. 6. Ingestion, Streaming, and Schema Evolution

Ingesting data means bringing a source's new information into the platform while remembering how far we have got. This memory of progress is the heart of the problem: if a pipeline stops halfway, on restart it must know what it has already loaded, so it neither loses nor duplicates data. How progress is recorded depends on what the source delivers. If it delivers files that never change again, remembering which files we have read is enough. If it delivers a complete picture of its state, a snapshot, we can replace the previous copy. If it delivers events, operations on entities such as "order created" or "order cancelled", we must apply them in the right order. In this chapter we start from the source and arrive at the Databricks tools for each case.

6.1 Start With the Source Contract

Let's begin by telling events and state apart. An event feed records transitions: "order O1 was created", then "order O1 was cancelled". The same order_id therefore appears several times, and each time it carries new information. A current-state table instead keeps one row per order, with the latest accepted version. The feed keeps the sequence of events; the table summarizes them into a state.

Before choosing a tool we need to know what the source promises, its contract. What are the keys? How are updates and deletes signaled? In what order do records arrive? How can the schema change? How long does the source keep data, so that we can reread it after a failure? The contract also says whether an extract is consistent. A transactional snapshot captures the source at one precise instant; an extract taken while the source keeps changing can read some rows before a change and others after it.

The extraction method follows from these answers. With a snapshot we replace or reconcile the previous copy. With a cursor we read rows whose update value, such as an updated_at column, exceeds the one saved at the last run. With CDC (change data capture) we read operations directly from the database log. The cursor has two weak points worth knowing. A physically deleted row disappears from the source table and therefore from cursor queries too: seeing it requires an explicit delete signal. And several rows with the same updated_at value, or overlapping batches, can cause the same row to be read twice, so it must be deduplicated or ordered with a tie-breaking rule.

The table summarizes the most common approaches and the correctness question each one raises.

Source behavior Candidate approach Main correctness question
Small periodic full dataset Snapshot/CTAS/replacement Is the snapshot complete before it is published?
Recurring immutable files COPY INTO or Auto Loader How are already discovered files and duplicated business events distinguished?
Supported operational database changes Managed Lakeflow Connect CDC connector Can the source retain changes through gateway/pipeline outages?
Event bus Structured Streaming with a supported connector Which offsets, event schema, and retention window govern replay?
Unsupported/custom source Notebook or external extraction service Who implements progress, retries, throttling, and delete handling?

Sometimes ingestion scheduling lives outside Databricks. Azure Data Factory, for example, can orchestrate copies across many systems and call Databricks to process the data. In that case Data Factory decides when to start and when to retry, while deduplication and transactions stay in the code that reads and writes in Databricks. For this reason scheduling has a single owner: two orchestrators each retrying on their own can launch the same load twice.

6.2 SQL Loading Methods Have Different Repetition Semantics

The simplest way to load data is SQL. The three main methods behave differently when we rerun them, and that behavior is exactly what decides which one to use.

The first is CTAS (CREATE TABLE ... AS SELECT), which creates a table from a query result. With IF NOT EXISTS it creates the table only if it is missing: on the second run the table already exists and stays unchanged. It suits the initial load of a dataset.

The second is CREATE OR REPLACE TABLE ... AS SELECT, which on every run replaces the table's contents with the query result. The scope of the query matters here. If the query selects only yesterday's orders, after the run the table contains only yesterday's orders, and those of earlier days are gone. The replacement is exactly as wide as the input.

The third is COPY INTO, designed to load files incrementally. It remembers which files it has already loaded into the target Delta table and skips them on later runs. We can therefore rerun it without fear of duplicating files already read: it is idempotent at file level. That idempotency concerns files, though. If the same order appears in two different files, both are new files and the order is loaded twice; guaranteeing that every business event appears only once takes a rule on rows, as we see later.

COPY INTO sales_dev.bronze.order_events
FROM '/Volumes/sales_dev/bronze/order_files/incoming/'
FILEFORMAT = JSON;

Running the example requires a compatible target table and a valid path. File tracking has a few exceptions worth knowing: a forced load with the force option, a file modified after the first load, replacing the target table, or wiping its state can make already-read files load again. In every case COPY INTO decides what is new based on the state it has kept.

When files arrive in large numbers and with structures that change often, COPY INTO shows its limits. For these cases there is Auto Loader, which discovers new files continuously even across millions of files and handles schema evolution more richly. Before looking at it, though, we need the engine it relies on.

6.3 Structured Streaming Is Incremental Execution With State

Structured Streaming is Spark's engine for incremental processing. The idea is to treat a source that grows over time as a table that keeps receiving new rows. We write a query as if we were working on static data, giving source, transformations, and destination (the sink), and Spark runs it piece by piece, processing only the new data at each step. To do so it must remember how far it has read and, for operations such as aggregations or deduplication, also some intermediate state, such as partial totals or identifiers already seen.

This memory lives in the checkpoint, a durable folder dedicated to a single query. If we restart the query with the same checkpoint, it resumes exactly where it stopped. If we give it a new checkpoint, the query has no memory and starts reading again according to its initial options, which can mean rereading everything. Two different queries sharing the same checkpoint overwrite each other's progress and state, with unpredictable results.

Let's see how Structured Streaming guarantees that no data is lost or duplicated after a failure. Three ingredients are needed: a source that allows rereading data from a given position, a checkpoint that remembers that position, and a sink that records writes in coordination with the checkpoint. With a Delta sink all three are present, and every record is written exactly once (exactly-once). If instead the query sends an email or calls an external API for each batch, a failure halfway through a batch makes the batch repeat, and with it the email or the call. These external effects need their own way of recognizing repetitions, such as a batch identifier that the receiver checks.

The output mode decides which rows the query emits at each step. With append it emits only new rows; with update it emits the result rows that changed, such as updated totals; with complete it emits the whole result each time, in the combinations where this is supported. The output mode decides what leaves the query, and applying those rows to a table by key, updating existing ones, is a further operation, typically a MERGE.

6.4 Auto Loader Separates File Discovery From Row Meaning

Auto Loader is a Structured Streaming source specialized for files. It keeps track of the files it has already discovered and finds new ones in two ways: by listing folders periodically (directory listing) or by receiving notifications when a file is created (file events). Notifications avoid relisting huge folders every time, but require configuring the cloud resources that produce the events, as we saw in chapter 4.

Let's look at a complete example that reads the orders' JSON files and writes them to a bronze table:

incoming = "/Volumes/sales_dev/bronze/order_files/incoming/"
state_root = "/Volumes/sales_dev/bronze/ingestion_state/orders/"

order_stream = (
    spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", state_root + "schema")
    .load(incoming)
)

query = (
    order_stream.writeStream
    .option("checkpointLocation", state_root + "checkpoint")
    .trigger(availableNow=True)
    .toTable("sales_dev.bronze.order_events")
)
query.awaitTermination()

Let's read the code from the top. The cloudFiles source is Auto Loader, which we tell that the files are JSON and where to keep the schema it derives from the data (schemaLocation). The write names the checkpoint and the target table. The availableNow trigger processes all the files present at startup and then stops the query, and awaitTermination() waits for it to finish. Running the example requires the volumes, the permissions, and a compatible runtime. /Volumes/ paths have the form catalog, schema, and volume separated by slashes. The operational state sits in a different volume from the incoming files, so Auto Loader never mistakes its own metadata for data to load.

Three artifacts therefore take part in this example, each with a role. The schema location keeps the schema derived from the data; the checkpoint keeps progress and state; the target table keeps the committed output. For a correct recovery the three must stay consistent with one another: deleting the checkpoint while keeping the table, for example, makes files already present in the target load again.

Auto Loader solves file discovery, and event duplication remains a separate problem. Suppose event evt-100 appears in two different files, perhaps because the source retried a delivery. To Auto Loader they are two new files, and it loads both correctly. A later step must recognize that the two rows represent the same event, using its identifier or sequence, and keep only one. File discovery and event deduplication work at different granularities: the first on files, the second on rows.

6.5 Schema Inference, Evolution, and Rescue

JSON files declare no schema, so Auto Loader must derive one by observing the data. This process is called inference and has natural limits. A sample may lack rare values, and a value that looks like a number can have a textual meaning. Think of a postal code such as 00184: treated as an integer it becomes 184 and loses its leading zeros, while as a string it stays correct even though it consists only of digits.

For this reason, with text formats such as JSON and CSV, Auto Loader by default treats every column as a string, a cautious choice that loses no information. We can ask it to infer types with the cloudFiles.inferColumnTypes option, or fix the type of some columns with schema hints. The schema describes the expected structure; what remains to decide is what to do with records that fall outside it.

The changes that can arrive are of two kinds. Structural changes alter the shape of the data: a new column appears, or a column changes type incompatibly. Semantic changes alter meaning while the shape stays the same: an amount switches from local currency to dollars and remains a decimal. The schema catches the former; only checks on the data contract, which know what the columns mean, catch the latter.

For structural changes Auto Loader offers several evolution policies, compared in the table.

Evolution policy Expected operating choice Consequence to plan for
Add new columns Accept compatible structural growth Detection can update stored schema and stop the stream; the documented restart procedure is still required.
Rescue unexpected fields Preserve unexpected input outside the main schema Rescue counts expose structural mismatches for review and reprocessing.
Fail on new columns Require an explicit contract change Processing resumes after the input or accepted schema is corrected.
Ignore new fields under the selected mode Preserve a stable projection Information may not reach the intended columns; this is a deliberate loss/omission policy.

The default policy, which adds new columns, behaves in a way that surprises people the first time: when Auto Loader finds a new column, it updates the stored schema and stops the stream with an error. On restart the stream resumes with the updated schema. In production we therefore plan for an automatic restart, for example through job retries.

A special case is type widening, which Delta supports for some combinations depending on the runtime and the table features. Going from INT to BIGINT widens the range of representable values, and every old value remains valid in the new type. Converting a string to an integer is a different operation: it interprets the content and can fail on values such as "n/a".

With the rescue policy, values that do not fit the schema land in the _rescued_data column, as JSON, and are kept for later. Counting how many rows have this column populated gives a direct measure of the incoming mismatches. And when we decide to accept a new column into the schema, we can reprocess the rescued rows and move their values into the right columns.

6.6 Triggers and Processing Cadence

A streaming query can also run at intervals. The trigger decides when to process. With availableNow, which we used in the example, the query processes everything available at that moment and then stops. Scheduling this query every hour gives incremental processing, thanks to the checkpoint, with compute that stays on only for the time needed.

With a processing time trigger the query stays active and runs a micro-batch at regular intervals, for example every minute. If a batch takes longer than the interval, the effective cadence slows accordingly; if data arrives faster than the query can process it, the backlog grows. The word "continuous" also needs care, because it names three different things: the continuous mode of a declarative pipeline keeps it always active; a continuous job starts a new run as soon as the previous one ends; Spark's continuous processing is a separate execution mode with very low latency.

Data freshness for consumers depends on the whole chain: how often the source produces data, how long compute takes to start, how long processing lasts, and how often we schedule it. If the source produces a snapshot every hour, querying it every minute makes the data no fresher. And if a report tolerates a 30-minute delay, an incremental run every 15 minutes with availableNow satisfies it and costs far less than an always-on stream.

6.7 Event Hubs and Kafka-Compatible Ingestion

Let's move from files to real-time events. Azure Event Hubs is an event streaming service that also offers a Kafka-compatible endpoint, so Spark can read it with its standard Kafka source. Every record read contains a few fixed columns: the topic, the partition, the offset (the record's position in the partition), a timestamp, and a key and a value in binary format. Our code must decode the value, for example from JSON, into typed columns. Partition and offset are worth keeping, because they identify each record's position in the source precisely: when we find a duplicate or a malformed event, they tell us where it came from.

Connecting requires the endpoint address, an encrypted TLS connection, an authentication method, the event hub name, which corresponds to the topic in Kafka, and permissions to read it. Credentials come from a secret or a supported identity. The archived course also mentions a native Event Hubs connector: it is a separate integration, with its own format, dependencies, options, and schema.

That leaves the starting point. Options for the starting offsets, such as earliest or latest, apply only to a new query; a resuming query uses the position saved in the checkpoint. Resuming works, however, only if the source still keeps records from that position on. Event Hubs keeps events for a limited period: if the query stays stopped longer, the intermediate events are lost even if the checkpoint is intact.

6.8 CDC, Delta Change Data Feed, and AUTO CDC

Three similar names refer to different things. CDC is the general pattern: capturing a source's inserts, updates, and deletes. Delta Change Data Feed is a Delta feature that exposes the changes of a Delta table across retained versions, as we saw in chapter 7. AUTO CDC is a Databricks declarative pipeline statement that applies a stream of changes to a target table. They can work in a chain: a table's change feed can be the source of AUTO CDC.

To be usable, a change record must tell us three things: which entity it concerns (the key), what happened (the operation), and in which order to apply it (the sequence). A timestamp can serve as the sequence only if the source guarantees enough precision or supplies a tie-breaker for equal values. The arrival time in the platform is an unreliable sequence instead, because networks and retries can deliver events in a different order from the one in which they happened.

For databases, Lakeflow Connect offers managed connectors. Some combine an initial full load with continuous reading of changes from the database log; others extract data with queries and cursors. Components such as the gateway, the technology used to read the log, schema handling, and rereading options vary from connector to connector.

AUTO CDC applies changes using the key and the sequence, and can produce current state (SCD type 1) or full history (SCD type 2). The source contract must clarify two delicate cases. The first is deletes, which must be recognizable from an operation field. The second is partial updates: if a change record omits a field, it means "keep the previous value"; if it explicitly sets it to NULL, it means "clear the value". NULL handling during change application must respect this distinction.

Delta's change feed, finally, represents every update with two rows, the preimage and the postimage. Whoever consumes it must apply the operation type: counting every row as a new fact would count every update twice. The change feed is available for the table's retention period, and keeping changes longer means copying them into a history table, as we saw in chapter 7.

6.9 Recovery Exercise

Let's check the chapter's rules with five inputs arriving at the orders pipeline. A new file is discovered and loaded. An already loaded file is recognized by tracking and skipped. The same event contained in a different file passes discovery, because the file is new, and is then removed by row deduplication. A new column follows the chosen schema evolution policy. A cancellation arriving out of order is placed correctly thanks to the source sequence.

Now suppose a run stops halfway. Restarted with the original checkpoint, it resumes from the recorded progress and nothing is lost or duplicated. Restarted with a new checkpoint, it starts again without memory and can reread input already processed. Whether this changes the result depends on how idempotent the pipeline is with respect to events: with deduplication by event identifier, the reread leaves the table unchanged.

7. Table Design, Transactions, and History

A table answers questions well only if we know precisely what each of its rows represents. In this chapter we start right there: we see how the meaning of a row is established, how keys recognize entities, and which measures can be summed without errors. Then we move to how Delta Lake stores the model in files, how it handles concurrent writes, and how the history of changes is represented. We close with physical layout, which leaves results unchanged and decides how much it costs to obtain them. Throughout the chapter we use the same example: an online shop with orders, order lines, and customers.

7.1 Grain, Keys, and Measures

Suppose we have an order O1 with three products and a shipping fee of 9 euros, which the customer pays once for the whole order. If we load the order into a table with one row per product and copy the shipping fee onto every row, we get this:

order_id line_id Product Amount Shipping
O1 1 Book 20 9
O1 2 Pen 5 9
O1 3 Notebook 8 9

The sum of the amounts is 33 euros and is correct. The sum of the shipping column is 27 euros, while the customer paid 9. Every row was loaded correctly: the problem arises because shipping belongs to the order, while each row of the table represents a single product of the order.

This "what one row represents" is called the table's grain. In the table above the grain is the order line: one row for each product of each order. An orders table would have order grain, with one row per order; an order-status events table would have one row for each change, such as "paid" or "shipped". Fixing the grain is the first design decision, because it determines which calculations give correct results.

We call a measure a numeric value that we aggregate, such as an amount or a quantity. A measure can be summed freely when it belongs to the same grain as the table. Amount and quantity belong to the order line, so their sum is correct. Shipping belongs to the order: to sum it correctly we must take it once per order, or keep it in a table with order grain. The same reasoning applies to counts. A customer snapshot table holds one row for each customer existing on a given date, so counting its rows tells us how many customers there were; an events table holds one row for each transition, so counting its rows tells us how many transitions happened. Both numbers are useful and answer different questions.

Once the grain is fixed, we need a way to recognize each row. The business key is the identifier the source system uses for the entity: for the order line it is the pair (order_id, line_id), for an event it can be its identifier or the order key together with a sequence number, for a customer it is the customer code. If the grain is respected, each business key appears only once in the table; finding it twice signals a duplicate or a grain different from the declared one.

The business key is enough as long as we care only about the current state. Now suppose customer C42 moves from the North region to the South region and we want to remember both situations. The customers table will then hold two rows with the same code C42, one for each version. To tell them apart we introduce a surrogate key: an identifier generated by the data platform that points to one specific stored row, that is, one specific version of the customer. The business key says "which customer"; the surrogate key says "which version of that customer". We return to this example in section 7.5.

To generate surrogate keys Delta offers identity columns, which automatically assign a unique value to every new row. The values are unique and can have gaps in the numbering. Databricks also disables concurrent write transactions on tables with an identity column, so this choice is weighed together with the way the table is loaded.

What remains is to describe how tables connect. In Unity Catalog we can declare primary key and foreign key constraints, for example that customer_id in the orders table refers to the customers table. These constraints are informational: Databricks records them and shows them to whoever explores the model, and with the RELY option the optimizer can use them to simplify some queries. Databricks still accepts rows that violate them, though. If we load the same order line twice, the primary key stays declared and the duplicate still enters the table. Actual verification is therefore the pipeline's job, checking that keys are unique and that every reference finds its matching row. The constraint describes how the data should be; the check measures whether it really is. With RELY this check becomes even more important, because the optimizer trusts the declaration and, if the data violates it, can return wrong results.

7.2 File Formats and Table Formats Solve Different Problems

Once we have decided what each row represents, we must choose how to store it in files. Two levels come into play here, and it helps to keep them apart: the file format and the table format.

The file format decides how data is written inside each file. CSV and JSON write text records one after another. They are convenient for exchange between systems, but whoever reads them must decide every time the column types, how to treat quotes and separators, what to do with malformed records, and how to represent nested structures. Parquet is a columnar format instead: it stores values column by column, with declared types and compact encodings. An analytical query that uses three columns out of fifty reads only those three, and this is why Parquet suits analytics.

A set of Parquet files is still just a set of files, though. If one process writes new files while another reads, the reader can see half of the work; if a write is interrupted, orphan files remain. The table format solves this problem with a metadata layer that says which files make up the table at each moment. Delta Lake keeps a transaction log, the _delta_log folder, in which every commit records which files were added and which removed. A reader consults the log and always sees a complete version of the table. Transactions, schema evolution, time travel, and the change data feed, which we see in the next sections, all rest on this log. Apache Iceberg follows the same idea with its own metadata system and its own ecosystem of engines.

In Databricks, Delta is the default format and is integrated with ingestion, change handling, and automatic maintenance. Iceberg becomes interesting when other engines must read and write the same table through that protocol. In both cases interoperability depends on several factors together: which engines read, which write, which catalog they use, and which table features they understand. A Delta table using a recent feature, such as deletion vectors, can be unreadable to an external reader that does not yet support it.

This choice is independent of the one between managed and external tables, which we saw in chapter 2. Managed or external says who manages the file lifecycle; the format says how those files become a table. An external table in Delta format still has a log and transactions, while an external CSV table simply exposes the text files, with only the operations that format allows.

7.3 Transactions and Concurrent Writers

The log lets Delta treat every write as a transaction. Let's see what this means in practice and how far the guarantee reaches.

Every commit creates a new version of the table, and every version describes a consistent snapshot: a reader sees all the changes of that commit or none of them. If a MERGE on the orders table must update a thousand rows and is interrupted halfway, none of the thousand changes becomes visible.

The guarantee covers a single statement on a single table. Suppose the pipeline, after updating orders, writes a row to the audit table. These are two statements and therefore two separate transactions: a reader can see the updated orders before the audit row appears, and if the second statement fails the orders stay updated without audit. To handle this case we give every run an identifier, for example the batch ID, and write it into both tables. A reconciliation process can then find batches present in orders and missing from the audit, and complete the publication. Where Databricks offers multi-statement transactions, and the use case is among the supported ones, the two writes can also go into a single commit.

What happens when two processes write to the same table at the same moment? Delta uses optimistic concurrency control. Each writer reads the current version, prepares its changes, and at commit time checks whether someone else has written in the meantime. If the two writes touch different data, such as two appends of new orders, both succeed. If they touch the same files, such as two UPDATEs on the same orders, the second commit fails with a conflict error. The table's isolation level and features such as deletion vectors and row-level concurrency affect how often conflicts occur.

When a commit fails because of a conflict, the new attempt must start from the updated version of the table, so the computation includes the changes committed in the meantime. If instead we rewrote the result prepared in the first attempt, for example with an overwrite, we would erase exactly those changes.

Transactions also protect the table's structure. With schema enforcement Delta rejects a write whose columns or types do not match the schema: a string amount column is rejected by a decimal column. With schema evolution, which we enable explicitly, we accept supported changes such as adding a new column. Both mechanisms reason only about types. An amount of -50 euros is a valid decimal and passes the schema, even though for orders it is an error: catching it takes the quality checks of chapter 8. Then there is the consumers' side: even a schema change accepted by Delta can break a report that reads columns by position or expects a fixed list of columns.

7.4 Choose the Required Kind of History

Let's turn to data history. The question "what was this data like in the past?" has different answers depending on what we want to remember and for how long, and Databricks offers a mechanism for each. The table compares them.

Mechanism Information represented Retention and interpretation
SCD type 1 Current accepted attribute values Each update replaces the previous value in the business model.
SCD type 2 Attribute values with business-validity intervals Ordered changes create versions; interval checks establish consistency.
Delta time travel A table snapshot at a retained version or time Availability follows retained log metadata and data files.
Delta Change Data Feed Row-level changes across retained versions Capture begins at enablement and replay follows source retention.
Persisted change-history table Captured events or versions in a separate table Its own retention can extend the history; coverage follows successful capture.

The first two rows concern the data model, choices we make in the design. A slowly changing dimension (SCD) is a dimension table whose attributes change rarely, such as a customer's region. With SCD type 1 every change overwrites the previous value: the table answers "where is C42 today?" and forgets the rest. With SCD type 2 every change closes the current version and opens a new one with its own validity interval: the table also answers "where was C42 when they placed the March order?". There are more limited variants: type 0 keeps the original value and ignores later changes, type 3 keeps only the previous value next to the current one.

The other three rows concern the table's technical history. Time travel lets us read a past version, for example with VERSION AS OF 12, as long as the log and the files of that version exist. Log retention, thirty days by default, and VACUUM, which by default deletes files removed more than seven days ago, limit its horizon. The change data feed records changes row by row between one version and the next, starting from the moment we enable it and for the retention period. Time travel and change data feed therefore serve recoveries, recent audits, and propagation of changes to other tables. A history that must last for years is kept in a dedicated table, as we see in section 7.6.

One distinction about time remains. Business time says from when a fact is true in the real world; processing time says when the system recorded it. Suppose C42 moves on Monday and the change reaches the pipeline on Wednesday. If we used the load time as the start of validity, Monday's and Tuesday's orders would be attributed to the wrong region. By keeping both timestamps we attribute facts correctly and also know when the pipeline received the change.

7.5 Build SCD Type 2 Around Invariants

Let's return to customer C42, who at business time 2026-09-10 09:00:00 moves from North to South. In an SCD type 2 table the customer's history becomes:

Customer Region Valid from Valid to
C42 North 2026-01-01 00:00:00 2026-09-10 09:00:00
C42 South 2026-09-10 09:00:00 NULL, meaning current

Each version has a start (valid_from) and an end (valid_to), and the current version has a NULL end. The intervals are half-open: they include the start instant and exclude the end instant. This way the exact instant of the move belongs to a single version, South, and every moment falls in exactly one interval.

With this structure we can link each order to the region valid at the moment it was placed:

SELECT fact.order_id, history.region
FROM sales_prod.silver.orders AS fact
JOIN sales_prod.silver.customer_history AS history
  ON fact.customer_id = history.customer_id
 AND fact.order_timestamp >= history.valid_from
 AND (fact.order_timestamp < history.valid_to OR history.valid_to IS NULL);

The join gives the right result only if the history respects a few rules that must always hold, which is why we call them invariants. For each customer the intervals do not overlap, otherwise an order would find two regions and be counted twice. There is at most one current version. Every interval starts before it ends. Order timestamps and history timestamps have the same meaning and the same timezone. Finally, rules are needed for edge cases, such as the order of a deleted customer or of one not yet present in the history.

Let's now see how this history is built from incoming changes. The first problem is order. If two changes for C42 arrive in the same batch, we need to know which comes first, and this requires a sequence field supplied by the source, such as a progressive number or a change timestamp. With type 1 keeping the batch's last change is enough; with type 2 every intermediate change becomes a version with its own interval.

The second problem is null values. In SQL the comparison NULL = 'North' returns NULL, so an ordinary comparison misses the change from a value to NULL or the other way round. To decide whether an attribute changed we use a null-safe comparison, such as the <=> operator, which treats two NULLs as equal and a NULL and a value as different.

The third problem concerns MERGE. A change to C42 requires two actions: closing the North version and inserting the South version. In a MERGE, however, each source row follows a single branch: if it finds a matching row it runs WHEN MATCHED, otherwise WHEN NOT MATCHED. The C42 row finds the current version and closes it, and stops there. The usual solution is to prepare the source so that every change appears twice: one copy with the customer key, which finds the current version and closes it, and one copy with a null merge key, which finds no match and is therefore inserted as the new version. This way closing and inserting happen in the same MERGE, and therefore in the same transaction. With one MERGE to close and a separate INSERT to open we would instead have two transactions: a failure between them would leave C42 without a current version, and two separate calls to current_timestamp() could return different instants, opening a gap between the end of one version and the start of the next. Using the change's business time as the boundary, in place of the execution time, also removes this risk.

All this work can be delegated. In Lakeflow declarative pipelines, AUTO CDC builds an SCD type 1 or type 2 table from a stream of changes, once the key and the sequence column are given, and handles ordering, out-of-sequence arrivals, and deletes. A manual implementation must solve the same problems on its own. In both cases the final check consists of verifying the invariants on the resulting table.

7.6 Persist Operational History When Required

In section 7.4 we saw that the change data feed keeps changes for a limited period. When we need a longer operational history, for example for multi-year audits, we regularly read the change feed and copy its content into a dedicated history table, governed in Unity Catalog and with its own retention.

The change feed describes each change with a few extra columns: _change_type gives the operation type, _commit_version the Delta version that produced it, and _commit_timestamp the commit time. An insert produces an insert row and a delete a delete row. An update produces two rows: the preimage (update_preimage), with the values before the change, and the postimage (update_postimage), with the values after. The history table keeps these values together with the source table and version, the event identifier when the source provides one, and two times: the source commit time and the ingestion time into the history. With this information we can explain why a row disappeared, which value it had before a change, and when we recorded it.

This history has two limits to keep in mind. The change feed records changes only from when it was enabled, so the history starts at that moment. Moreover, if the copy process stays stopped longer than the source's retention, intermediate versions are lost. To notice in time we compare the versions already copied with those available in the source: a jump in the version sequence indicates a gap, which we can still fill as long as the source keeps them.

7.7 Partitioning, Clustering, and Data Skipping

So far we have dealt with correctness: what a row represents, how it changes, how its history is kept. Physical layout answers another question: how many files a query must read to find the rows it needs. Two tables with the same data return the same results, but can read very different amounts of data to get there.

The basic mechanism is data skipping. For each file Delta records some statistics in the log, including the minimum and maximum of the indexed columns. Suppose a query asks for September orders: a file whose maximum date is August 31 cannot contain useful rows, and the engine skips it without opening it. By default Delta collects statistics on the first 32 columns of the table, and table properties let us name different columns. Data skipping works on any Delta table, but its effectiveness depends on how values are distributed across files. If every file contains orders from every month, minimum and maximum cover the whole year and no file can be skipped.

Layout techniques exist precisely to gather nearby values into the same files. Traditional partitioning splits the table into folders, one for each value of the partition column, for example one per day: a query filtering on a day reads a single folder. It works well with few large partitions, so much so that Databricks advises avoiding it for tables under a terabyte and aiming for partitions of at least a gigabyte. Partitioning by order_id, which is nearly unique, would produce millions of tiny folders, and the cost of managing them would exceed the benefit.

Liquid clustering reaches the same goal more flexibly. We name the clustering columns and Databricks, during OPTIMIZE, reorganizes the data so that rows with nearby values end up in the same files, without fixed folders:

ALTER TABLE sales_prod.silver.orders
CLUSTER BY (customer_id, order_timestamp);

Here we choose customer_id and order_timestamp because the most frequent queries filter by customer and by date range; the statement requires a table and a runtime that support liquid clustering. The keys can be changed later with a new ALTER TABLE. From then on new optimizations follow the new strategy, while data already written keeps its previous organization until we reorganize it, for example with OPTIMIZE FULL, which consumes compute in proportion to the table size. With CLUSTER BY AUTO we can also let Databricks choose the keys based on observed queries, within that feature's prerequisites.

Z-ordering is the earlier technique: OPTIMIZE ... ZORDER BY rewrites files bringing together the values of the given columns. On the same table it cannot be combined with liquid clustering, which Databricks recommends for new tables.

Two mechanisms complete the picture. Compaction, also performed by OPTIMIZE, merges many small files into a few large ones and reduces the cost of opening them one by one. Deletion vectors record deletes and updates by marking rows as removed, without immediately rewriting the whole file; the rewrite happens later, during maintenance. Each of these tools tackles a different cost: too many small files, scattered values, expensive rewrites.

7.8 Modeling Exercise

Let's put the pieces together with our example. With the join of section 7.5, a C42 order from September 5 finds the North version and an order from September 12 finds South. If the same region change arrives twice, the second copy has the same sequence and the history stays unchanged. If two changes have the same timestamp, the source's sequence field decides which comes first. If a change with a past business time arrives late, the history accommodates it in the right place and the interval that contained it gets shorter. If C42 is finally deleted, the table contract decides whether to close their last version or mark it as deleted.

The same table can then be stored without partitioning or with liquid clustering on customer_id and order_timestamp. The join returns exactly the same rows in both cases, but in the second it reads far fewer files. This is the distinction that runs through the whole chapter: grain, keys, and history decide whether results are right; layout and maintenance decide how much it costs to obtain them. The modeling lab lets us try these features with compatible compute and permissions.

8. Transformations and Data Quality

The data arriving in the bronze layer is what the source sent us, with all its defects: missing identifiers, amounts written as text, repeated events, updates arriving late. A transformation's job is to bring these records into line with the silver layer's contract. For orders, for example, the contract can require that every event has an identifier, that the timestamp is parseable, that the amount is consistent with the refund rules, and that repeated or superseded events are always handled the same way. Every rule in the contract has two parts: a condition to check and a decision about what to do with records that violate it. In this chapter we follow this path, from getting to know the data to publishing it.

8.1 Profile Before Choosing a Repair

Before repairing data we need to know what the input looks like. Profiling describes it with a few numbers: how many rows there are, how many have missing values, how often each key repeats, what the minimum and maximum values are, how they are distributed. These numbers become more useful when broken down by source, batch, or period, because a defect concentrated in a single day or a single source is easily lost in an overall average.

SELECT
  COUNT(*) AS total_rows,
  COUNT(*) - COUNT(order_id) AS missing_order_ids,
  COUNT(*) - COUNT(order_total) AS missing_amounts,
  MIN(order_total) AS minimum_amount,
  MAX(order_total) AS maximum_amount
FROM sales_dev.bronze.order_events;

The query relies on a property of COUNT: COUNT(*) counts all rows, while COUNT(order_id) counts only those where order_id is present, so the difference gives the number of missing identifiers. The result makes sense only if the columns already have the right type. If order_total were still a string, minimum and maximum would follow alphabetical order, and "9.50" would come out greater than "100.00". These are two different checks: parsing establishes whether a value can be represented as a number, and the range check verifies whether the resulting number respects the business rule.

There is also a choice between precision and cost. Exact counts serve when we must reconcile totals or verify a key's uniqueness over the whole population. Approximate counts, such as approx_count_distinct, cost much less and are enough for exploration. A sample, finally, describes only the observed rows: a defect affecting one row in a million can escape any reasonable sample, and measuring it takes the whole population.

8.2 Parse Types Without Concealing Information Loss

Choosing a column's type means deciding how to interpret its values, and some choices lose information without saying so. Amounts are the classic example. The DECIMAL type represents numbers with a fixed number of digits and decimals, exactly as we write them. Floating-point types, such as DOUBLE, use a binary representation that introduces small rounding errors: 0.1 + 0.2 is not exactly 0.3. Money therefore uses DECIMAL, with enough precision for calculations too: the yearly sum of many orders can need more digits than a single amount.

Identifiers need care too. A code like 00042 looks like a number, but converting it to an integer turns it into 42, and two different codes can become equal. As a string it stays intact. Timestamps carry a timezone, and the timezone decides which day an order belongs to: an order placed at 23:30 in Rome falls on the next day in UTC. A timezone change can therefore move revenue from one day to another even when every timestamp is valid.

When we convert a string to a number, we must decide what to do with values that cannot be converted. CAST in ANSI mode fails and stops the query at the first bad value. TRY_CAST instead returns NULL and lets processing continue. This creates an ambiguity, though: a NULL in the result can mean a value missing in the source or a value present but not convertible. To tell them apart we compare the result with the original value:

SELECT
  order_id,
  amount_text,
  TRY_CAST(amount_text AS DECIMAL(18,2)) AS order_total,
  amount_text IS NOT NULL
    AND TRY_CAST(amount_text AS DECIMAL(18,2)) IS NULL AS invalid_amount
FROM sales_dev.bronze.raw_orders;

The query keeps the original string amount_text, produces the converted amount, and adds an invalid_amount column that is true only when the source had a value and the conversion lost it. This way no error disappears into an anonymous NULL. A negative amount converted correctly passes this step and reaches the next rule, the business one, which decides whether it is a legitimate refund or an invalid order.

8.3 Null Semantics and Deterministic Deduplication

NULL values follow three-valued logic: a comparison can be true, false, or unknown. If amount is NULL, the condition amount <> 0 is unknown, and a WHERE clause discards rows whose condition is not true. A filter that seems to exclude only zeros therefore also excludes every missing amount. To look for missing values we use IS NULL; to compare two values while treating two NULLs as equal we use null-safe equality <=>. The same logic explains the difference between COUNT(*), which counts rows, and COUNT(amount), which counts present amounts.

NULL and zero mean different things. NULL says "we do not know what the amount is"; zero says "the amount is zero". Replacing NULLs with zero therefore asserts something we do not know, and if those orders had a real amount, revenue comes out understated. Facing a missing amount we have three possible policies: keep it as unknown, move the row to quarantine for review, or estimate it with a declared rule. Each is legitimate if the contract provides for it.

Now duplicates. Deduplicating takes two decisions: which records we consider equivalent, the key, and which record we keep among the equivalent ones, the survivor rule. If the rows are identical in everything, removing the copies is enough. If instead we have several versions of the same order, we must choose the most recent, and that requires an explicit ordering with a tie-breaker. A window function expresses exactly this:

SELECT *
FROM sales_dev.bronze.order_updates
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY order_id
  ORDER BY source_sequence DESC, event_id DESC
) = 1;

The query groups rows by order_id, orders them from the highest sequence to the lowest, uses event_id to break ties, and keeps the first row of each group. The result is deterministic: run twice on the same data, it always picks the same row. This works because the source contract gives meaning to the order of source_sequence and event_id; if event_id were a random identifier, its alphabetical order would say nothing about which event is more recent. The query returns the current state of each order and discards intermediate versions, which an SCD type 2 table would keep with the mechanism of chapter 7.

In streaming, deduplication has an extra problem: to recognize a duplicate arriving today, the query must remember the identifiers of events seen in earlier batches, and that memory would grow without limit. The watermark solves the problem by declaring how late an event can arrive, for example two hours after its timestamp. Beyond that threshold Spark forgets old identifiers. A duplicate arriving later goes unrecognized, and handling it follows the application's policy for late data and corrections.

8.4 Joins and Set Operations Change Cardinality

A join can change the number of rows in surprising ways. A left join keeps every row of the left table and produces one row for each match on the right. If an order finds two customer rows with the same identifier, for example because of a duplicate in the customers table, the order appears twice in the result and its amount is counted twice. An inner join removes orders that find no customer; an anti join returns exactly those orders, which makes it useful for finding them. Counting rows before and after a join, and counting those without a match, reveals these effects immediately.

A typical case is the join with a history table. If we join orders to customer_history only on customer_id, every order finds all of the customer's versions and multiplies. The temporal predicate of chapter 7 instead selects only the version valid at the time of the order. The same holds when we aggregate before a join to reduce data: the aggregation must keep the keys and information the join and the final measure need.

Set operations have their own rules on duplicates and column alignment. In SQL, UNION removes duplicate rows and UNION ALL keeps them. In PySpark, union keeps duplicates and aligns columns by position, so two DataFrames with the same columns in a different order put values in the wrong columns without any error; unionByName aligns them by name, and with the option for missing columns it also accepts different structures. Aligning names is only part of the job: the merged columns must also have compatible types and meaning, for example amounts in the same currency.

INTERSECT returns rows present in both sets, EXCEPT those present only in the first, and the DISTINCT and ALL variants decide how to treat duplicates. These operations compare whole rows. To compare two versions of the same entity attribute by attribute, for example to find what changed in a customer, a join on the business key is needed instead.

8.5 Reshaping, Grain, and Units

Many transformations change the shape of data, and some also change its grain. Flattening a nested structure, for example bringing address.city into a city column, adds columns and leaves the number of rows unchanged. Exploding an array with explode instead creates one row per element, and the grain moves from order to order line. If in the same order we explode both the array of lines and an independent array of discounts, every line combines with every discount: an order with three lines and two discounts produces six rows, a Cartesian product that usually nobody wanted.

A pivot turns the values of a column into columns, for example one column per region with its revenue, and usually aggregates. If we list the regions explicitly, the result's schema stays stable; if we let them be derived from the data, a new region in the source adds a column to the result and can break whoever consumes it.

An unpivot does the reverse: it turns measure columns into rows, each with the measure name and its unit. The labels keep the meaning that used to sit in the column name. A row with a NULL value represents an unknown measure explicitly, while omitting it changes the set of things the table represents.

Denormalization, finally, copies into the same table attributes that are often used together, for example the customer's region in the orders table, so reads avoid repeated joins. The price is that every correction to the source must be propagated to every copy. The choice is between simpler reads and more coordinated updates.

8.6 Place Each Quality Rule at the Correct Layer

We have seen many rules about data. Databricks offers several mechanisms to apply them, each suited to one kind of rule. The table orders them from the most structural to the most aggregated.

Mechanism Appropriate rule Important boundary
Parsing/schema checks Expected fields and representable values Establishes structural compatibility.
Enforced table constraints Supported write invariants such as NOT NULL or CHECK Rejects writes violating the enforced rule; key constraints can be informational.
Pipeline expectations Row expressions with a chosen violation action Classifies individual records and records the configured outcome.
Aggregate/reconciliation tests Key cardinality, totals, referential completeness, source/target balance Evaluates a defined population and time window.

Two examples clarify the boundaries. A NOT NULL constraint rejects missing values, but a CHECK (amount >= 0) constraint on a NULL amount gives an unknown result and lets the row through: presence and range are two distinct rules, and if both are needed both must be declared. Moreover, when we add a constraint to an existing table, Databricks also checks the rows already present, and the operation fails if any of them violates it.

Uniqueness is the trickiest rule, because it depends on the population it refers to: events, current entities, historical versions, or a single batch. A micro-batch can contain no duplicates internally and still repeat an order that arrived yesterday. To guarantee uniqueness across batches, the check must be able to consult the target table or a state that remembers the keys already seen.

8.7 Expectations and Quarantine

In Lakeflow declarative pipelines, row rules are written as expectations: a condition every row must respect, with an action that decides what happens to rows that violate it. There are three actions.

Action Data outcome Appropriate reason
Warn/default Violating rows continue; quality metrics can be recorded Measure a defect while a downstream consumer tolerates it.
Drop Violating rows are excluded from that output The consumer explicitly accepts omission and omissions are observable.
Fail The affected update/flow fails under the service's semantics Publishing this output with a violation is unacceptable.

With the fail action, what fails is the update of the affected table, within the service's transaction boundary; other independent flows of the same pipeline may already have completed their work. With the drop action invalid rows disappear from the output, and knowing which ones and why is possible only from the metrics. Quarantine goes one step further: in place of discarding the rejected rows, it writes them to a separate table together with the reason for rejection, so we can review them and, once corrected, reprocess them.

Let's look at an expectation with the fail action:

CREATE OR REFRESH STREAMING TABLE valid_order_events (
  CONSTRAINT required_order_id
    EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(sales_dev.bronze.order_events);

The definition creates a streaming table that reads bronze events and requires every row to have an order_id. If one arrives without it, the table's update fails. It works inside a pipeline, with namespace and permissions configured. An expectation checks one row at a time, so rules such as order uniqueness or sequence consistency, which require looking at several rows together, are verified with other tools, such as the aggregate tests of the previous table.

Let's see how a quarantine is built. We start from the raw input, kept as it is, and classify it in an intermediate dataset that evaluates every rule for every row. Rows passing all rules enter the validated table. The others enter the quarantine table, together with the event identifier, the list of violated rules, the source reference, and the run metadata. NULLs need attention: if a rule returns an unknown result, the row must still end up on one side or the other, so the classification handles that case explicitly too.

If the classification is done well, every row ends up in exactly one place and none is lost. We can verify this with a simple equality, computed over the same population: input rows = accepted rows + quarantined rows + explicitly accounted exclusions. If the numbers do not add up, some row was lost along the way. And when a quarantined row is corrected and reprocessed, idempotent event handling guarantees it enters the validated table only once.

8.8 Load the Target According to Its Contract

The last step is writing data to the target table, and the way we write determines what happens if the same load runs twice. Let's look at the four main strategies.

The simplest is append, which adds records to the existing content. If a job fails after writing and is rerun, a repeated INSERT INTO adds the same rows again. To avoid this, before appending we compare events with those already in the target, or rely on a mechanism that recognizes writes already done. In-batch deduplication, seen in section 8.3, solves a different problem: repetitions within the same batch.

MERGE compares incoming rows with those of the target by key and, for each one, chooses an action: update if the key exists, insert if it is missing, possibly delete. For it to work, every key must appear only once in the source: if two incoming rows match the same target row, Databricks cannot tell which to apply and the MERGE fails. Branches are evaluated in the order they are written, and the first whose condition is true determines the action. Adding a sequence condition to the update branch, such as "update only if the incoming sequence is greater than the current one", makes the target ignore an old update arriving late.

Overwrite replaces a defined part of the table with the incoming data. A frequent confusion deserves attention: .partitionBy(...) decides how files are organized on disk and leaves open which data to replace. The scope of the replacement is defined with a predicate or a supported key mechanism, and the incoming data must represent the entire intended content for that scope.

The most controlled form of overwrite is REPLACE WHERE, which replaces exactly the rows satisfying a predicate, for example those of a given day. Rerunning that day's load always produces the same result, which makes it idempotent by construction. Other operations, such as REPLACE USING, define the replacement through their own matching rules. Which of these operations are available depends on the runtime and the compute.

Let's test the chapter's rules with a small batch built on purpose. A repeated event tests deduplication. An update with a sequence older than the one already present tests the sequence condition in the MERGE. A badly written amount tests parsing and the invalid_amount column. A missing identifier tests the presence check. A nonexistent customer tests referential integrity. And an order with two lines tests that revenue is computed at the right grain.

9. Pipelines, Orchestration, and Recovery

So far we have seen the individual steps of the orders pipeline: ingestion, transformation, quality checks. Now we must make them work together, every night, reliably, and know what to do when something breaks. We can see the pipeline as two overlapping graphs. The data graph connects each table to the tables it is computed from: revenue depends on silver orders, which depend on bronze events. The operational graph connects activities: extracting data, validating it, exporting it, notifying whoever is waiting for it. Lakeflow declarative pipelines manage the first graph; Lakeflow Jobs coordinates the second, which can also include declarative pipelines as one of its steps.

9.1 Choose the Appropriate Control Model

There are two ways to write a pipeline's logic. In the first, procedural, we write a notebook that says step by step what to do: read this table, filter, if the count is zero skip this step, write that other table, call an API. We have complete control, and with it the responsibility for operation order, for tracking how far we have got, and for recovery after an error. This model fits heterogeneous operations and existing procedural code well.

In the second, declarative, we use Lakeflow Spark Declarative Pipelines and describe only which tables we want and what they are computed from. The service derives the dependencies, decides the execution order, and handles incremental updates and recovery. The two table types we saw in chapter 2 have precise roles here: streaming tables process new data incrementally, while materialized views keep a query result up to date. The difference matters when corrections and deletions arrive, which a streaming table fed by appends cannot absorb on its own.

Let's see how they combine in the orders pipeline. A streaming table captures events as they arrive. An AUTO CDC flow applies them to maintain the current state of each order, handling updates and cancellations. A materialized view computes revenue from that state. If we treated all three stages as simple appends, a cancelled order would stay in revenue unless we wrote correction logic by hand.

A note on names: Apache Spark Declarative Pipelines is the open-source API, while the Databricks service adds features such as expectations and AUTO CDC. Which definitions an environment can run therefore depends on the runtime and the service.

9.2 Definition Evaluation and Side Effects

In a declarative pipeline, every definition describes a dataset and returns it. The engine can run a definition's code several times, for example while building and validating the graph, before processing any data. If a definition contained an external effect, such as sending an email or writing to another table, that effect would repeat every time the engine evaluated it. Notifications and external writes therefore belong in operational job tasks, which run once per run.

Here is how revenue is defined as a materialized view, starting from the current-state table:

CREATE OR REFRESH MATERIALIZED VIEW daily_revenue
AS SELECT
  CAST(order_timestamp AS DATE) AS order_date,
  SUM(order_total) AS revenue
FROM sales_prod.silver.orders
GROUP BY CAST(order_timestamp AS DATE);

The query is simple because it relies on work done upstream: it assumes that the rows of orders are already those eligible for revenue, that amounts are in a single currency, and that timestamps have a defined timezone. If cancelled orders must be excluded or currencies converted, the contract decides whether to do it in the source table's transformation or in this query.

A declarative pipeline also has a configuration, which binds the definitions to the target catalog and schema, the identity it runs under, the compute, and the run mode. Before running it we can launch a dry run, which checks the syntax and the graph structure without processing data. The dry run checks only the form, though: whether the identity can read the sources, whether the results are correct, and how long it takes are learned only by running the pipeline on the data.

9.3 Design a Job as Explicit Dependencies

Now the operational graph. The nightly orders job runs five tasks: it extracts the data, updates the order state, validates quality, refreshes revenue, and finally publishes completion, for example by writing a record that reports check. Validation acts as a gate: if it finds contract violations it fails, and the failure blocks the following tasks. Publication starts only if transformation and validation succeeded.

Dependencies between tasks follow those between data. A task using another's output must wait for it, so the two run in series. Two tasks reading independent sources, such as orders and customers, can instead proceed in parallel. The publication task, which gathers both, checks that they have finished and that their data is consistent, for example that it belongs to the same batch and has the expected counts.

Lakeflow Jobs offers two kinds of condition for deciding what to run. A task's Run if condition looks at the state of the tasks it depends on: with All succeeded the task starts only if all of them succeeded, with All done it starts anyway once they have finished, which is useful for a cleanup task, and with At least one failed it starts only if something went wrong, to handle the error. The If/else task instead looks at a value, such as the number of invalid rows produced by an earlier task, and picks one branch or the other. The former decide based on how tasks went, the latter based on what they produced.

A task can also end up not running for different reasons: skipped by a condition, disabled, stopped by a timeout, or failed. Each of these states propagates differently to downstream tasks. Disabling an update task, for example, means that the following tasks find the previous run's data, or no data, and their conditions must account for it.

The For each task, finally, runs the same task for every element of a list, for example once per region, possibly in parallel. Parallel iterations share compute capacity, though, and if they write to the same partition or use the same checkpoint they get in each other's way. Parallelism pays off only when each iteration has its own state and destination.

9.4 Parameters and Logical Work Identity

A job run must know which data to work on, and parameters serve exactly this: the catalog, the source, the business interval to process, the input version, a request identifier. Think of the job processing September 14 orders. If a failure makes it start a day late, it must still process September 14, even though the clock says 16. For this reason the data interval is an explicit parameter and stays separate from the moment the job runs.

Tasks in a job can also pass information to each other. Task values carry small coordination values, such as a count or a table name. The actual data travels through governed tables, which later tasks read by name. When a parameter ends up in a path or an SQL name, it must be validated, because a malicious value could turn into executable code.

Parameters also enable backfill, processing a past interval, for example to recompute a month after a bug fix. A backfill runs the usual transformation over an explicit historical interval. What happens to data already published for that interval, whether it is replaced, reconciled, or extended, depends on the publication policy.

9.5 Choose Triggers According to Availability

A job can start for different reasons, and the choice of trigger depends on when the data is available. The most common trigger is a time schedule. Advanced schedules use Quartz cron syntax, which also has a seconds field, and a configured timezone. With UTC the interval between two runs is always the same; with a local timezone the run follows the business clock, daylight saving included, so the 7:00 report always comes out at 7:00 local time.

If data arrives at irregular times, it makes more sense to start the job when it arrives. The file arrival trigger starts the job when new files appear in a monitored location. It works best when every delivery has a new name; if a file is overwritten under the same name, behavior depends on the trigger's specific rules. When a delivery consists of several files, the arrival of the first one does not mean the batch is complete: the source can send a manifest file last, listing the expected files, and the job checks completeness against it.

The table update trigger instead starts the job when monitored tables change. If the job depends on several tables, a change to one of them does not guarantee the others are ready; versions or batch identifiers let us verify that all of them belong to the same business batch before publishing.

Then there is continuous scheduling, which starts a new run as soon as the previous one ends. As we saw in chapter 6, this is different from an always-on Spark query and from a declarative pipeline's continuous mode. Supported streaming triggers also vary with the compute: the course material distinguishes availableNow, which processes what is available and stops, on serverless, from interval triggers on other supported compute.

Finally, pausing a trigger stops only future starts. Runs already in progress continue until we cancel them, and an external system with the necessary permissions can still start the job through the API. A maintenance window must therefore consider all three: the trigger, the active runs, and whoever can start the job from outside.

9.6 Concurrency and Queues Need an Explicit Policy

What happens if the trigger fires while the previous run is still in progress? With a maximum concurrency of one, runs of the same job never overlap. This rule concerns only that job: idempotency remains the responsibility of the processing logic, and another job can still write to the same table. The interaction between different writers on the same target is left to Delta transactions and the coordination seen in chapter 7.

If queueing is enabled, excess runs wait their turn in place of being discarded, within the service's limits. A queue absorbs only temporary peaks, though. If triggers keep arriving faster than the job can complete them, the queue grows longer and data arrives later and later. To notice it, beyond task duration we measure the age of waiting runs and the data freshness for consumers.

Deciding what to do with waiting runs is a business choice. If the job archives events, every interval must be processed and no run can be skipped. If the job updates a current state from a snapshot, ten queued requests can be merged into one that reads the most recent snapshot. Concurrency and queue are configured to implement this policy.

9.7 Retry, Repair, and Replay Are Different Operations

When a run fails we have three ways to try again, with different effects. A retry automatically repeats the failed attempt, according to the policy configured on the task. A repair reruns, within an existing run, the failed tasks and those depending on them, leaving successful ones untouched. A replay reprocesses an interval or a whole dataset from scratch. In all three cases the new attempt can find effects left by operations that had already succeeded, such as rows already written or notifications already sent.

This is why idempotency matters: repeating the same request several times must have the same effect as running it once. Event keys, transactional sinks, replacements of a bounded scope such as REPLACE WHERE, and tracking of requests already executed all provide it. The central element is a stable request key: attempts with the same key are repetitions of the same request, while a new key indicates a new request.

Only some errors are solved by a retry. A temporary network or capacity problem can clear on its own between attempts, and then a retry works. A missing grant, an invalid schema, or a deterministic data violation recur identically on every attempt, and retries only consume time and compute until someone fixes the configuration or the data. Classifying the error tells us which of the two paths to take.

Times must be put together too. A timeout limits the duration of a single attempt of a task; the number of retries and the interval between them extend the total time a task can consume. A duration warning threshold sends a notification without stopping anything, while timeout and cancellation interrupt the run. The calculation must also include the automatic retries the service applies to continuous or serverless workloads.

9.8 Report Failure Through the Execution Contract

The job decides whether a task succeeded or failed according to precise rules. A notebook fails if it raises an unhandled exception or uses a documented failure mechanism. A frequent mistake follows: if the code catches an exception with a try block and then ends normally, the task appears successful, even though the required output was never written, and downstream tasks start on missing data.

The same misunderstanding arises with dbutils.notebook.exit("FAILED: ..."). This statement ends the notebook and returns the string as its result, while the task appears successful. The caller can read the string and interpret it, if an explicit protocol provides for it. Making the task fail takes raising an exception. The returned value and the run status travel on two separate channels.

"Completed" also means different things depending on the operation. A notebook ends; a streaming query can stay active indefinitely; a Delta transaction completes its commit independently of the rest of the task. Publication must wait for the outcome that really matters, for example the commit of the revenue table.

When something fails, the notification must make action possible: who is responsible, which job, run, and task, which data interval, where to find the diagnostics. An intermediate retry and the final failure, after all attempts are exhausted, are different events. Muting intermediate notices avoids a flood of messages and keeps the final one. Notifications, finally, stay free of credentials and sensitive data rows.

9.9 Recovery Exercise

Let's look at a few failures in the orders pipeline. If the error happens after the silver table commit but before publication, a repair reruns only the publication task, and the data already written stays valid. If instead we rerun the whole batch, in an idempotent pipeline revenue stays identical and streaming resumes from the same checkpoint, while the publication state is reconciled.

The kind of failure decides the response. Invalid input needs a correction of the data or the rules, and only then a new run. A temporary source outage is solved by a retry. The pipeline lab and Jobs lab explore these behaviors. Trigger, task, and concurrency availability depend on workspace and compute capabilities.

10. Testing and Deployment

A pipeline that works in a developer's notebook must then work the same way in production, today and six months from now. To achieve this we must be able to rebuild exactly the environment that produces the data: the code, the libraries with their versions, the configuration, the target objects, and the identities under which everything runs. A reproducible release records all these elements together. In this chapter we look at two tools that make this possible. Tests verify that code behaves as expected on known inputs. Declarative Automation Bundles describe, in versioned files, the code and resources to deploy, so every environment can be recreated from scratch.

10.1 Separate Transformation Logic From Interactive State

The first step toward testable code is moving logic out of notebooks. If the orders transformation lives in a function inside a Python module, we can call it from a test with prepared data and check the result. The notebook stays, but it becomes a coordinator: it reads parameters, calls functions, and writes results. There is a second advantage. In an interactive session it is easy to depend on something that exists only in memory, such as a variable defined in a cell run an hour earlier. A job starts from scratch, so all the state it needs must be created explicitly by the code, and code organized in modules makes it evident what is needed.

Version control with Git ties code, contracts, and configuration to a change someone can review. In Databricks, Git repositories are cloned into Git folders in the workspace, and there is a detail worth knowing here: if someone switches branch in a shared Git folder, the code changes for everyone using it. Each developer therefore works in their own copy, and production uses a recorded revision that identifies exactly what was deployed.

A Git merge combines text, but code also carries expectations about behavior. Suppose one developer updates the transformation to use a new column while another, in parallel, changes the parameter that feeds it. The two branches merge without conflicts, the code is syntactically valid, and the output is wrong. Only a test exercising the combination of code, schema, and parameters notices.

Test data deserves the same care. Synthetic fixtures, small invented datasets for tests, can be read and reviewed in the repository without exposing real customer data. Production values and credentials stay out of the code history, read from governed locations. Notebook outputs need attention too: if they are saved in the commit, they can carry with them the data the code displayed.

10.2 Match Each Test to a Claim

Every test proves a precise claim, and different kinds of test prove different things. The table orders them from the smallest to the broadest.

Test Evidence Execution boundary
Unit test A function maps inputs to expected rows and types A transformation and its controlled dependencies
Integration test Real components interact under the intended runtime and identity The selected service and storage connections
End-to-end test The workflow produces and publishes expected output A complete configured workflow and input scenario
User acceptance test Stakeholders accept semantics, totals, and freshness The business interpretation of published results

A unit test must run on the same engine production will use, because the engine decides how NULLs, types, ordering, and distributed processing behave. A Spark function is tested with Spark; a test written with pandas verifies pandas behavior, which can differ. Small, deterministic fixtures help find the error immediately, and controlled external dependencies make the result repeatable.

How results are compared matters too. Checking schema and row count verifies the shape of the result; verifying its content requires comparing keys and values. In Spark the row order of a DataFrame is generally undetermined, so comparison happens by key or after an explicit sort. For numbers, the allowed tolerance is part of the contract: a statistical calculation can accept small differences, while a financial total is compared exactly, respecting the agreed decimals.

Edge cases each deserve a test, because each one tests a different boundary: duplicates, NULLs, malformed input, late changes, empty batches, forbidden access, a retry after a commit already done. One case is especially instructive: give the pipeline deliberately invalid input and verify that it is rejected. Only this way do we know that the quality check really blocks the violation.

10.3 Isolate Test Data and Enforce Failure

Tests that write data must do so in a place separate from production. A catalog or schema dedicated to tests holds the synthetic fixtures and the outputs to delete at the end. The test configuration resolves destinations in that catalog and rejects any production destination. The archived course showed a test writing to a table called production: here we replace it with an explicit test boundary.

Cleanup also needs care. Every test run keeps an explicit list of the objects it created and, at the end, deletes only those, checking their identifier and owner. Deleting everything with a certain name prefix risks hitting unrelated objects that happen to have a similar name.

In the continuous integration (CI) pipeline, tests act as gates: if a test fails, the next step, such as deployment, does not start. The gate triggers only if the test really fails, with a failed assertion or a nonzero exit code. A test that prints "ERROR" and then ends normally signals success. Keeping test results and run identifiers ties every release to the checks it passed.

10.4 Understand Bundle Configuration

Let's turn to deployment. Declarative Automation Bundles, previously called Databricks Asset Bundles, describe in YAML files the code and resources to deploy. The main file is databricks.yml, which declares the bundle and can include other files. Inside it we find three main sections. Variables supply configuration values that change from one environment to another. Targets define the environments, such as development and production, with their configuration changes. Resources describe the jobs, pipelines, and other objects to create.

Let's look at an example with two serverless notebook tasks. Running it requires the referenced source files, the notebook environments, workspace authentication, permissions, and the target catalogs.

bundle:
  name: orders_pipeline

variables:
  target_catalog:
    default: sales_dev

resources:
  jobs:
    orders_job:
      name: orders_pipeline
      max_concurrent_runs: 1
      tasks:
        - task_key: transform
          notebook_task:
            notebook_path: ./src/transform.py
            base_parameters:
              target_catalog: ${var.target_catalog}
        - task_key: validate
          depends_on:
            - task_key: transform
          notebook_task:
            notebook_path: ./src/validate.py
            base_parameters:
              target_catalog: ${var.target_catalog}

targets:
  dev:
    default: true
    mode: development
  prod:
    mode: production
    variables:
      target_catalog: sales_prod

Let's read the example. The orders_job job has two tasks, transform and validate, and depends_on states that the second starts only after the first. max_concurrent_runs: 1 prevents two runs from overlapping. Both tasks receive the target_catalog parameter, which is sales_dev by default and sales_prod in the production target: the same code thus writes to the right catalog for each environment. The file describes what to deploy, while data access permissions remain those of the run identity and its grants, and workspace address, authentication, and resource permissions complete the deployment context.

The two targets use different modes. Development mode applies a few settings meant for individual work: it adds a prefix with the developer's name to resource names and pauses schedules, so two developers can deploy the same bundle without colliding and no test job starts on its own. Production mode instead adds checks suited to production. In both cases the real workspace, identity, permissions, and schedules come from the effective configuration, and the proof that the release works comes from the tests.

It is worth telling bundle variables apart from job parameters. Variables act at deployment time and decide how the job is configured, for example which catalog it writes to. Job parameters act at run time and decide which work to do, for example which day to process. The same deployed job can therefore process different days by receiving different parameters.

10.5 Validate, Plan, Deploy, Run, and Check Data

With a recent version of the Databricks CLI and authentication configured, a bundle's lifecycle goes through distinct stages:

databricks bundle validate -t dev
databricks bundle plan -t dev
databricks bundle deploy -t dev
databricks bundle summary -t dev
databricks bundle run -t dev orders_job

Each command has a precise role. validate checks that the configuration respects the bundle schema and is consistent with the CLI context. plan shows which resources will be created, changed, or deleted, and runs the configured builds. deploy uploads the artifacts to the workspace and aligns the managed resources with the configuration. summary reports the identity used and the deployed resources. run starts the job. After the run one last step remains, which no command does for us: verifying with data assertions that the output respects the contract.

Validation has a limit worth knowing: it checks the configuration against the schema of the CLI version in use. A warning about an unknown property can mean a typo or a property that version does not know yet, and it is a signal worth investigating. Pinning the CLI version in the release makes this behavior stable. Runtime behavior is then verified by execution and data tests.

A central concept for understanding bundles is deployment state. The bundle is deployed to a workspace folder, the root path, which by default contains the name of whoever deploys, the bundle name, and the target. In that folder the bundle keeps a state that links every resource in the configuration to the identifier of the real object in the workspace, for example the job_id. When we redeploy, the bundle uses this state to update existing objects. If the identity of whoever deploys changes, however, the default root path changes too: the new deployment finds no previous state and creates a second job, with a second schedule, in place of updating the first.

To bring an existing object under bundle management, for example a job created by hand, we use binding, which associates that object's identifier with the bundle resource. From then on later deployments update that job.

10.6 CI/CD, Concurrency, and Recovery

In a CI/CD process, promotion carries an approved revision first into the test environment and then into production. Deployment uses an automation identity, such as a service principal, which supplies stable credentials independent of people. Separating the identity that deploys from the one that processes data has an advantage: the first manages jobs and pipelines, the second reads and writes tables, and their permissions can evolve independently.

The plan also shows deletions, which have direct consequences. If we remove a resource from the bundle, the next deployment can delete the corresponding job or pipeline. Persistent data has its own lifecycle, though: tables created by a pipeline, for example, are tied to that pipeline by specific ownership rules. A release must therefore be thought of in terms of both definitions and data retention.

Two simultaneous deployments of the same bundle could corrupt the state, and the bundle uses a lock to prevent it. Forcing an active lock lets two deployments change the state together, with the risks that follow; forcing a lock left behind by a deployment that has already ended, for example after a crash, is a legitimate recovery operation. Running job executions are another matter: deployment and execution have separate lifecycles, and a rule is needed to decide whether an active run continues with the old definition or is cancelled.

That leaves rollback. Restoring the previous version of the code is simple; restoring data is another matter. We can bring a table back to a compatible version with time travel, reprocess the source, or apply compensating corrections. And before restarting the old code we must verify that it is compatible with the current schema and with the checkpoints, which the new code may have updated in the meantime.

10.7 Resource APIs and Bundle Deployment State

The published October 19 DP-750 objectives mention bundle deployment through REST. The available documentation, however, describes two distinct mechanisms: the bundle lifecycle through the CLI and workspace, and the Jobs APIs for individual jobs and runs. A bundle deployment manages artifacts, planning, state, and dependencies all together, while the APIs operate on one job or run at a time. A REST procedure for deploying a whole bundle remains, for this course, an open documentation point.

At the level of individual resources, the Jobs API documents these operations:

Operation Endpoint State to retain/check
Create a job POST /api/2.2/jobs/create Returned job_id and deployed settings
Read a job GET /api/2.2/jobs/get Effective settings, with pagination when applicable
Partially update a job POST /api/2.2/jobs/update Documented replacement/merge semantics of submitted settings
Replace job settings POST /api/2.2/jobs/reset Complete intended settings, not an incomplete partial payload
Request a run POST /api/2.2/jobs/run-now Returned run_id, subsequent terminal outcome, and data checks

Two operations look alike and must be told apart: update changes only the settings it receives and leaves the others as they are, while reset replaces the whole configuration with the one sent, so an incomplete payload erases the missing settings. Automation using these APIs authenticates to the workspace, sends valid requests, and keeps the returned identifiers. run-now returns a run_id immediately, but the outcome arrives only when the run reaches a terminal state, which must be queried later. If the start request risks being repeated, for example because of a network timeout, a stable idempotency token guarantees that only one run is created. This token protects the start of the run; the writes the job performs on data need their own idempotency mechanisms, seen in chapter 9.

Combining bundles and APIs takes some discipline. The bundle state describes the desired resources; if someone changes a job directly through the API, the job drifts from the configuration, and the next deployment brings the job back to what the bundle says, undoing the change. An orderly workflow leaves definition management to the bundle, through the CLI, and uses the APIs to start and inspect runs.

11. Performance and Observability

When a pipeline is slow or expensive, the temptation is to add resources. Often, though, time is lost at one precise point, and the extra resources end up elsewhere. In this chapter we see how to find that point. The basic idea is simple: optimizing means changing the physical work the system performs while leaving the logical result identical. Doing it takes three kinds of information: end-to-end timings, to understand where delay accumulates; execution metrics, to understand which resource limits the work; and result comparison, to be sure that the optimized version produces exactly the same data.

11.1 Separate Waiting, Startup, Execution, and Freshness

Let's start from the most common question: "why does the report data arrive late?". The total delay is the sum of many phases: the time the source takes to make data available, the wait for the trigger, time in the queue, compute startup, processing, and publication. If a run spends an hour in the queue and Spark then processes in a few seconds, optimizing Spark changes almost nothing. Freshness also depends on the source: a successful run over data the source has not updated still publishes old information.

To compare two runs and understand whether an intervention really improved anything, every run must leave a complete record: the interval and version of the input data, the run identifier, the timings of each phase, the freshness obtained, how many rows were processed and how many rejected, and the code and configuration revision. With this information we can tell a real improvement from a run that was faster only because it had less data or covered a different period.

The information lives in different places. Job and task details show orchestration: when each task started and how long it lasted. The Spark UI shows distributed execution on the compute that exposes it. Query profiles and history cover SQL and supported serverless analysis. Declarative pipeline views show events and quality metrics. Which infrastructure metrics are available depends on the compute model: on serverless, for example, the underlying machines stay hidden.

11.2 Diagnose From the Executed Plan

Once we know that time is lost in processing, we move to the executed plan. The plan connects a slow task to the operations it consists of: reads, data exchanges between executors (exchange), joins, and stages. The associated metrics, such as the number of tasks, the distribution of their durations, spill, and driver and executor activity, show where resources are spent. EXPLAIN describes the plan before execution; the metrics tell what really happened.

The table links the most frequent symptoms to their likely causes and to the check that tells them apart.

Observation Candidate cause Discriminating check Possible intervention
Few tasks run while capacity is idle Insufficient useful parallelism or serial work Task count and driver activity Change the data/operation parallelism if semantics permit.
One or a few tasks run much longer Skew, unusually large records, or a slow executor Per-task input and duration distribution Address key distribution or the identified node issue.
High spill in expensive stages Partitions or state too large for available execution memory Per-task spill, memory, and partition sizes Reduce per-task data/state or change memory/partition sizing.
Large shuffle volumes Wide joins, aggregations, or repartitioning Exchange nodes and shuffle read/write Reduce data before the exchange or use a suitable join strategy.
Driver failure with mostly idle executors Driver-side collection or coordination pressure Driver logs and code using collect/toPandas Keep computation distributed or bound returned data.
High elapsed time with little computation Remote source, network, startup, or queue delay Timeline and dependency metrics Fix the relevant boundary; more executors leave the time unchanged.

The middle column is the most important, because identical symptoms can have different causes. Suppose one task takes ten times longer than the others. If it received ten times more data, the cause is skew, an unbalanced distribution. If it received the same amount of data as the others but ran on a troubled executor, the cause is the node. Duration alone leaves both cases open; read together with the distribution of work and the behavior of resources, it separates them.

11.3 Shuffle and Skew

Let's look more closely at the most common causes, starting with the shuffle. When Spark runs a join or an aggregation by key, rows with the same key must be on the same executor. The shuffle moves them: each executor serializes the data, writes it to disk, and sends it over the network to the others, which receive and deserialize it. It is one of Spark's most expensive operations. The most effective way to reduce its cost is to move less data: filter rows and select only the needed columns before the exchange, when the semantics allow it.

Skew arises when one key is far more frequent than the others. Suppose a large business customer accounts for 40% of orders, or that many rows have a NULL customer_id: after the shuffle, all those rows end up in a single partition, processed by a single task. The job waits for that task while the other executors sit idle. Doubling the workers leaves the time almost unchanged, because the dominant task is still one and keeps processing the same amount of data.

Spark has automatic tools for some of these problems. Adaptive Query Execution (AQE) observes data during execution and adapts the plan: it can merge partitions that are too small, split unbalanced partitions in joins, and change the join strategy. One of these strategies is the broadcast join: when one side of the join is small, such as a countries table, Spark sends a complete copy of it to every executor, and the large table no longer needs to be redistributed. The price is memory: every executor must hold the whole copy. The final plan shows which strategy Spark actually chose.

When the automatic tools are not enough, we can turn to salting. The idea is to split the frequent key artificially into several subkeys, by adding a random number, so its work spreads over several tasks. In a join the other side must be expanded accordingly, replicating each row for every subkey, otherwise matches are lost. In an aggregation, partial results are computed per subkey first and then recombined. Done correctly, salting leaves matches and totals identical and changes only the physical distribution of work.

11.4 Memory Spill and Partition Sizing

Spill happens when a task's intermediate data does not fit in available memory and Spark writes it temporarily to disk. It is a safety net: it lets work finish even with little memory, at the price of many extra disk reads and writes. The metrics show how much data went to disk and how long it took, and from these numbers we understand whether the problem is serious.

The number of shuffle partitions directly affects spill. With more partitions each task receives less data and needs less memory; but partitions that are too small multiply the cost of scheduling and coordinating thousands of tiny tasks. With fewer partitions overhead drops and the memory each task needs rises. The right size balances the two costs on real data, and AQE helps by adapting it during execution.

Before adding memory it pays to ask why so much is needed. Very wide rows, joins that multiply rows, streaming state that grows without limit, caching, and skew all increase memory demand, but they call for different interventions. If a wrong join multiplies rows, the join must be fixed, and extra memory would only compute a wrong result faster. Adding memory is the right choice when the data to process is legitimately large.

Driver and executors have separate memory. Operations such as collect() or toPandas() bring the entire result to the driver, which becomes the limit: it can run out of memory while the executors are nearly empty. Keeping computation distributed, and bringing to the driver only small or bounded results, avoids the problem.

11.5 Caching Has a Reuse and Capacity Contract

The word cache names three different mechanisms in Databricks. The Spark cache, enabled with cache() or persist(), keeps in memory or on disk an intermediate result computed from a DataFrame. The Databricks disk cache automatically keeps copies of files read from storage on the machines' local disks. The Databricks SQL result cache keeps the result of identical repeated queries. Each has its own scope, its own lifetime, and its own rules for invalidating itself when data changes.

A cache pays off only if the computation it avoids exceeds the cost of creating, keeping, and maintaining it. Caching a DataFrame used only once adds work with no benefit. Moreover, the cache occupies memory that other operations need, and releasing it with unpersist() gives it back. If the compute is replaced, the cache disappears and must be rebuilt.

Measuring a cache's effect also needs care. A "warm" test, with the cache already full, measures only the benefit of reuse; a "cold" test includes the first read and building the cache. A representative measurement reproduces the real mix of new and repeated data, and accounts for data changes that can invalidate the cache.

11.6 Table Maintenance and Query Optimization

In chapter 7 we saw how table layout lets queries skip useless files. This works only when query filters, file statistics, and value grouping are aligned. Moreover, declaring clustering keys establishes only a strategy: the real layout is the one produced by the reorganizations already completed. To know whether the layout helps a query, we measure how many bytes and files it reads.

Two maintenance commands are often confused. OPTIMIZE reorganizes files: it compacts small ones and applies clustering, changing the layout that reads will find. VACUUM deletes files the table no longer uses, according to retention: it frees space and reduces the history available for time travel, within the recovery window seen in chapter 5.

Statistics matter too. The optimizer uses them to estimate how many rows each operation will produce and to choose accordingly, for example whether to use a broadcast join. Missing or stale statistics lead to wrong estimates and therefore to inefficient plans, while up-to-date file statistics also enable data skipping. On managed tables, predictive optimization can run this maintenance automatically, recording the work done and its cost.

Knowing whether an intervention worked takes a controlled comparison. We hold fixed the input data, the contract, and every setting not involved, and change only one thing, for example the join strategy. This way a change in shuffle or duration can be attributed to that intervention. And we verify that the results are identical, to be sure the two runs performed the same logical work.

11.7 From Consumption to Cost

Performance translates into cost. The system table system.billing.usage contains one record for every recorded consumption, with the quantity consumed, the SKU, the type of billed product, and the unit of measure. When we aggregate these records, SKU and unit are always kept, because summing quantities of different SKUs or units produces a meaningless number:

SELECT
  usage_date,
  sku_name,
  usage_unit,
  SUM(usage_quantity) AS quantity
FROM system.billing.usage
WHERE usage_date >= CURRENT_DATE() - INTERVAL 7 DAYS
GROUP BY usage_date, sku_name, usage_unit;

The query sums the last seven days' consumption by day, SKU, and unit. These numbers are quantities. To obtain the cost, each quantity is multiplied by the price valid in that period, contractual discounts are applied, and, for classic compute, the Azure charges for the virtual machines are added, since they do not appear in this table.

To attribute consumption to workloads, the records contain metadata such as the job identifier, the workspace, the identity, and custom tags. A run can generate several records, though, and billing can contain later corrections. When these records are joined with the history of cluster configurations, the join must use the right keys and time validity, so that each quantity is associated exactly once with the configuration in force at that moment.

The number that really matters is the cost per validated batch, which combines price, duration, retries, and any idle resources such as pools. A compute with a low per-minute price can produce a more expensive batch if it takes much longer. Budgets and their notifications report spending. Acting on resources is the job of other controls, such as compute policies that limit configurations and automatic shutdown.

11.8 Azure Monitor and Log Analytics

Besides system tables, Databricks logs can be sent to Azure monitoring tools. The workspace resource's diagnostic settings send selected log categories, such as those for jobs or clusters, to Log Analytics, a storage account, or Event Hubs. The path depends on five choices: the resource, the categories, the destination, the permissions, and the retention. Account, workspace, execution engine, and application logs are each collected differently.

Writing alerts on these logs requires knowing their schema, which depends on the diagnostic configuration. The outcome of an operation is read from the structured status and response fields. A typical mistake is searching for the word "error" in the text: a successful response can contain the field error_message: null, and a text-based alert would mistake it for an error. The correct alert evaluates the value of the documented status field.

Logs also distinguish different kinds of failure. A failed job creation is a configuration problem; a failed transformation is a problem of execution on data. The recorded action, the identifiers, and the final state let us understand what happened and who can fix it.

A scheduled alert in Azure Monitor runs a query over a time window, compares the result with a threshold, and, if it is exceeded, starts an action, at the configured frequency. The window must account for the delay with which logs reach Log Analytics. Then there is a kind of problem that error logs miss: silence. A job that never starts is simply absent from the logs. Noticing it requires alerts on the absence of expected events, such as a completion that does not arrive, or on stalled data freshness.

Logs reach Log Analytics asynchronously, with some delay. To measure it, and to confirm that the collection path works, we can use a known event whose identifiers and time we know. This reference lets us distinguish genuine inactivity from telemetry that is missing or late.

11.9 Diagnose Before Restarting

Faced with a failed job, the common reflex is to restart it. First, though, it pays to save the information about the failure: the run logs, the queries, the stages, and the error messages. A restart recreates the environment and clears part of the state useful for diagnosis. And many errors survive the restart: a wrong conversion, a missing grant, or a wrong join recur identically until the data, the permissions, or the code change.

After a fix, verification must be representative: use the data or the scale that caused the failure. A focused case proves that the identified cause was the right one; a run over the whole interval proves that recovery is complete and the data consistent. An empty batch that succeeds proves only that the job can handle an empty batch.

12.2 Power BI: Choose Freshness and Identity Deliberately

Power BI can connect to Databricks in two ways, with very different consequences. In Import mode Power BI copies data into its own semantic model. During refresh, Unity Catalog authorizes the extraction under the connection identity; afterwards, report queries work on the copy, protected by Power BI controls, until the next refresh. The report is fast and leaves Databricks free on every click, but the copy has its own lifecycle: it is as fresh as the last refresh, and its security depends on Power BI.

In DirectQuery mode Power BI instead sends every query to Databricks, usually to a SQL warehouse, and shows the result. Data is always current, but every interaction with the report depends on the network, warehouse availability, the number of simultaneous users, and latency. Caches, in Power BI and in Databricks, also affect how fresh the data appears.

Whether Unity Catalog grants are evaluated per user depends on the connection identity. With a service principal or a fixed token, all queries reach Databricks under a single identity, and every report user sees the same data. With supported single sign-on (SSO), each user's identity is propagated all the way to Databricks, which evaluates their personal grants, including row filters and column masks. The published report's configuration and the token flow determine which of the two cases applies.

The connection is configured with a few parameters, each with a precise meaning: the hostname and HTTP path choose the compute, catalog and schema choose the namespace, authentication chooses the principal. A detail that often confuses people is that Power BI Desktop, on the developer's laptop, and the Power BI service, where the report is published, can use different credentials and network paths. A report that works on the laptop can therefore fail once published.

If the Databricks workspace is reachable only from a private network, the published service needs a gateway or another supported path, while the laptop uses its own connection. Connector and driver versions also matter, because they affect how much logic is delegated to Databricks (query folding), how types are converted, and the resulting semantic model.

Databricks can also publish a model directly to Power BI, transferring descriptions and relationships. Informational foreign keys, seen in chapter 7, become model relationships, but they remain metadata: the correctness of cardinality and references must be verified on the data. This feature has its own requirements for capacity, XMLA endpoint, tenant settings, and permissions.

In short, with Import the report's data is that of the last successful refresh, which in turn depends on upstream publication: to know which data a report is showing, we look at the outcome and time of the refresh. With DirectQuery the data is current, filtered by the effective security context of each query.

12.3 Fabric: Metadata, Shortcuts, and Data Access

With Microsoft Fabric there are two integrations, going in opposite directions. The first brings Databricks data into Fabric without copying it. A Mirrored Azure Databricks Catalog replicates into Fabric the metadata of a Unity Catalog catalog and creates, for each table, a OneLake shortcut, a link pointing to the original files. The data stays where it is and Fabric reads it through the link. Fabric's traditional mirroring works differently: it keeps a separate replica of the data, updated with the source's changes.

This link has an important security consequence. According to the archived material, Fabric accesses the source under the connection identity, and Fabric users are then governed by Fabric security. Unity Catalog row filters and column masks, which evaluate the individual user, apply only on query paths where Databricks knows that user. The shortcut with Fabric authorization is therefore a separate security path, to be designed on its own.

It follows that only some tables suit mirroring. The connector has requirements on table types, external access privileges, networking, and OneLake security. Data protected by per-user policies requires a path that preserves that evaluation. Alternatively, a dataset approved specifically for Fabric can be prepared, becoming a new exposure boundary protected by Fabric controls.

The second integration goes the other way: Databricks writes curated data into OneLake. Here the boundary is defined by the target lakehouse, authentication, format, visibility, and permissions. Files written to a lakehouse's Files area remain plain files; for Fabric engines to see them as tables, they must be registered as such in a compatible format.

When several engines read and write the same data, each brings its own requirements: protocol, enabled table features, how metadata is updated, handling of concurrent writers. The shared path exposes the same bytes to all of them, but each engine must be able to interpret them. And reading data stored elsewhere still consumes compute, and can carry capacity, network, and data egress costs.

12.4 Power Platform: Distinguish User Access From Automation

Power Apps and Power Automate can use the Databricks connector to run SQL queries or start jobs. Here too the central question is identity. An interactive app, a background automated flow, and a service-principal connection can use different identities, even in the same environment.

Suppose we build an app to browse orders. If the app uses a service principal, all calls reach Databricks with that principal's permissions, and every user sees the same data. This is fine if the app exposes a common approved dataset. If instead each user must see only their own orders, the restriction belongs in a layer that knows the user: in the app, in the connector, or in data access under the user's identity.

A typical Power Platform concept is delegation. When a filter or aggregation is delegable, Power Apps sends it to Databricks, which applies it to the whole table. When it is not, Power Apps retrieves a limited number of rows, for example the first 500, and applies the filter only to those. As long as the table is small the results match; once it exceeds the limit, the local filter ignores the rows never retrieved and the result silently becomes incomplete.

Each connector also has its own rules on licensing, request limits, supported clouds, connection modes, and virtual tables. Grouping operations into batches reduces the number of calls; retrying while respecting limits handles throttling; idempotent writes ensure that a repeated request produces a single effect.

12.5 Purview: Discovery and Lineage

Microsoft Purview is Microsoft's enterprise data catalog, and it can scan Databricks metadata to make it searchable alongside that of other sources. The available features change between the legacy Hive metastore and Unity Catalog, and depend on the supported network and authentication modes.

It helps to tell three operations apart. Discovery, in Purview, lets us find an asset and read its description. Classification adds labels, such as "personal data", that a policy can use. Authorization stays in Unity Catalog, which evaluates grants when someone runs a query. Finding a table in Purview therefore leaves read rights unchanged.

Lineage in Purview also has coverage limited by the supported paths, tools, and transformations. To know what is captured and with what delay, we can use a known transformation as a reference and check whether and when it appears. The scanning identity's permissions, finally, decide which metadata Purview can see and therefore show.

These permissions depend on what we ask of the scanner. Discovery reads only metadata; some classifications must instead read column values to recognize their content, and therefore require broader access. The chosen connector and features define the permissions needed.

12.6 VS Code and Databricks Connect

Many developers prefer working in VS Code on their own computer. The Databricks extension for VS Code connects the local environment to the remote workspace in three ways, each with a different execution boundary. Synchronization copies local files to the workspace. Remote execution starts a file as a job in the workspace. Databricks Connect, finally, lets us run Spark code from our own computer using remote compute.

It is worth understanding how Databricks Connect works. The Python program runs on the local computer and builds the Spark operations, which are then sent to the remote compute and executed there. It follows that the local debugger, with its breakpoints, sees the Python program's flow on the client; the distributed activity of the executors is observed with remote tools such as the Spark UI.

The same split applies to dependencies. Code running locally imports the libraries installed on the computer; operations executed on remote compute use the remote environment's libraries. If a library is needed on both sides, for example in a function defined locally and executed on the executors, it must be installed in compatible versions on both. The Databricks Connect client version must also be compatible with the remote runtime version.

Synchronization goes in one direction only: from the local computer to the workspace. If someone edits files directly in the workspace, those changes stay there, outside the local repository. For this reason the artifacts that count for a release are those of approved Git revisions and the bundles seen in chapter 10.

12.7 Genie and the Analytical Data Model

Genie lets users ask data questions in natural language, such as "how much revenue did we make in Lombardy last month?". A Genie space gathers a set of governed tables and the context needed to interpret questions about them. Genie translates the question into SQL, runs it, and returns the result. The quality of the answers depends almost entirely on the context we supply: table grain, relationships, descriptions, example queries, and definitions connect the user's words to correct SQL operations. The chosen tables bound the questions the space can answer coherently.

Take the word "revenue". To compute it correctly Genie must know which order statuses to include, how to treat cancellations and refunds, how to convert currencies, which date and which timezone to use. If attributes are historical, it must also know which version to use based on the date. These are the same definitions as the data contract seen in chapter 5, and they determine which query really computes the requested number.

Context is supplied through different tools, each with its own task. Table and column descriptions explain meaning. Join relationships say which table combinations are valid. SQL expressions define reusable measures and filters, such as net revenue. Example questions with their queries show how to translate typical phrasings. General instructions add conventions and rules for the ambiguous cases that remain.

Genie can also link the user's words to values stored in the tables (entity matching): if the user writes "Lombardy" and the table uses the code LOM, the link lets it find the right rows. To do so Genie keeps sample values, which have their own freshness and can expose data: they deserve the same care as the data itself. The space's settings decide which context is visible, while actual data access remains governed by Unity Catalog authorization.

Knowing whether a space works takes test questions (benchmarks), each with its expected interpretation and result. The most useful questions probe the weak points: ambiguity, empty results, joins that can duplicate rows, historical dates, forbidden access. And results are evaluated on three separate aspects: the value is correct, the query ran successfully, the permissions were respected.

An example shows how much ambiguity matters. "Revenue last month by customer region" can mean the region where the customer is today or the one where they were at the time of the order. In the first case the query joins orders to the current dimension; in the second it uses the temporal join of chapter 7. If C42 moved in September, the two calculations attribute their August orders to different regions. A convention declared in the instructions, or a clarifying question to the user, chooses the intended calculation.

12.8 Copilot Studio and Microsoft Foundry

Agents built with Copilot Studio or Microsoft Foundry can use Databricks data as tools. The integrations described in the archived material expose tables or Genie spaces, also through managed MCP servers. Tools differ in the operation they perform. A lookup retrieves rows with structured criteria, such as "order O1". Natural-language-to-SQL translation turns a question into a query. Semantic retrieval searches content by meaning, for example in documents. The chosen tool determines which operation hides behind a question.

When an agent uses Genie, interpretation happens twice: Genie interprets the question and produces a result, and the agent interprets that result to build the final answer. Verifying an answer therefore requires keeping its provenance: which query was run and which result it returned.

For agents too the key question is identity, and the answer depends on the connector and the token flow. If the user's identity is propagated, Databricks evaluates that user's permissions. If the agent uses a fixed credential, all users access data with the application's permissions. MCP standardizes how the agent calls tools; authentication and authorization depend on the integration's security configuration.

An agent in production depends on many elements: the integration's release status, the warehouse, the network, request limits, and conversation state. On this last point there is a practical detail. If every tool call is independent, a follow-up question such as "and in the previous quarter?" makes sense only if the agent passes the tool the needed context, that is, which metric and which period were being discussed.

In all these cases, the reliability of the answer depends on that of the data: an agent answers well only if it accesses data that is correct, authorized, current, and traceable.

12.9 End-to-End Acceptance Scenario

We close the course with a scenario that puts the pieces together. A Power BI report and a Genie space show the same approved revenue, through different paths. To verify them we use a known monthly total as a reference: if both reproduce it, the source version and the revenue definition explain the agreement. We then verify the security of each path with two identities: an authorized one, which sees the data, and an unprivileged one, which is rejected.

Finally, suppose a correction arrives. With DirectQuery and Genie the correction appears at the next query; with Import it appears after the next refresh. If we revoke an access, the affected path closes, while copies already created, such as an Import model or an export, follow the controls of the downstream system. Correctness and security therefore depend both on the pipeline producing the data and on the data's lifecycle at the consumer.

The scenario is an acceptance design. Running it requires Power BI, Fabric, Power Platform, Purview, and Foundry each with their own licensing, capacity, resources, and permissions.
