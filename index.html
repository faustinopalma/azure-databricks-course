1. Architecture and Execution

Azure Databricks combines four components with distinct lifecycles: a workspace stores development artifacts, compute executes code, cloud storage persists data, and Unity Catalog governs access. A notebook remains in the workspace between executions; its compute starts when work runs; the resulting table remains in storage after compute stops. The execution identity determines which data that code can read or change.

1.1 Follow One Workload

An order system writes JSON files to cloud storage. A data engineering workload reads new files, validates order identifiers and amounts, updates analytical tables, and publishes daily revenue. Each stage has a corresponding platform component:

Responsibility Component in this example Mechanism
Store source files and table data Cloud object storage Persists the bytes; Delta Lake adds the transaction log that defines table versions.
Execute reads and transformations Databricks compute Runs code under an identity authorized to access the sources.
Register tables and govern their use Unity Catalog Resolves object names and evaluates privileges on the registered assets.
Define processing logic SQL, Python, or declarative pipeline definitions Describes the operations executed interactively or as a scheduled workload.
Schedule work and handle task dependencies Lakeflow Jobs Starts tasks in dependency order and records their execution outcomes.

An ingestion request crosses network, storage authorization, catalog privileges, compute, and data-validation boundaries. A timeout points toward connectivity; an access-denied response identifies an authorization check; a malformed-record error points toward input handling. Each symptom localizes the part of the read path that failed.

1.2 Account, Workspace, and Metastore

A Databricks account organizes workspaces, account-level identities, and shared configuration. An Azure subscription organizes Azure resources and authorizes their management through Azure RBAC. The two scopes govern different parts of the same deployment.

A workspace contains notebooks, workspace files, jobs, dashboards, and compute configurations. Separate development and production workspaces give each environment its own operational artifacts. Data isolation is established through grants, execution identities, workspace bindings, and storage and network controls.

A Unity Catalog metastore contains metadata and governance information for registered assets. A workspace attaches to one metastore at a time, and multiple workspaces can attach to the same regional metastore. This allows the same catalog objects to be used from different workspaces, subject to permissions and any workspace bindings that restrict their availability.

For example, when development and production share a metastore, sales_prod.gold.daily_revenue identifies the same registered table from either workspace. Its name communicates its purpose; its grants determine who can write to it, and workspace bindings can restrict where it is available.

Unity Catalog names data objects using catalog.schema.object. A catalog provides a high-level organizational boundary, a schema groups related objects within it, and the final name identifies a table, view, function, or volume. The metastore contains the catalogs above this three-part SQL namespace.

Legacy Hive metastore objects appear through hive_metastore.schema.table and retain their legacy governance model. Migration to Unity Catalog changes their metadata registration and authorization model.

1.3 Control Plane and Compute Plane

The control plane provides workspace interfaces, scheduling, orchestration, and resource-management coordination. The compute plane executes data-processing workloads. A query can involve both: compute processes the rows, while control-plane services coordinate execution and may handle results or operational metadata according to the feature used.

In the classic compute model, compute resources run in the customer's Azure subscription. Runtime, instance configuration, and deployment-network settings are customer-selectable. Databricks operates the managed-service components around that compute.

In the serverless compute model, Databricks provisions and manages workers in its service-managed environment. The user configures a supported workload through the controls exposed by the service. Available features and connectivity options depend on the workload and region.

A workspace can offer several compute choices. Each task therefore has its own execution location, identity, and network path to dependencies. These three properties describe its operational context.

1.4 Storage Is Independent of Running Compute

A persisted Delta table remains in durable storage after its cluster stops. Compute is needed when reading or changing its contents. Python variables and cached DataFrames live within an execution context and are reconstructed when a new context starts.

Workspace storage and analytical data storage also serve different purposes. Workspace assets and system-generated artifacts include notebook files, revisions, results, and operational information. Business tables and governed files are organized through Unity Catalog storage arrangements. The exact physical provisioning depends on the workspace and storage model.

Recovery follows those lifecycles: version control restores committed code, data retention or backups restore durable data, and checkpoints or run records support operational recovery. Reconstructing the orders pipeline can involve all three.

Unity Catalog tables provide governed access to tabular data; volumes provide governed access to files. These are the current building blocks for workloads previously implemented with DBFS root or mounts. A notebook path identifies code, a volume path identifies governed files, and a cloud storage URI identifies a physical storage location.

1.5 Understand What Executes

A notebook contains code cells and explanatory text. Its attached execution environment supplies the engine, supported languages, and APIs. A Scala cell, for example, requires an execution environment with Scala support.

Apache Spark distributes work across an execution environment. In a conventional multi-node cluster, the driver coordinates execution and executors perform tasks on partitions of data. A Spark partition is a unit of distributed processing; a storage partition describes file organization. Reads and shuffles determine how records are distributed across the partitions of a particular computation.

DataFrame transformations normally construct an execution plan. An action, such as writing a result or collecting it, triggers execution of that plan. Read, conversion, and join errors can therefore surface at the write: that is when Spark performs the planned work.

The cost of an expression comes from its execution plan. A join can read large datasets and redistribute records between executors. Filter pushdown reduces the rows read, while other optimizations reduce intermediate results. The executed plan and task metrics expose those costs.

The word job describes two execution levels. A Lakeflow Job is an orchestrated workflow containing tasks. A Spark job is an execution unit created inside a Spark application, often in response to an action. One Lakeflow notebook task can produce multiple Spark jobs and stages. Lakeflow monitoring shows workflow progress; Spark monitoring shows distributed execution.

1.6 The Platform Components in Context

Delta Lake supplies table transactions and metadata over data files. Unity Catalog registers and governs assets. Spark and Databricks execution engines process queries. Databricks SQL provides SQL-oriented execution and analytical tooling, typically through SQL warehouses.

Lakeflow Connect addresses ingestion through supported connectors. Lakeflow Spark Declarative Pipelines lets you describe datasets and their relationships so the service can manage their processing. Lakeflow Jobs orchestrates tasks and dependencies, including notebooks and pipeline updates. A workflow can use all three: ingest customer changes, update derived datasets, and then run a downstream validation task.

Machine learning features such as MLflow use the data produced by these workloads. Training and serving depend on governed, reproducible inputs; data engineering supplies their quality, access controls, and traceability.

1.7 Reason Through the Boundaries

Three outcomes in the orders pipeline illustrate these boundaries:

  1. A developer opens a notebook and receives an authorization error reading sales_prod.bronze.orders. Workspace permissions authorized the notebook access; table privileges are evaluated separately against the execution principal.
  2. A result stored as a temporary view or cached DataFrame disappears when compute restarts. Writing that result to a persistent table gives it a lifecycle independent of the execution context.
  3. A scheduled run succeeds under a service principal while the same code fails interactively for a developer. Different execution identities produce different authorization outcomes for the same table operation.

2. Storage and Unity Catalog Objects

Storage has three independent properties: lifecycle ownership, file format, and access interface. Managed and external describe ownership; Delta describes a table format; tables and volumes expose relational and file-based interfaces. A managed table and an external table can both use Delta Lake. A volume exposes files, including CSV and Parquet, through paths.

2.1 Establish the Namespace Before Loading Data

The orders workload uses sales_dev and sales_prod catalogs to organize environments, with bronze, silver, and gold schemas. Bronze preserves source-level information, silver contains validated data, and gold publishes business datasets. Transformation code implements these responsibilities; the schema names make the processing stages recognizable.

CREATE CATALOG IF NOT EXISTS sales_dev;
CREATE SCHEMA IF NOT EXISTS sales_dev.bronze;
CREATE SCHEMA IF NOT EXISTS sales_dev.silver;
CREATE SCHEMA IF NOT EXISTS sales_dev.gold;

Creation requires managed storage and the corresponding create privileges. Some environments specify the storage location explicitly at catalog creation. IF NOT EXISTS creates an absent object and leaves an existing object's owner, location, and permissions unchanged.

A write to orders resolves against the session's current catalog and schema. A write to sales_prod.silver.orders has an explicit destination. Deployment parameters can select the catalog while keeping the schema and table interface stable across environments.

Stable names identify ownership, environment, and purpose for consumers. Descriptions and version control record changing lifecycle information, while privileges control access. Unity Catalog identifier normalization makes names differing only in letter case unsuitable as separate object identities.

2.2 Managed Storage Resolution

For customer-configured managed storage, Unity Catalog determines the managed location from the most specific applicable setting: schema, then catalog, then metastore fallback. Configuring storage at catalog scope often aligns physical placement with a data domain or environment. A schema-specific location provides a narrower placement rule when required.

Unity Catalog allocates object-specific locations beneath the configured managed-storage root. It coordinates those files with object metadata and deletion. Registering an overlapping external table or moving the files manually introduces a second owner of the same bytes and can break that coordination.

Storage placement chooses where bytes live. A storage identity authorizes the platform to reach those bytes; Unity Catalog privileges authorize users to access the registered objects. Both authorization layers participate in a read.

Default storage is a service-managed storage option. The archived course associates its catalog creation with serverless workspaces and its use with serverless compute. Managed tables backed by customer cloud storage support other documented compute configurations. Storage mode therefore determines the applicable compute and direct-access options.

2.3 Managed Versus External Tables

Decision Managed table External table
Who manages table metadata? Unity Catalog Unity Catalog
Who controls the underlying data lifecycle? Databricks manages it with the table The external storage owner retains responsibility
How is the location selected? The applicable managed storage configuration An explicit registered external location/path
What does dropping the object mean? Metadata removal and managed data deletion according to the supported recovery/lifecycle rules Registration removed; underlying files retained
Why choose it? Databricks is the primary data manager and supported automated maintenance is useful Existing or independently managed data must remain at a controlled external location

Both table types consist of metadata and cloud files. Unity Catalog governs access through the registered table. Direct access to external files follows cloud-storage permissions instead, so those permissions define a second access path to the same data.

A managed-table example is deliberately small:

CREATE TABLE sales_dev.silver.orders (
  order_id BIGINT NOT NULL,
  customer_id BIGINT,
  order_total DECIMAL(18,2),
  order_timestamp TIMESTAMP
) USING DELTA;

No LOCATION is specified, so the example relies on managed storage. An external Delta table instead registers an approved data path:

CREATE TABLE sales_dev.bronze.orders_external
USING DELTA
LOCATION 'abfss://landing@examplestorage.dfs.core.windows.net/orders_delta/';

The illustrative URI identifies an existing Delta table, including its transaction log. Registration requires a storage credential, external location, privileges, and connectivity. Loading JSON into a Delta table is a separate read-and-write operation.

DROP TABLE removes registration and, for managed tables, starts the managed deletion lifecycle. External files remain under their owner's control. Where supported, CREATE OR REPLACE TABLE replaces definition or data while preserving metadata according to the operation's documented semantics. The distinction matters to dependent queries, privileges, and table history.

2.4 Files Belong in Volumes When the Interface Is File-Based

A Unity Catalog volume exposes files through an object named catalog.schema.volume. Landing files, documents, model artifacts, CSV, and Parquet can all use this path-based interface. A table exposes rows and columns through queries; a volume exposes files through filesystem operations.

CREATE VOLUME IF NOT EXISTS sales_dev.bronze.order_files;

Files are addressed through /Volumes/sales_dev/bronze/order_files/.... The volume is the Unity Catalog permission boundary, and its subdirectories share that boundary. Separate volumes allow invoices and public product images to have separate grants.

Managed volumes use managed storage and the volume-specific deletion lifecycle. External volumes register independently managed paths and retain their files after the volume is dropped. Volumes and tables have their own deletion and recovery rules.

A storage credential represents the identity used to access cloud storage. An external location associates a path with that credential and a governable boundary. An external table or volume is then created within an appropriate location. These are three different objects: identity, authorized path, and data interface.

2.5 Tables, Views, Materialized Views, and Streaming Tables

A standard view stores a query definition. Each query against the view evaluates that logic against the underlying data. The view gives consumers a stable projection, reusable business rule, or governed interface; its read cost includes the underlying computation.

A materialized view stores a query result and updates it through refreshes. Repeated reads reuse the stored result, shifting computation to refresh time. An hourly dashboard can tolerate the delay between refreshes; a fraud response system may require fresher data. Refresh frequency connects read cost to freshness.

An incremental refresh updates the result from source changes. Its eligibility depends on source features, query shape, and service decisions. A full recomputation processes a broader input when incremental maintenance is unavailable or unsuitable; refresh history shows which strategy ran.

A streaming table processes source data incrementally, using recorded progress to select the next input. An append-only stream adds new records; applying corrections to earlier records requires change processing, such as CDC. Checkpoints and refresh policy govern how processing resumes or rebuilds.

Materialized views and streaming tables are maintained from their declared definitions. The service owns their update lifecycle, so refresh or pipeline operations are the interface for maintaining their results.

2.6 Foreign Catalogs and Remote Queries

A foreign catalog exposes supported external-system metadata through a Unity Catalog connection. In query federation, a query can push supported operations into the remote database and retrieve results without first replicating all source data into local tables.

An external table registers files at a cloud-storage path. A foreign catalog exposes a remote system's namespace. Federated queries therefore depend on the remote database's availability, credentials, connectivity, execution capacity, and supported pushdown operations.

Federation suits exploratory or limited cross-system queries because it reads the source on demand. Ingestion creates a durable local analytical copy, decoupling downstream processing from source availability and shifting repeated analytical reads away from the operational database.

A connection stores the remote endpoint and authentication arrangement; a foreign catalog exposes the chosen remote namespace. Users receive catalog privileges while the connection manages the underlying credentials.

2.7 Check the Design

For our orders system, the source team owns the incoming files, Databricks owns validated analytical tables, and analysts need a daily summary. A reasonable design is an external landing volume when the files already live in independently managed storage, managed silver/gold tables for Databricks-owned outputs, and a view or materialized view chosen according to query cost and freshness requirements.

In this design, removing the landing-volume registration leaves source-owned files intact. Managed analytical tables remain available between compute runs. Grants and workspace bindings define their availability to other workspaces. Object type establishes lifecycle ownership; permissions establish access.

The catalog objects lab provides hands-on work. Basic managed objects may fit a supported learning workspace; external storage, connections, and specific refresh capabilities require their own prerequisites.

3. Compute Selection and Configuration

Compute runs a workload within a specific combination of APIs, libraries, identity rules, and connectivity. Compatibility determines the available choices; the execution pattern determines their lifecycle. Total cost includes startup, processing, idle time, and retries. A short daily job and an interactive BI workload can therefore benefit from different compute even when they read the same tables.

3.1 Separate the Selection Axes

Compute terminology combines several independent choices:

Axis Question Examples
Infrastructure management Who manages the execution infrastructure and its configuration? Serverless or classic
Workload interface What kind of work is submitted? Notebooks, job tasks, SQL queries, declarative pipeline updates
Access mode on applicable classic compute How are identities and workloads isolated? Standard or dedicated
Resource shape What execution resources are available? Single-node or multi-node, worker family, memory/core ratio
Lifecycle How long does compute exist? Interactive session, job-associated compute, warehouse lifecycle

These choices combine: a job can run on serverless or classic infrastructure, and applicable classic compute can use standard or dedicated access mode. Infrastructure, interface, isolation, resource shape, and lifecycle describe separate properties of that execution.

3.2 Match the Workload

Serverless manages worker provisioning and much infrastructure configuration for supported workloads. Consumption still depends on the volume of data, query plan, dependencies, and selected performance mode: those factors determine how much work the managed infrastructure performs.

Classic compute exposes controls such as runtime and instance selection, supported initialization, and execution APIs. These controls suit workloads needing a particular runtime, hardware, or system configuration. Compatibility is specific to the workload and current runtime or service release.

A SQL warehouse serves SQL queries and BI clients. Serverless, pro, and classic options differ in management and execution capabilities. Notebook compute executes supported notebook languages and APIs. The submitted workload determines which interface is suitable.

A job-associated environment gives a workload its own execution lifecycle and declared dependencies. A long-lived interactive cluster shares capacity, installed libraries, and restart events across sessions. Dedicated job lifecycles reduce that coupling and add startup or repeated initialization costs.

Serverless performance-optimized mode prioritizes startup latency. Standard mode can accept a slower start in exchange for lower consumption. The mode expresses a latency-versus-cost choice for a particular run.

3.3 Access Mode Is a Security and Compatibility Decision

Standard access mode supports isolated multi-user execution for supported workloads. Dedicated mode assigns compute to a user or, where supported, a group. Access mode determines how execution identity is applied and which APIs are available; legacy shared compute without isolation has different security properties.

Group-dedicated execution uses the group's permission and ownership context. A member's personal access to an extra table belongs to that person's context. This explains why identical code can have different access outcomes in personal and group-dedicated execution.

Language support is specific to the execution interface: notebook cells, job task types, and libraries have distinct support matrices. The archived unit contains conflicting statements about Scala on serverless; the feature-specific compatibility documentation linked below is the reference for that combination.

3.4 Size for the Limiting Resource

Executor cores provide task execution capacity. Memory supports joins, aggregations, state, and caching. Local disk supports intermediate spill, shuffle, and some caching. The driver has separate responsibilities and can fail even when executors have free memory, particularly if application code collects too much data to the driver.

Additional workers increase executor capacity when enough independent tasks are ready. A large driver-side object consumes driver memory; a skewed key concentrates work in a few partitions; a throttled source limits input rate. CPU, memory, I/O, network, source capacity, and task balance each impose a different ceiling on throughput.

At equal total cores and memory, cluster shape changes network traffic, failure domains, per-node overhead, and memory concentration. More small nodes spread resources across machines; fewer large nodes concentrate them. A benchmark with the same input and concurrency reveals how these differences affect the workload.

A single-node environment performs all work on one machine and suits small workloads. For a small dataset, startup and coordination can dominate execution time, making a larger cluster slower and more expensive.

3.5 Autoscaling, Pools, and Termination

Autoscaling changes resource count within configured bounds as demand changes. Provisioning takes time, the maximum caps capacity, and the minimum establishes an idle-cost floor. Partition distribution and streaming state determine how effectively the workload uses newly available resources.

An instance pool keeps reusable VMs ready for classic compute. Warm instances shorten provisioning time and incur Azure VM charges while idle; Databricks processing charges follow compute use. The pool's maximum limits the number of instances it can supply.

Pool demand is the number of simultaneous driver and worker instances. Several notebooks can share a cluster, while one notebook can use many workers. Notebook count and VM count therefore describe different kinds of demand.

Automatic termination controls idle interactive compute. Job-associated compute follows the job lifecycle. Pool idle termination controls reusable instances separately, so a pool can retain its configured minimum after a cluster terminates.

Spot workers offer lower-cost, reclaimable capacity. Reclamation can trigger recomputation and delay; driver protection and supported decommissioning reduce disruption. Their economic benefit is the acquisition saving after accounting for retries and completion delays.

3.6 Runtime, Photon, and Libraries

Databricks Runtime supplies a Spark version and packaged execution environment for applicable classic compute. LTS defines the support lifecycle. Dependency compatibility and query behavior depend on the particular release, which is why upgrade comparisons use representative correctness and performance tests.

Photon executes supported SQL and DataFrame operations in a native engine. Its benefit depends on the share of runtime spent in those operations. Driver-side Python and network waits retain their own costs, so the executed plan determines the acceleration available to the whole workload.

Machine learning runtimes package ML libraries and support their execution patterns. Their value comes from the dependencies and operations performed by the workload itself.

Dependency scope determines reproducibility and blast radius:

Scope Consequence Appropriate use
Notebook/session dependency Limited to the supported session environment Exploration with explicit versions
Job/task dependency Declared with the workload Repeatable production execution
Compute-scoped dependency Affects workloads sharing the cluster; installation is reapplied at startup Intentionally shared environment
Initialization script Executes startup configuration and can prevent startup if it fails Required system configuration not handled by normal library mechanisms

Versioned dependency declarations reproduce the same environment on each deployment. Library mechanisms install application packages; initialization scripts handle startup system configuration. Manual session changes disappear when the environment is recreated unless captured in those declarations.

Standard access mode can require approval for JARs, Maven coordinates, and initialization scripts. The allowlist approves an artifact for execution; READ VOLUME authorizes reading its files; compute permissions authorize managing or using the compute. Loading a package can involve all three checks.

3.7 Compute Permissions and Entitlements

For applicable classic compute, CAN ATTACH TO permits attachment, CAN RESTART adds lifecycle operations, and CAN MANAGE adds configuration and permission management. These workspace permissions govern compute use. Azure roles govern Azure resources, and Unity Catalog grants govern data objects.

A workspace entitlement enables capabilities such as unrestricted cluster creation. A compute policy constrains allowed configurations. Together with compute permissions and data grants, they determine what an identity can create and execute.

Driver logs contain application and library output and can expose sensitive values, including transformations of secrets that escape redaction. Log-access controls and credential-free application output reduce this exposure.

3.8 Apply the Decision

The daily orders transformation is a notebook job with specific SQL/Python, dependency, and connectivity requirements. Compatible serverless and classic job environments can be compared on total run cost. BI queries use a SQL warehouse. A legacy API dependency can make classic compute necessary until the code is migrated.

4. Identity and Authorization

A data read is a chain of checks: an identity submits a query, compute executes it, Unity Catalog authorizes the object operation, and a storage identity reaches the files over an allowed network path. Azure Contributor authorizes resource management; SELECT authorizes table reads; firewall rules govern connectivity. Success requires the applicable checks along the whole path.

4.1 Identify the Principals in the Request

Four identities participate in the orders pipeline:

Identity Responsibility Typical authorization surface
Interactive developer Authors and tests code Workspace objects, compute, and Unity Catalog
Deployment principal Creates or updates job and pipeline definitions Workspace APIs and resource permissions
Job execution principal Runs the production workload Input/output objects, secrets, and execution resources
Storage identity Authenticates the governed storage connection to Azure Azure storage data-plane roles and applicable storage controls

These identities can coincide or have separate grants. A deployer with permission to edit a job can publish it successfully while its execution principal receives a source-access error. The author, deployer, and runtime each act under their own authority.

Databricks-managed service principals provide platform-managed automation identities. Microsoft Entra ID-managed service principals connect to Entra application identities and can support automation spanning Azure services. Authentication supplies a token for the target API's audience and supported mechanism.

A managed identity is a workload identity with credentials maintained by Azure. When used by a storage credential, it authenticates storage requests. A job's execution principal is configured separately and supplies the user-level authority for its operations.

4.2 Grant the Complete Privilege Combination

Reading a table normally combines USE CATALOG, USE SCHEMA, and SELECT. The first two authorize use of the namespace; the third authorizes reading the table. The grants below give analysts access to the published revenue table:

GRANT USE CATALOG ON CATALOG sales_prod TO `revenue-analysts`;
GRANT USE SCHEMA ON SCHEMA sales_prod.gold TO `revenue-analysts`;
GRANT SELECT ON TABLE sales_prod.gold.daily_revenue TO `revenue-analysts`;

This example assumes the group and objects already exist and the grantor is authorized to manage the grants. It gives a group one analytical interface rather than access to raw customer data.

A transformation needs read privileges on its sources and write privileges on its target. MODIFY authorizes table data changes; creating an object requires the corresponding creation privilege on its container. The workload's operations determine this privilege combination.

The same distinction applies to files. A volume reader needs namespace usage plus READ VOLUME; a writer needs the supported read/write combination and any operation-specific requirements. Creation of an external object additionally depends on the appropriate external-location privilege.

4.3 Inheritance, Ownership, and Administration

Schema-level SELECT is inherited by current and future applicable objects. A newly created table therefore enters the schema's existing read-access boundary. Table-level grants define a narrower boundary; separate schemas can group data with different audiences.

Effective access combines direct grants, group membership, inherited grants, ownership, and applicable policies. After a direct table grant is revoked, an inherited schema grant can still authorize the read. This is why effective access is evaluated across the privilege hierarchy.

Ownership gives administrative authority over an object's lifecycle. Assigning production ownership to an operational group lets that responsibility survive individual staff changes.

MANAGE authorizes object administration, including privilege management under the current model. Reading data requires a data-access grant such as SELECT. The ability to grant that access makes privilege administrators part of the data's trust boundary.

ALL PRIVILEGES expands to the applicable privilege set defined for the object type. The current reference excludes MANAGE, EXTERNAL USE SCHEMA, EXTERNAL USE LOCATION, and READ METADATA; these have separate grant semantics.

4.4 Workspace Bindings and the Storage Boundary

Workspace bindings add an origin condition to supported catalog or storage objects. The principal needs the relevant privilege and the request needs an allowed workspace. A production-only binding can restrict a catalog shared through a regional metastore to production workspaces.

Direct cloud-storage requests take a separate authorization path. Storage credentials and Azure data-plane permissions govern that path, while Unity Catalog privileges govern registered-object access. Restricting direct cloud access closes an alternative route to the same files.

For Azure storage, a common managed-identity design is:

  1. An Azure Databricks access connector references a system-assigned or user-assigned managed identity.
  2. Azure storage data-plane roles authorize that identity to read or write the chosen storage scope.
  3. A Unity Catalog storage credential refers to the connector and the applicable identity.
  4. An external location associates the credential with a storage path.
  5. Object and location grants authorize operations by Databricks principals.
  6. Network rules allow the compute-to-storage connection needed by those operations.

A system-assigned identity follows its connector's lifecycle. A user-assigned identity has an independent Azure lifecycle. Removing a connector, revoking the identity's storage role, or changing a firewall can break a pipeline even when its Unity Catalog grants are unchanged.

File-event ingestion also uses a notification path. Event resources, queue access, and blob access have distinct roles in discovering and reading new files; the connector's supported setup brings them together.

4.5 Row Filters, Column Masks, and Views

Row filters select the rows visible to a query. Column masks transform protected values during query execution. Both operate through supported query paths and compute. Encryption and direct-file authorization protect the underlying storage separately.

For example, a mask can reveal customer email only to an authorized account group:

CREATE FUNCTION sales_prod.silver.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('customer-support') THEN email
  ELSE '[masked]'
END;

ALTER TABLE sales_prod.silver.customers
ALTER COLUMN email SET MASK sales_prod.silver.mask_email;

The example requires the table, function and policy-management permissions, and compatible compute. The function preserves the string type: members of customer-support receive the email value; other callers receive [masked]. Null handling and use in filters or joins are part of its observable query behavior.

A dynamic view stores a controlled projection and identity-dependent predicates, potentially joining several objects. Consumers query this interface under its access rules. Separate base-table grants provide an additional path governed by those tables' permissions.

View resolution involves ownership and caller context. The chosen filtering or ABAC mechanism defines how each context participates in policy evaluation. Queries executed as the intended consumer reveal the effective rows and masked values for that identity.

ABAC adds centralized policy selection based on governed attributes; the next chapter explains how it differs from attaching individual masks to individual tables.

4.6 Secrets Are a Separate Authorization Surface

A secret supplies a credential required by a dependency, such as a database password. A secret scope authorizes retrieval; the remote service then authenticates and authorizes the credential. Identity-based integrations delegate credential lifecycle to the identity platform where supported.

Databricks-backed scopes store secrets in Databricks. Azure Key Vault-backed scopes provide an interface to secrets managed in Key Vault. With the latter, secret creation and rotation occur in the vault rather than by writing through the Databricks scope.

Key Vault-backed scopes use a specific integration with supported vault permission models and network configurations. Those requirements determine which vault configurations can serve a Databricks scope.

Scope readers can retrieve secrets exposed by the linked vault. Separate vaults and scopes create distinct credential boundaries for audiences such as development and production operators.

Secret redaction conceals recognized values in supported output. Code authorized to retrieve a secret can also transform or transmit it. Logs, URLs, cluster configuration, and environment variables can therefore widen its exposure beyond the original scope boundary.

Rotation comprises creation of a new credential, adoption by consumers, and retirement of the old credential. Running environments may cache or inject values at startup, making reload or restart part of adoption. A successful downstream connection with the new version confirms that transition.

5. Governance, Retention, and Sharing

Governance defines the meaning, access, ownership, and lifecycle of data. For orders, it connects the definition of an order to the identities allowed to change it, the consumers receiving those changes, the recoverable history, and the datasets disclosed to partners.

5.1 Metadata and the Data Contract

A data contract defines grain, source, refresh behavior, and business interpretation. order_total DECIMAL(18,2) specifies numeric precision; the contract adds currency, tax treatment, and refund representation. Those details determine how an amount can be aggregated and compared.

For daily_revenue, the day can mean order date or settlement date in a specified timezone. Included statuses determine which orders contribute; cancellation rules determine whether previous totals change. A generated SQL query is correct when it implements that definition.

Metadata is part of the deployed interface. A drop-and-recreate sequence can change descriptions, grants, ownership, and dependencies along with the data. A deployment contract therefore includes these properties as well as the loaded rows.

Generated comments derive their meaning from the context supplied to the model. Source definitions and transformation rules provide the evidence for accepting a suggested description as authoritative metadata.

5.2 Attribute-Based Policy Selection

Attribute-based access control (ABAC) selects policies using attributes such as governed tags. Instead of attaching an email mask separately to hundreds of columns, define an approved classification and a policy that matches it. Newly classified objects can then receive the intended control without another hand-written table policy.

Four elements participate in policy evaluation:

  • The governed tag definition controls allowed classification keys/values and who can assign them.
  • The classification identifies the data selected by a policy.
  • The policy establishes scope, relevant principals, and the filter or mask to use.
  • The function defines the transformation or row condition.

A tag classifies data; a matching policy selects the control; a function implements it. Underlying privileges authorize the query before its results are filtered or masked. Changing a policy-relevant tag can change the effective protection, making tag-assignment authority part of the security boundary.

Policy coverage is visible in the outcomes for newly tagged columns and different principals. Overlapping filters or masks follow the feature's conflict-resolution and inheritance semantics; conflicting effective controls can produce access errors. Those cases reveal how policy selection behaves as the catalog grows.

Policy functions run within queries, so their evaluation cost becomes part of query cost. Simple expressions are easier to optimize than complex lookups. Where supported, the policy selects the audience and the function performs the transformation, separating selection from execution.

5.3 Retention Has Several Independent Clocks

Retention applies to several kinds of information, each with its own lifetime:

Older table versions and data files Time travel and recovery Delta log/file retention and maintenance

Delta time travel reconstructs a version from its metadata and referenced data files. Its recovery window ends when either becomes unavailable. A 30-day recovery requirement therefore needs compatible retention for both logs and files.

VACUUM removes obsolete files eligible under the retention rules. A file containing old orders remains necessary while the current snapshot references it. Business retention changes the logical records, for example through DELETE; file cleanup later reclaims eligible physical data.

The commands expose table properties, committed history, and files that a cleanup would remove. DRY RUN lists candidates while leaving them intact. Retention protects the files needed by long readers, active writers, stream recovery, and rollback; a shorter window can remove those dependencies too early.

5.4 Logical Deletion and Physical Erasure

A DELETE removes rows from the current logical table state. Older versions can still reference their data, and deletion vectors can represent removed rows without immediately rewriting all affected data files.

A deletion process therefore has several steps: identify the subject's data, apply logical deletions, propagate them to derived datasets, physically purge affected content using the supported table maintenance process, allow the required retention interval, and verify the scope of remaining copies. For deletion-vector workloads, the supported rewrite/purge operation and later cleanup serve different purposes.

skipChangeCommits lets a stream skip certain source-change commits, leaving previously appended downstream rows in place. Propagating deletion requires a change feed whose delete records are applied, coordinated deletions, or recomputation from authoritative current data. This distinction corrects the archived retention example.

A refreshed result can incorporate source deletions, while an append-only output retains its earlier rows until explicitly changed. Derived tables, exports, sensitive checkpoint state, recipient copies, and backups each have a lifecycle through which the deletion propagates.

Legal and data-governance owners define required evidence and exceptions; the engineering process produces the deletion and verification records for that scope.

5.5 Maintenance and Storage Lifecycle

Predictive optimization schedules supported maintenance for managed tables, including compaction, cleanup, and statistics-related work. The configured retention window governs which obsolete files automated cleanup can remove.

Cloud lifecycle policies select storage objects by criteria such as age. Delta snapshots and streaming checkpoints reference particular objects. Deleting an active referenced file breaks reads or recovery; moving it to an offline archive tier makes access depend on rehydration.

File age records storage operations, while event time describes business activity. Compaction can put old business records into newly written files. Table-aware archival or a separately managed archive dataset preserves that distinction while keeping the operational table queryable.

5.6 Lineage, History, and Audit Answer Different Questions

Lineage identifies observed dependencies between data assets and operations. It helps answer which consumers may be affected if order_total changes meaning or type. Table history records transactional changes to a Delta table. Audit events record supported actions and actors across service surfaces.

Each source records a specific fact: a lineage edge records a dependency, a history entry records a transaction, and an audit event records an action and actor. For example, getTable records a metadata lookup. Transformation correctness comes from data validation; data-read evidence comes from the relevant execution or audit events.

Catalog Explorer presents ownership, dependencies, and available history. Column-change impact includes downstream datasets, jobs, views, and dashboards. Captured lineage supplies observed dependencies; code references and published contracts add dependencies outside that capture. Compatibility tests show how consumers behave with the new definition.

Verbose audit logging can retain command text, increasing investigative detail and sensitive-data exposure. Log permissions and retention govern that evidence. Azure diagnostic settings separately configure delivery to Azure Monitor, storage, or a SIEM.

5.7 Share Deliberately

6. Ingestion, Streaming, and Schema Evolution

Ingestion transfers new information into a target while recording progress. Immutable files are discovered by file identity, snapshots describe a selected source state, and change events carry operations on existing entities. Replay behavior depends on which of these units the source supplies and how the target records its application.

6.1 Start With the Source Contract

An order-event feed records transitions, such as "order cancelled", even when order_id already exists. A current-state order table records the latest accepted representation of each order. The feed preserves events; the table resolves them into state.

The source contract defines keys, update and delete operations, ordering, schema, and replay window. It also defines snapshot consistency: a transactionally consistent extract represents one source state, while a moving extract can observe records from different moments.

A full snapshot replaces or reconciles a selected source state. Cursor extraction reads rows whose update field exceeds a saved position; log-based CDC captures operations from the change log. Hard deletes require a deletion signal because the row disappears from cursor queries. Equal cursor values and overlapping batches require tie-breaking or deduplication rules.

Source behavior Candidate approach Main correctness question
Small periodic full dataset Snapshot/CTAS/replacement Is the snapshot complete before it is published?
Recurring immutable files COPY INTO or Auto Loader How are already discovered files and duplicated business events distinguished?
Supported operational database changes Managed Lakeflow Connect CDC connector Can the source retain changes through gateway/pipeline outages?
Event bus Structured Streaming with a supported connector Which offsets, event schema, and retention window govern replay?
Unsupported/custom source Notebook or external extraction service Who implements progress, retries, throttling, and delete handling?

Azure Data Factory can own cross-system scheduling and recovery, invoking Databricks for processing. Target deduplication and transactions remain responsibilities of the ingestion and write logic. A single scheduling owner gives retries and run dependencies one coordinated lifecycle.

6.2 SQL Loading Methods Have Different Repetition Semantics

CTAS creates a table from a query result. IF NOT EXISTS makes this a create-if-absent operation, preserving an existing table unchanged. This suits initial loading or creation of a new dataset.

CREATE OR REPLACE TABLE ... AS SELECT makes the query result the new target contents under the supported semantics. A query selecting only yesterday's records therefore produces a target containing only yesterday. Its input scope defines the replacement scope.

COPY INTO records which files it has loaded into a Delta target. Normal reruns skip those files, providing file-level idempotency. Two distinct files containing the same order are both eligible, so business-event uniqueness requires a row-level rule.

COPY INTO sales_dev.bronze.order_events
FROM '/Volumes/sales_dev/bronze/order_files/incoming/'
FILEFORMAT = JSON;

The example requires an existing compatible target and a valid volume path. Force reload, changed files, target replacement, or reset ingestion state can make earlier input eligible again. Rerun behavior follows the retained file-tracking state.

Auto Loader adds sustained large-scale file discovery and richer schema handling to incremental ingestion. These capabilities are useful when arrival rate and schema variability exceed the needs of a simple recurring SQL load.

6.3 Structured Streaming Is Incremental Execution With State

Structured Streaming represents a source as an incrementally processed dataset. A streaming query defines source, transformations, sink, and checkpoint location. The engine records progress and, where needed, state used by operations such as aggregations or deduplication.

A checkpoint stores one query's progress and operational state at a durable, query-specific path. Restarting with that checkpoint resumes recorded progress. A fresh checkpoint creates a new consumer history; sharing a checkpoint across independent queries makes their state conflict.

Recovery combines source replay, checkpoint state, and sink commit behavior. Supported Delta sinks coordinate writes with progress for exactly-once processing. An external callback can execute again after failure, so email delivery or external writes need their own idempotency mechanism.

Output mode selects emitted results: append emits new result rows, update emits changed result rows, and complete emits the full result for supported query combinations. Applying these rows to an existing target by business key is a separate operation, such as MERGE.

6.4 Auto Loader Separates File Discovery From Row Meaning

Auto Loader is a Structured Streaming source for incremental file ingestion. It tracks discovered files and supports directory listing or supported file-event/notification mechanisms. Event-based discovery can reduce repeated listing overhead, but requires the appropriate source and cloud configuration.

incoming = "/Volumes/sales_dev/bronze/order_files/incoming/"
state_root = "/Volumes/sales_dev/bronze/ingestion_state/orders/"

order_stream = (
    spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", state_root + "schema")
    .load(incoming)
)

query = (
    order_stream.writeStream
    .option("checkpointLocation", state_root + "checkpoint")
    .trigger(availableNow=True)
    .toTable("sales_dev.bronze.order_events")
)
query.awaitTermination()

The example requires both volumes, suitable target permissions, and a compatible runtime. /Volumes/ paths use slash-separated catalog, schema, and volume names. State resides outside the input directory, keeping operational metadata separate from files eligible for ingestion.

The schema location stores inferred structure; the checkpoint stores progress and state; the target stores committed output. Recovery coordinates these three artifacts so their assumptions about processed data remain consistent.

If evt-100 appears in two distinct files, both are valid new discoveries. Deduplication by event identity or source sequence then reduces the two rows to one accepted business event. File discovery and event deduplication operate at different granularities.

6.5 Schema Inference, Evolution, and Rescue

Inference proposes a schema from observed data. Sampling can miss rare values, and numeric-looking identifiers can carry textual meaning. A postal code represented as a string preserves leading zeros even when every observed character is a digit.

For common text formats, Auto Loader can infer strings conservatively; type inference or schema hints refine that choice. The schema expresses the expected structure, and mismatch handling determines the fate of records outside it.

Schema changes include new columns and incompatible types. Semantic changes can preserve the type: an amount can switch from local currency to USD while remaining decimal. Business-contract checks detect that change through meaning rather than structure.

Evolution policy Expected operating choice Consequence to plan for
Add new columns Accept compatible structural growth Detection can update stored schema and stop the stream; the documented restart procedure is still required.
Rescue unexpected fields Preserve unexpected input outside the main schema Rescue counts expose structural mismatches for review and reprocessing.
Fail on new columns Require an explicit contract change Processing resumes after the input or accepted schema is corrected.
Ignore new fields under the selected mode Preserve a stable projection Information may not reach the intended columns; this is a deliberate loss/omission policy.

Type widening expands a supported type's representable range, subject to runtime and table features. Converting a string to an integer instead interprets content and can fail on nonnumeric values. These are distinct forms of schema change.

_rescued_data retains input that falls outside the expected schema. Its population rate measures structural mismatch. After an accepted schema change, reprocessing can move those preserved values into their intended columns.

6.6 Triggers and Processing Cadence

AvailableNow processes the available increment of a supported source and stops. Repeated scheduled runs reuse the checkpoint, combining retained incremental progress with bounded compute activity.

A processing-time trigger requests recurring micro-batches. A batch lasting longer than the interval limits the achievable cadence; backlog grows when input rate exceeds processing rate. Continuous pipeline mode governs pipeline activity, continuous job scheduling governs run repetition, and Spark continuous processing is a separate execution mode.

End-to-end freshness includes source publication cadence, startup, processing, and scheduling delays. Hourly source snapshots set a freshness floor regardless of a faster polling schedule. A reporting workload tolerating 30 minutes can use bounded incremental runs and avoid paying for continuous compute.

6.7 Event Hubs and Kafka-Compatible Ingestion

Azure Event Hubs exposes a Kafka-compatible endpoint. Spark's Kafka source returns topic, partition, offset, timestamp, and binary key/value fields. Payload decoding converts the value into typed columns; retained partition and offset identify its source position during duplicate or malformed-event investigations.

The connection combines an endpoint, TLS and authentication settings, topic or event-hub name, and permissions. Supported secret or identity configuration supplies credentials. The native Event Hubs connector shown in the archive is a separate integration with its own format, dependencies, options, and payload schema.

Starting offsets initialize a new query; resumed queries normally use checkpointed progress. Recovery also requires the source to retain the referenced offsets. An outage longer than source retention creates a replay gap even with an intact checkpoint.

6.8 CDC, Delta Change Data Feed, and AUTO CDC

CDC is the general pattern of capturing source inserts, updates, and deletes. Delta Change Data Feed is a table feature that exposes changes in a Delta table over retained versions. AUTO CDC is a managed change-application mechanism in supported Databricks declarative pipelines. One can consume data produced by another, but they are not the same feature.

A usable change record needs a business key, operation meaning, and ordering information. A timestamp can order changes only if the source guarantees sufficient precision or supplies an additional tie-breaker. Ingestion arrival time is usually a poor replacement for the source's change sequence because networks and retries can reorder arrivals.

Managed Lakeflow Connect database connectors can combine initial loading with change capture; query-based connectors extract through queries and cursors. Gateway use, log technology, supported schema changes, and replay requirements depend on the connector.

AUTO CDC applies keyed, sequenced changes to current state or supported SCD type 2 history. The source contract defines delete meaning and partial updates. An omitted field can mean "retain the previous value", while an explicit null can mean "clear it"; null-update handling implements that distinction.

Delta Change Data Feed exposes inserts, deletes, and update preimages/postimages. Applying the operation type produces the intended state; counting every feed row as a new fact can count both sides of an update. Feed retention bounds replay, while a persisted history table can keep captured changes longer.

7. Table Design, Transactions, and History

A table's grain is the meaning of one row. Orders, order lines, and order-state changes have different grains and support different calculations. Joining them changes row multiplicity, which directly affects counts and revenue totals. Format and physical layout determine how that logical model is stored and read.

7.1 Grain, Keys, and Measures

For order lines, a candidate business key is (order_id, line_id). For order events, it may be an event identifier or a source key plus sequence. A customer dimension uses a customer business key, but a historical dimension needs an additional way to identify each customer version.

At line grain, line quantities and amounts can be summed under their business rules. An order-level shipping fee repeated on three lines would be counted three times by the same sum. Snapshot counts measure represented entities; event counts measure transitions. The table contract establishes the unit behind each measure.

A business key identifies the source entity. A surrogate key identifies a stored row or version, allowing several historical rows to refer to the same entity. Identity-generated values provide one surrogate-key mechanism with its own supported features and concurrency behavior.

Informational primary and foreign key constraints document relationships for readers and supported optimizer features. Pipeline checks establish whether keys are unique and references resolve. The declaration describes the relationship; validation measures whether the data satisfies it.

7.2 File Formats and Table Formats Solve Different Problems

CSV and JSON describe serialized records. They are useful for interchange but require decisions about types, escaping, malformed values, and nested structure. Parquet is a columnar file format with typed columns and encoding suitable for analytical reads.

Delta Lake adds a transaction log and table semantics over data files, commonly Parquet. Apache Iceberg is another table format with its own metadata and protocol ecosystem. The choice affects supported readers/writers, schema evolution, transactional behavior, and platform features, not merely compression.

Delta integrates the orders workload with Databricks ingestion, change handling, and maintenance. Iceberg offers another protocol ecosystem for supported multi-engine access. Interoperability comprises reader support, writer support, catalog integration, and table-feature versions; a particular engine can support different subsets of those capabilities.

The managed/external choice from chapter 2 establishes lifecycle ownership. The table format establishes transactional behavior: external Delta uses its transaction log, while external CSV exposes serialized files under its supported read and write semantics.

7.3 Transactions and Concurrent Writers

A Delta version describes a consistent snapshot. Commit publishes the transaction's change atomically at its supported boundary. Several independent statements have separate commit boundaries, so readers can observe the first completed operation while a later one is still pending.

For example, an orders update and an audit append are separate unless enclosed by a supported transaction mechanism. Failure between them leaves updated data and a missing audit row. A durable run identifier links their states so reconciliation can complete or repair the intended publication.

Concurrent writes may conflict according to operations, affected data, isolation, and table features. Re-evaluating an update against current state incorporates changes committed since the first attempt. Reusing an earlier overwrite result can instead replace those newer changes.

Schema enforcement checks write compatibility; schema evolution permits supported structural changes. Business validation applies an additional contract: a negative amount can fit a numeric type yet violate an order rule. Consumer compatibility also includes assumptions such as fixed projections.

7.5 Build SCD Type 2 Around Invariants

Suppose customer C42 changes region from North to South at business time 2026-09-10 09:00:00. The intended history is:

C42 North 2026-01-01 00:00:00 2026-09-10 09:00:00

Half-open intervals include the start and exclude the end. At the transition timestamp, exactly the new version matches. A fact-to-dimension lookup becomes:

SELECT fact.order_id, history.region
FROM sales_prod.silver.orders AS fact
JOIN sales_prod.silver.customer_history AS history
  ON fact.customer_id = history.customer_id
 AND fact.order_timestamp >= history.valid_from
 AND (fact.order_timestamp < history.valid_to OR history.valid_to IS NULL);

The lookup relies on nonoverlapping intervals and timestamps with consistent meaning and timezone. A valid history has at most one current version per key, ordered interval endpoints, and defined outcomes for deleted or missing customers. These invariants give each fact the intended historical match.

A deterministic sequence orders changes for each key. Type 1 can retain the latest record in a batch; type 2 retains intermediate transitions as separate intervals. Null-safe comparisons recognize changes between null and a value when those transitions create versions.

A MERGE source row follows the branch selected by its match. A matched row closing the current version takes the matched branch; inserting its successor requires a separate staged action. A later INSERT has a separate failure boundary, and a freshly evaluated current_timestamp() can differ between statements. Stable event identity and time link the two actions.

Supported AUTO CDC manages history from keyed, sequenced changes. A manual implementation stages closing and insertion actions, preserves event identity and time, and coordinates atomicity, replay, and concurrent writes. Correctness is expressed by the resulting interval invariants.

7.6 Persist Operational History When Required

Change-feed capture starts when the feature is enabled. Persisting captured changes into a separate governed table gives that history its own retention window, potentially longer than the source feed's replay window.

A change-history record carries operation type, source table and version, available event identity, commit time, ingestion time, and relevant values. Delete records explain removals; update preimages preserve earlier values; postimages preserve the replacement values.

Temporal history here is explicitly modeled through version rows or captured changes on Databricks. Comparing captured source-version ranges with expected ranges reveals gaps while source retention still allows replay.

7.7 Partitioning, Clustering, and Data Skipping

Physical layout reduces unnecessary reads when it aligns with predicates. Traditional partitioning groups storage by partition-column values. It helps when filters can prune substantial data and each partition contains enough data to justify its overhead. Partitioning by a nearly unique order ID usually creates excessive small groups rather than useful pruning.

Data skipping uses file statistics to exclude files whose values fall outside a predicate, including on unpartitioned Delta tables. For example, a file whose maximum order date precedes the requested range can be skipped. The table's statistics configuration determines which columns support this pruning.

Liquid clustering groups data around selected query keys with flexible layout boundaries. Changing the keys establishes a new organization strategy; optimization performs the physical reorganization and consumes compute. Reorganizing all existing data can require a supported full optimization.

ALTER TABLE sales_prod.silver.orders
CLUSTER BY (customer_id, order_timestamp);

The example requires compatible table features and runtime. customer_id and order_timestamp suit predicates that selectively retrieve customers and time ranges. Automatic key selection is a separate supported feature with its own prerequisites.

Z-ordering colocates values during optimization on compatible Delta tables. It and liquid clustering have distinct compatibility and migration rules. Compaction reduces small-file overhead, clustering improves value locality, and deletion vectors represent row changes efficiently. Each mechanism targets a specific physical cost.

8. Transformations and Data Quality

A transformation turns source records into data satisfying a defined contract. Silver orders can require an event identity, a parseable timestamp, an amount consistent with the refund model, and deterministic handling of repeated or superseded events. Each quality rule combines a predicate with an outcome for records that fail it.

8.1 Profile Before Choosing a Repair

Profiling describes the input through row counts, null rates, key multiplicity, ranges, and distributions. Breaking these measures down by source, batch, or interval exposes localized defects that an overall average can conceal.

SELECT
  COUNT(*) AS total_rows,
  COUNT(*) - COUNT(order_id) AS missing_order_ids,
  COUNT(*) - COUNT(order_total) AS missing_amounts,
  MIN(order_total) AS minimum_amount,
  MAX(order_total) AS maximum_amount
FROM sales_dev.bronze.order_events;

The query assumes typed columns. On raw strings, minimum and maximum follow lexical ordering; on numeric columns, they describe numeric range. Parsing checks establish representability, and range checks establish whether the parsed amount satisfies the business rule.

Exact counts support fixed-batch reconciliation and uniqueness checks over the selected population. Approximate counts trade precision for cheaper exploration. A sample describes only observed records, so rare defects require broader coverage to measure reliably.

8.2 Parse Types Without Concealing Information Loss

Decimal types represent fixed precision and scale; floating-point types use a different representation and rounding model. Required precision depends on both individual values and derived calculations: a yearly sum can need more digits than a single line amount.

String identifiers preserve meaningful formatting such as the leading zeros in 00042. Timestamp interpretation similarly carries meaning: the timezone determines which reporting day contains an event. A timezone shift can therefore change daily revenue while preserving valid timestamp types.

CAST and tolerant conversions such as TRY_CAST implement different error policies. A tolerant conversion returns null for supported conversion failures and lets processing continue. Comparing that result with a present source value identifies a parse failure separately from missing input.

SELECT
  order_id,
  amount_text,
  TRY_CAST(amount_text AS DECIMAL(18,2)) AS order_total,
  amount_text IS NOT NULL
    AND TRY_CAST(amount_text AS DECIMAL(18,2)) IS NULL AS invalid_amount
FROM sales_dev.bronze.raw_orders;

The pattern retains the original string and marks conversion failures separately. A successfully parsed negative amount then enters the business rule that distinguishes refunds from invalid orders.

8.3 Null Semantics and Deterministic Deduplication

SQL predicates evaluate to true, false, or unknown. For null input, amount <> 0 is unknown, so a WHERE filter excludes that row. IS NULL explicitly selects missing values; null-safe equality defines equality including nulls. COUNT(*) counts rows, while COUNT(amount) counts present amounts.

Null represents an unknown amount; zero represents a known amount of zero. Replacing null with zero makes a business assertion and can understate revenue. Retaining the unknown value, quarantining the record, and rule-based imputation express three different acceptance policies.

Deduplication has two parts: a key defines equivalent records, and a survivor rule selects the accepted record. Identical-row removal eliminates repetition; current-state selection orders competing versions. A window with an explicit sequence and tie-breaker implements the latter:

SELECT *
FROM sales_dev.bronze.order_updates
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY order_id
  ORDER BY source_sequence DESC, event_id DESC
) = 1;

The source contract gives source_sequence and event_id their ordering meaning. A randomly generated identifier has arbitrary lexical order. The query produces one current-state candidate per order; SCD type 2 retains intermediate changes through the history mechanism in chapter 7.

Streaming deduplication retains event identity across batches. Watermarks bound supported state using event-time lateness rules, limiting how long earlier events remain recognizable. Events arriving beyond that window follow the application's late-data and correction policy.

8.4 Joins and Set Operations Change Cardinality

A left join preserves each left row and produces one result for every matching right row. Two customer matches therefore double the joined order. An inner join removes unmatched orders; an anti join returns them. Multiplicity and unmatched counts expose these effects on the output contract.

Joining a historical dimension only on customer ID matches all customer versions. The valid-time predicate in chapter 7 selects the version effective at the order time. Preaggregation preserves correctness when its reduced grain still includes the join keys and information needed for the final measure.

SQL UNION removes duplicate rows; UNION ALL preserves them. PySpark union preserves duplicates and aligns by position; unionByName aligns by name. Allowing missing columns fills structural gaps. A compatible projection also aligns types and meaning, such as the units of amounts from different sources.

INTERSECT finds common rows and EXCEPT finds one-sided rows; distinct and ALL variants control duplicate treatment. These compare full projected rows. A business-key join instead pairs entity versions so changed attributes can be compared explicitly.

8.5 Reshaping, Grain, and Units

Flattening a struct exposes nested fields without necessarily changing row count. Exploding an array creates rows and therefore changes grain. Exploding both an order's line items and an unrelated list of discounts can accidentally create a Cartesian multiplication unless the intended relationship is defined.

A pivot turns selected attribute values into columns, normally with aggregation. Explicit categories stabilize the output schema; categories discovered from input can add columns when source values change.

Unpivot turns measure columns into rows labeled by measure name and unit. Those labels preserve meaning after reshaping. Keeping a null measure row records an explicit unknown; omitting it changes the represented population.

Denormalization places frequently used attributes together, reducing repeated joins. Attribute copies then require propagation of corrections from their authoritative source. The tradeoff is simpler reads in exchange for more update coordination.

8.6 Place Each Quality Rule at the Correct Layer

Mechanism Appropriate rule Important boundary
Parsing/schema checks Expected fields and representable values Establishes structural compatibility.
Enforced table constraints Supported write invariants such as NOT NULL or CHECK Rejects writes violating the enforced rule; key constraints can be informational.
Pipeline expectations Row expressions with a chosen violation action Classifies individual records and records the configured outcome.
Aggregate/reconciliation tests Key cardinality, totals, referential completeness, source/target balance Evaluates a defined population and time window.

NOT NULL explicitly rejects missing values. Comparison predicates follow their own null semantics, so presence and value range are distinct rules. Adding an enforced constraint also validates existing data according to the supported operation.

Uniqueness is evaluated over a key population: events, current entities, historical versions, or one batch. A micro-batch can be unique internally while repeating a key loaded yesterday. Cross-batch uniqueness therefore requires access to the relevant retained population or state.

8.7 Expectations and Quarantine

Lakeflow pipeline expectations provide three distinct outcomes:

Action Data outcome Appropriate reason
Warn/default Violating rows continue; quality metrics can be recorded Measure a defect while a downstream consumer tolerates it.
Drop Violating rows are excluded from that output The consumer explicitly accepts omission and omissions are observable.
Fail The affected update/flow fails under the service's semantics Publishing this output with a violation is unacceptable.

Flow failure follows the service's transaction boundary; independent flows can retain completed work. Drop removes rejected rows from an output. Quarantine adds a retained destination for those rows and their failure reasons.

CREATE OR REFRESH STREAMING TABLE valid_order_events (
  CONSTRAINT required_order_id
    EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(sales_dev.bronze.order_events);

This definition runs in a supported pipeline environment with configured namespace and permissions. A missing order_id fails the affected update. Uniqueness, event order, and amount validity are separate expressions or population-level checks.

Quarantine starts from retained raw input and a classified intermediate dataset. Accepted rows enter the validated target; rejected rows enter quarantine with event identity, failed rules, source reference, and run metadata. Explicit handling of null predicate results assigns each row to an outcome.

For a common input population, exclusive and exhaustive routing yields input = accepted + quarantined + explicitly accounted exclusions. This equality measures completeness at the processing boundary. Replay-safe event handling lets corrected quarantine records enter the accepted target once.

8.8 Load the Target According to Its Contract

Append adds records to existing contents. Repeated INSERT INTO can add the same rows again, so replay handling compares event identity with the accepted target or uses a transactional ingestion mechanism. Internal batch deduplication addresses repetition within that batch.

MERGE matches source and target and selects an applicable action. Source-key uniqueness removes ambiguous matches; conditional branch order determines which action wins. Comparing source and target sequence numbers allows a current-state target to reject an older update arriving late.

Overwrite replaces a defined scope. .partitionBy(...) controls layout; an explicit replacement predicate or supported key mechanism defines which existing data is replaced. The incoming data needs to represent the complete intended replacement for that scope.

REPLACE WHERE uses a predicate to define replacement; other supported operations such as REPLACE USING use their documented matching semantics. Runtime and compute support determine which operation is available.

9. Pipelines, Orchestration, and Recovery

A data pipeline has two graphs. The data graph connects datasets to the inputs used to compute them. The operational graph connects tasks such as extraction, validation, export, and publication. Declarative pipelines manage supported dataset dependencies; Lakeflow Jobs coordinates the broader workflow.

9.1 Choose the Appropriate Control Model

Notebook-based processing expresses reads, writes, branches, and external interactions as procedural code. The implementation coordinates ordering, progress, and recovery alongside the underlying engine. This model accommodates heterogeneous operations and existing procedural applications.

Lakeflow Spark Declarative Pipelines defines datasets and flows whose supported dependencies the service resolves. Streaming tables advance incremental processing; materialized views maintain query results. Their update semantics determine how new rows, corrections, and deletions affect the output.

For the orders example, a streaming source can land order events, an AUTO CDC flow can maintain current order state, and a materialized result can compute revenue from that current state. Treating all three as append-only tables would mishandle updates or cancellations unless additional logic repaired the derived results.

Apache Spark Declarative Pipelines supplies an API surface; the managed Databricks service adds supported features such as expectations and CDC capabilities. Runtime and service feature support determine which definitions an environment can execute.

9.2 Definition Evaluation and Side Effects

Dataset definitions describe and return datasets. The engine can evaluate them while discovering and planning the graph, potentially more than once. External mutations placed inside such a function would inherit that evaluation frequency. Operational tasks give notifications and external writes an explicit execution lifecycle instead.

For example, a materialized revenue result could be defined over an already maintained current-state table:

CREATE OR REFRESH MATERIALIZED VIEW daily_revenue
AS SELECT
  CAST(order_timestamp AS DATE) AS order_date,
  SUM(order_total) AS revenue
FROM sales_prod.silver.orders
GROUP BY CAST(order_timestamp AS DATE);

The query assumes source rows already represent revenue-eligible order states in one currency and a defined timezone. Filtering cancellations or converting currencies belongs in the source transformation or this query according to the business contract.

Pipeline configuration binds source definitions to a target namespace, execution identity, compute, and run mode. A dry run checks supported syntax and graph structure. A data-processing run supplies evidence about source access, output correctness, and performance.

9.3 Design a Job as Explicit Dependencies

An orders job extracts data, updates current state, validates quality, refreshes revenue, and publishes completion. The validation task acts as a gate by returning failure when the output contract is violated. Publication depends on successful transformation and validation.

A task consuming another task's output has a serial dependency. Independent sources can run in parallel. Publication combines their completion state with a data condition, such as matching batch identifiers and expected record counts, to establish a coherent output.

Run-if conditions evaluate task states: All succeeded follows successful tasks, All done allows cleanup after completion, and At least one failed routes error handling. If/else evaluates a value, such as an invalid-row count. State conditions and value conditions control different workflow decisions.

Skip, disable, timeout, and failure have distinct effects on downstream conditions. Disabling a task removes its execution from the path; consumers may then see missing or older data if they depend on its output. The graph's conditions determine how that state propagates.

For-each applies a nested task to collection elements. Parallel iterations consume shared capacity, and writes to the same partition or checkpoint introduce coordination dependencies. Useful concurrency comes from iterations with independent state and destinations.

9.4 Parameters and Logical Work Identity

Parameters identify the logical work: target catalog, source, business interval, input version, and stable request ID. A delayed run retains its explicit business interval even when the execution date changes. This makes scheduling time and data time independent.

Task values carry small coordination results such as counts and references. Governed storage carries datasets, with identifiers passed between tasks. Parameter validation constrains values used as paths or SQL identifiers, separating configuration data from executable syntax.

A backfill is the same business transformation applied to an explicit historical interval. Its publication policy determines whether it replaces, reconciles, or extends previously published data.

9.5 Choose Triggers According to Availability

Advanced job schedules use Quartz-style cron with a seconds field and configured timezone. UTC provides a stable elapsed-time basis; a local timezone ties publication to the business clock and follows its daylight-saving transitions.

File-arrival triggers detect supported new-file events. Immutable names give each delivery a new file identity. A multi-file batch needs a separate completeness signal, such as a manifest naming all expected files; overwriting an existing name follows the trigger's specific supported behavior.

Table-update triggers detect changes in monitored tables. Source versions or batch identifiers associate those changes with a common business batch. That association establishes cross-source consistency before publication.

Continuous job scheduling starts another run according to the job's continuous behavior. It differs from a continuously running Spark query and from a declarative pipeline's continuous mode. Supported streaming triggers vary by compute type: the archived material specifically distinguishes bounded AvailableNow jobs on serverless from time-based streaming patterns on other supported compute.

Pausing a trigger stops its future starts. Active runs have a separate cancellation lifecycle, and external callers can have independent run permissions. Maintenance therefore involves trigger state, active-run state, and external submission paths.

9.6 Concurrency and Queues Need an Explicit Policy

A concurrency limit of one serializes runs of that job. Replay safety belongs to the processing logic, and independent jobs retain their own concurrency policies. Table transactions and shared-writer coordination govern their interaction on a common destination.

Queueing preserves pending work only within the platform's supported queue behavior and limits. If arrivals are consistently faster than processing, a queue accumulates delay rather than solving capacity. Measure queue age and consumer freshness in addition to task duration.

Pending work has business meaning: an event archive needs every required interval, while a current-state refresh may coalesce older requests into a newer snapshot. Deployed concurrency and queue settings implement the chosen backlog policy.

9.7 Retry, Repair, and Replay Are Different Operations

A retry repeats a failed attempt according to configured policy. A repair reruns selected failed or affected parts of an existing job run under supported semantics. A full replay reconstructs an input range or whole dataset. Each can encounter side effects left by earlier successful operations.

Idempotency gives repeated attempts of one logical request the intended single effect. Event keys, transactional sinks, bounded replacement, or request tracking can supply it. A stable idempotency key links retries to the same request; a new key describes a new request.

A transient network or capacity failure can clear between attempts. Missing grants, invalid schemas, and deterministic quality violations persist until their configuration or data changes. Failure classification therefore determines whether retry or correction is the useful recovery path.

An attempt timeout bounds one attempt under the task's semantics. Retry count and delays extend the total run budget. A warning-duration threshold emits a notification; timeout or cancellation controls termination. Effective policies include any automatic retry behavior of continuous or serverless workloads.

9.8 Report Failure Through the Execution Contract

Task status follows the execution contract. An unhandled exception or documented failure signal marks failure. Catching an exception and returning normally reports successful completion even when the required output is missing.

dbutils.notebook.exit("FAILED: ...") returns the string as a notebook result. A parent can interpret that value through an explicit protocol. Task failure itself uses the documented failure mechanism, so returned data and execution status are separate channels.

Completion is operation-specific: a notebook can return, a streaming query can remain active, and a table transaction can commit independently. Publication depends on the relevant operation reaching its required terminal outcome.

Notifications identify the owner, job, run, task, affected interval, and diagnostic record. An intermediate retry and exhausted recovery are different operational events. Muting intermediate notices reduces duplication while retaining final failure notification and keeping credentials and row contents out of alerts.

9.9 Recovery Exercise

If failure occurs after the silver commit and before publication, repair can complete the missing publication step. Replaying the full logical batch against an idempotent design preserves the accepted revenue and checkpoint identity while reconciling publication state.

Invalid input follows a correction path; a temporary source outage follows a retry path. The pipeline lab and Jobs lab explore these behaviors. Trigger, task, and concurrency availability depend on workspace and compute capabilities.

10. Testing and Deployment

A reproducible release records code, dependencies, configuration, target objects, and execution identity together. Those components define the environment that produces the data. Declarative Automation Bundles version supported resources alongside code; tests establish how that release behaves on defined inputs.

10.1 Separate Transformation Logic From Interactive State

Source modules make transformation functions independently callable and testable. Notebooks coordinate their inputs, parameters, and results. Explicit initialization recreates the required state on a fresh job run, including state an interactive developer may already have in memory.

Git revisions tie code, contracts, and configuration to a reviewable change. Switching a workspace Git folder's branch changes that folder's contents for its users. Independent working copies separate development changes, while a recorded production revision identifies the exact deployed artifacts.

A merge combines behavioral contracts as well as text. A new transformation paired with an old schema or parameter can remain syntactically valid and produce the wrong output. Focused contract tests exercise that combination.

Synthetic fixtures make tests reviewable without embedding customer records. References to governed data locations keep production values and credentials outside the source-control history; notebook outputs can otherwise copy those values into a commit.

10.4 Understand Bundle Configuration

Declarative Automation Bundles, formerly Databricks Asset Bundles, describe code artifacts and supported Databricks resources. The main databricks.yml declares the bundle and can include resource definitions in separate files. Variables supply deployment-time configuration; targets select environment-specific overrides; resources define jobs, pipelines, and other supported objects.

The following configuration illustrates supported serverless notebook tasks. Its execution prerequisites are the referenced source files, notebook environments, workspace authentication, permissions, and target catalogs.

bundle:
  name: orders_pipeline

variables:
  target_catalog:
    default: sales_dev

resources:
  jobs:
    orders_job:
      name: orders_pipeline
      max_concurrent_runs: 1
      tasks:
        - task_key: transform
          notebook_task:
            notebook_path: ./src/transform.py
            base_parameters:
              target_catalog: ${var.target_catalog}
        - task_key: validate
          depends_on:
            - task_key: transform
          notebook_task:
            notebook_path: ./src/validate.py
            base_parameters:
              target_catalog: ${var.target_catalog}

targets:
  dev:
    default: true
    mode: development
  prod:
    mode: production
    variables:
      target_catalog: sales_prod

depends_on establishes task order; target_catalog selects the namespace. The run identity and its data grants authorize access there. Workspace host, authentication, and resource permissions complete the deployment context.

Development mode applies supported naming and schedule presets for isolated work. Production mode applies production-oriented validation and behavior. Effective target configuration supplies the actual workspace, run identity, permissions, and schedules; test records supply release evidence.

Bundle variables affect deployment-time configuration. Job parameters select run-time work, such as a business day. The same deployed job can therefore process different intervals by receiving different run parameters.

10.6 CI/CD, Concurrency, and Recovery

Promotion applies a reviewed revision to recorded test and production targets. A supported noninteractive identity provides stable automation credentials. Separate deployment and processing identities let resource-management permissions and data-access permissions evolve independently.

Code rollback restores an earlier implementation. Data recovery restores a compatible table version, replays source data, or applies compensating changes. Schema and checkpoint compatibility determine whether restored code can resume against the retained state.

11. Performance and Observability

Performance is the time and resources required to produce a correct result. An optimization changes physical work while preserving the logical contract. End-to-end timing locates delay, runtime metrics identify the limiting resource, and result comparison establishes that the same work was completed.

11.1 Separate Waiting, Startup, Execution, and Freshness

End-to-end delay adds source availability, trigger evaluation, queue time, compute startup, processing, and publication. An hour in the queue remains part of the delay even when Spark executes in seconds. Freshness also depends on source progress: a successful nightly run over unchanged input still publishes old information.

A comparable run record contains input interval and version, run ID, queue/start/end times, output freshness, processed and rejected counts, and code/configuration revision. These dimensions separate a genuine execution improvement from a smaller input or different business interval.

Job and task details describe orchestration. Spark UI exposes supported Spark execution metrics. Query profiles and history cover SQL and supported serverless analysis; pipeline views expose event and quality information. Each compute model defines which infrastructure-level metrics are available.

11.2 Diagnose From the Executed Plan

The executed plan connects a slow task to scans, exchanges, joins, and stages. Task counts, duration distributions, spill, and driver/executor activity show where resources were spent. EXPLAIN describes planned operations; runtime metrics quantify their actual execution.

Observation Candidate cause Discriminating check Possible intervention
Few tasks run while capacity is idle Insufficient useful parallelism or serial work Task count and driver activity Change the data/operation parallelism if semantics permit.
One or a few tasks run much longer Skew, unusually large records, or a slow executor Per-task input and duration distribution Address key distribution or the identified node issue.
High spill in expensive stages Partitions or state too large for available execution memory Per-task spill, memory, and partition sizes Reduce per-task data/state or change memory/partition sizing.
Large shuffle volumes Wide joins, aggregations, or repartitioning Exchange nodes and shuffle read/write Reduce data before the exchange or use a suitable join strategy.
Driver failure with mostly idle executors Driver-side collection or coordination pressure Driver logs and code using collect/toPandas Keep computation distributed or bound returned data.
High elapsed time with little computation Remote source, network, startup, or queue delay Timeline and dependency metrics Fix the relevant boundary rather than adding executors.

The discriminating measurement separates plausible causes. A long task with unusually large input suggests skew; a long task with ordinary input on one troubled executor suggests a node issue. Duration becomes diagnostic when paired with workload distribution and resource behavior.

11.3 Shuffle and Skew

A shuffle brings records together by key for joins or aggregations. It costs serialization, network transfer, disk activity, and coordination. Semantically valid filtering and projection before the exchange reduce the bytes that incur those costs.

Skew occurs when work is unevenly distributed. A very frequent customer key or a large null-key group can make one partition dominate a stage. Doubling worker count may leave the same dominant task running at the end because that task has not been subdivided.

Adaptive Query Execution changes supported plans using runtime information, including some skew and join adjustments. A broadcast sends a small join side to executors, saving a larger redistribution of the other side. Its memory cost depends on the broadcast representation and each executor's available capacity; the final plan shows the chosen strategy.

Salting divides a frequent key into subkeys to distribute its work. A join then needs matching expansion of the other side, and an aggregation needs recombination of partial results. Those steps preserve the original matches and totals while changing the physical distribution.

11.4 Memory Spill and Partition Sizing

Spill moves intermediate data from execution memory to disk. This can let an operation finish with limited memory, at the cost of extra I/O. Spill volume and time quantify that memory-versus-I/O tradeoff.

More shuffle partitions reduce average data per task; very small partitions increase scheduling and metadata overhead. Fewer partitions reduce that overhead and increase the memory demand of each task. Useful partition size balances those two costs against the actual distribution.

Wide rows, multiplied join results, growing streaming state, cache pressure, and skew all increase memory demand. Their remedies differ: correcting a multiplying join reduces the logical data volume, while increasing memory supplies more capacity for a legitimate working set.

Driver and executor memory are separate allocations. collect() or conversion to local pandas transfers distributed results to the driver, making driver memory the limiting resource. Distributed processing keeps the working set on executors; bounded collection limits the returned data.

11.5 Caching Has a Reuse and Capacity Contract

Spark cache/persist retains intermediate results for reuse. Databricks disk caching retains supported file data, while SQL result caching reuses eligible query results. Each has a distinct scope, lifetime, and invalidation rule.

A cache is beneficial when avoided repeated computation exceeds its creation, storage, and maintenance costs. One-time input gets little reuse benefit. Releasing an explicit cache returns capacity; replacing compute can lose warm state and incur a new warm-up cost.

A warm-cache benchmark measures reuse, while a cold run includes initial reading and materialization. The production mix of repeated and new inputs determines which measurement is representative. Data changes can also invalidate previously cached results.

11.6 Table Maintenance and Query Optimization

The layouts in chapter 7 reduce scans when predicates align with statistics and data locality. Declared clustering keys establish a strategy; completed reorganization determines the existing file layout. Bytes and files scanned reveal how useful that layout is to a query.

OPTIMIZE reorganizes eligible files through compaction and supported clustering. VACUUM reclaims obsolete files according to retention. The first changes the physical layout used by reads; the second changes retained history and storage consumption, subject to the recovery window in chapter 5.

Statistics estimate row counts and guide strategy selection. Missing or stale statistics can produce poor estimates; useful file statistics also enable selective skipping. Predictive optimization can schedule supported maintenance, whose history records the work completed and associated cost.

A controlled comparison holds input, result contract, and unrelated settings constant. Changing one candidate cause, such as join strategy, then relates a measured change in shuffle or duration to that intervention. Result equivalence establishes that both runs performed the same logical work.

11.7 From Consumption to Cost

system.billing.usage exposes consumption records. Preserve the SKU and usage unit when aggregating quantities:

SELECT
  usage_date,
  sku_name,
  usage_unit,
  SUM(usage_quantity) AS quantity
FROM system.billing.usage
WHERE usage_date >= CURRENT_DATE() - INTERVAL 7 DAYS
GROUP BY usage_date, sku_name, usage_unit;

The query reports consumption separately by SKU and unit. Monetary cost applies the relevant dated price and discounts to each quantity, then includes applicable additional cloud charges. Keeping units separate preserves the dimensions needed for that calculation.

Supported job, workspace, identity, and tag metadata attributes consumption to workloads. A run can have multiple usage records and billing corrections. Joins to historical cluster metadata use both keys and time validity to associate each quantity with the correct version exactly once.

Cost per validated batch combines unit price, duration, retries, and relevant idle infrastructure or pools. A cheaper minute can still produce a more expensive batch when execution takes longer. Budgets and threshold notifications provide visibility; enforced resource limits or shutdown automation are separate controls.

11.8 Azure Monitor and Log Analytics

Azure diagnostic settings route selected workspace log categories to Log Analytics, storage, or Event Hubs. Resource, category, destination, permissions, and retention define the delivery path. Account, workspace, engine, and application logs each have their supported collection arrangements.

Destination schemas depend on the selected diagnostic layout. Structured status and response fields express the operation outcome. For example, error_message: null can occur in a successful response, so an alert evaluates the field's value and documented status rather than a text match on its name.

A failed job-creation request concerns configuration; a failed transformation concerns data execution. Action type, run/task IDs, and terminal outcome identify which event occurred and which owner can address it.

A scheduled-query alert evaluates a defined population within a time window, compares it with a threshold, and routes an action at a configured frequency. The window accounts for ingestion delay. Missing-completion or stalled-freshness conditions detect silence, including a schedule that never starts.

Log Analytics delivery is asynchronous. A known event and its identifiers provide a reference for measuring delivery delay and confirming the collection path. That baseline helps distinguish genuine inactivity from missing or delayed telemetry.

11.9 Diagnose Before Restarting

Run, query, stage, and error records capture the failing state. Restarting recreates the execution environment and clears some interactive state. Deterministic cast errors, missing grants, and wrong joins persist until their data, permissions, or code changes.

A representative verification includes the data or scale that triggered the failure. The focused case tests the proposed cause; the full affected interval tests recovery and output consistency. An empty batch exercises a different workload.

The monitoring lab requires suitable monitoring permissions. Azure Monitor delivery needs Azure resources, and classic compute metrics cannot be assumed available in Free Edition. No cost or performance improvement in this chapter is presented as a measured result of these unexecuted exercises.

12.2 Power BI: Choose Freshness and Identity Deliberately

Import mode copies data into a Power BI semantic model. Unity Catalog authorizes extraction under the connection identity. Report queries then use that copy under Power BI's access controls until refresh. The copy reduces repeated source queries and acquires its own security and freshness lifecycle.

DirectQuery sends supported queries to Databricks, commonly through a SQL warehouse. Responses depend on connectivity, warehouse availability, concurrency, and query latency. Cache and application behavior also contribute to the freshness observed in the report.

A fixed service principal or token gives Databricks one connection identity to authorize. Supported identity passthrough or SSO can instead propagate individual users. The token flow and published configuration determine which principal's grants are evaluated for each query.

The server hostname and HTTP path select the compute endpoint; catalog and schema select the namespace; authentication selects the principal. Power BI Desktop and the published service can have separate credentials and network routes, giving them distinct connection behavior.

A private workspace requires a supported gateway or network route from the published service. The developer laptop uses its own route. Connector and driver versions also affect query folding, type mapping, and semantic-model behavior, making those properties part of integration compatibility.

Databricks-to-Power BI publishing can transfer supported descriptions and relationships into a semantic model. Informational foreign keys supply relationship metadata; data validation establishes the actual cardinality and references. The publishing feature has its own capacity, XMLA, tenant, and permission requirements.

An Import refresh depends on completed upstream publication and establishes a new model version when it finishes. Its terminal outcome and observed data version identify what the report serves. DirectQuery instead follows the current query path and its effective security context.

12.3 Fabric: Metadata, Shortcuts, and Data Access

A Mirrored Azure Databricks Catalog exposes supported metadata and creates OneLake shortcuts to supported tables. This provides access to referenced data. Traditional database mirroring instead maintains a separate replica from source changes; the integration type determines where the data resides.

The archived Fabric integration uses the configured connection identity for source access and Fabric controls for downstream users. Per-user Unity Catalog masks and filters belong to query paths that evaluate that user's identity. Shortcut access and downstream Fabric authorization therefore form a distinct security path.

Connector support includes table types, external-access privileges, networking, and OneLake security. Data protected by viewer-specific Unity Catalog policies needs a query path preserving that evaluation. A separately approved dataset can instead establish a new disclosure boundary protected by Fabric controls.

Writing curated data into OneLake creates a new publication boundary defined by lakehouse location, authentication, format, visibility, and permissions. Files placed in the Files area are stored objects. Table registration and engine compatibility determine how a Fabric engine exposes them as tables.

Multi-engine access depends on support for the table protocol, enabled features, metadata changes, and writer concurrency. A shared path exposes the same bytes, while each engine retains its own compatibility requirements. Referenced-data access also consumes compute and can incur capacity, network, or egress charges.

12.4 Power Platform: Distinguish User Access From Automation

Power Apps and Power Automate can use supported Databricks connector operations such as SQL access or job orchestration. A user-facing app, a background flow, and a service-principal connection can have different effective identities even when configured from the same environment.

An orders app can expose a common approved dataset or user-specific subsets. Calls under one service principal use that principal's Databricks permissions. Any additional per-user restriction is enforced in a supported application, connector, or data-access layer.

Delegation moves supported filters and aggregations to the data engine, where they cover the source population. A client-side filter over a capped retrieved subset covers only those returned rows. The distinction becomes visible when the source exceeds the retrieval limit.

Each connector defines licensing, rate limits, supported clouds, connection modes, and virtual-table capabilities. Batching reduces request overhead; rate-aware retries respect throttling; replay-safe writes preserve the intended result when requests repeat.

12.5 Purview: Discovery and Lineage

Microsoft Purview can register and scan supported Databricks metadata so assets appear alongside other enterprise data sources. Scan capabilities differ between legacy Hive metastore and Unity Catalog integrations and between supported network/authentication arrangements.

Purview makes supported asset metadata discoverable. Unity Catalog evaluates data grants when a query runs. Classification supplies metadata that an enforcement policy can consume; discovering, classifying, and authorizing a table are separate operations.

Lineage coverage depends on supported execution paths, tools, and transformations. A known transformation provides a reference for measuring capture and metadata freshness. Scanner permissions determine the metadata made available to discovery consumers.

Scanner features can require different scopes: metadata discovery reads supported metadata, while some classification features require access to values. The selected connector and feature define the scanning identity's required access.

12.6 VS Code and Databricks Connect

The VS Code extension connects local development to a remote workspace. File synchronization transfers artifacts; remote job execution starts a workload; Databricks Connect submits Spark operations from a local client. Each has its own execution boundary.

Databricks Connect builds Spark operations in a local client and executes them on remote compute. Local Python control flow and breakpoints describe client execution; distributed executor activity is observed through the remote execution tools.

Client/runtime compatibility and dependency placement determine execution. Local orchestration imports libraries from the client environment; remote operations use their supported remote environment. A dependency used on both sides may require compatible installation in each.

One-way synchronization copies local changes to the workspace. Remote edits have a separate lifecycle from the local Git repository. Reviewed Git revisions and the bundle workflow in chapter 10 establish the authoritative artifacts for release.

12.7 Genie and the Analytical Data Model

A Genie space interprets questions within an analytical context over selected governed data. Grain, relationships, descriptions, sample queries, and business definitions connect the user's terms to valid SQL operations. The selected objects define the question set the space can answer coherently.

Revenue meaning comes from included statuses, cancellations and refunds, currency conversion, date, and timezone. Historical customer attributes add a valid-time relationship. These definitions determine which executable SQL query computes the requested business quantity.

Table and column descriptions express meaning. Join relationships express valid combinations. Reusable SQL expressions define measures and filters. Example questions and SQL connect phrasing to query patterns. General instructions supply remaining conventions or ambiguity rules.

Prompt/entity matching links user terms to stored values, such as a region name to its code. Representative values support that mapping and have a freshness and disclosure scope. Presentation settings select visible context; data authorization governs actual access.

Benchmark questions associate expected interpretations with outputs. Ambiguity, empty results, duplicate-sensitive joins, historical dates, and unauthorized requests exercise distinct behaviors. Correct values, successful execution, and enforced permissions are separate measurable outcomes.

For example, "revenue last month by customer region" can mean current region or the region at order time. A current-dimension join implements the first; a valid-time join implements the second. An agreed convention or clarification selects the intended calculation.

12.8 Copilot Studio and Microsoft Foundry

The archived integrations expose tables or Genie spaces as tools, including managed MCP paths. A table lookup retrieves rows through structured criteria; natural-language-to-SQL translates a question into a query; semantic retrieval finds content by meaning. Tool choice determines the operation behind a natural-language request.

A Genie tool receives a question, interprets it against its analytical context, and returns a result that the calling application can summarize. Recorded query and result provenance connect the final answer to its computation through both interpretation stages.

Identity propagation follows the connector and token flow. Supported user propagation lets Databricks evaluate the user; a fixed application credential produces application-level access. MCP standardizes tool interaction, while authentication and authorization are supplied by the integration's security configuration.

An integration's contract includes release status, supported warehouses, networking, rate limits, and conversation state. With independent calls, a follow-up such as "and for the previous quarter?" requires the caller to include enough authorized context to resolve the earlier metric and period.

These consumers depend on a data-engineering contract of accurate, authorized, fresh, and traceable access to the intended analytical data.

12.9 End-to-End Acceptance Scenario

BI and Genie can consume the same approved revenue dataset through different paths. A known monthly total provides a reference for their results; source version and revenue definition explain agreement. An authorized identity and a rejected unauthorized identity establish the access boundary for each path.

A source correction propagates through refresh or live querying according to the connection mode. Revocation closes the applicable access path, while previously copied data follows downstream controls. Correctness and security thus depend on both the producing pipeline and the consumer's data lifecycle.

The scenario describes an acceptance design. Power BI, Fabric, Power Platform, Purview, and Foundry have separate licensing, capacity, resource, and permission requirements for its execution.

Databricks Free Edition advertises free Academy self-paced training and links to the free training catalog. Course access, hosted labs, instructor-led delivery, and exams have their own pricing and eligibility conditions.

The Academy login page provides separate routes for customers and prospects, partners, and Microsoft employees. The appropriate portal can depend on the learner's affiliation. No account was accessed during this research.

Free Edition is a practice environment, not a course. The getting-started documentation describes a serverless-only, quota-limited environment and states that it replaced Community Edition, retired in 2025. It supports learning exercises with notebooks, SQL, and Lakeflow, but is not a substitute for a full Azure Databricks environment.

The documented limitations include no custom compute configurations, no R or Scala, no custom workspace storage locations, no account console or account-level APIs, no private networking configuration, and no SSO or SCIM. Usage quotas can suspend compute until the relevant limit resets. These restrictions determine which labs can run there; account eligibility and actual execution remain untested.

Exercises fall into three environment groups: Free Edition-compatible, full-workspace-required, and Azure-specific. Identity, storage, and networking concepts remain relevant across the course, with practical demonstrations using the appropriate environment. Free Edition and time-limited trials have separate usage and access terms.
