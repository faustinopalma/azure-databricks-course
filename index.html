1. Architecture and Execution

Azure Databricks separates the environment in which people develop work, the compute that executes that work, the storage that persists data, and the governance that authorizes access. These components interact, but they are not interchangeable. A notebook can exist without running compute; a table can outlive the compute that wrote it; access to a workspace does not by itself grant access to every table.

1.1 Follow One Workload

Suppose an order system writes JSON files to cloud storage. A data engineering workload reads new files, validates order identifiers and amounts, updates analytical tables, and publishes daily revenue. Five responsibilities must be assigned:

Responsibility Component in this example What it does not establish
Store source files and table data Cloud object storage Files alone do not provide a table's transaction semantics.
Execute reads and transformations Databricks compute Compute access does not imply authorization to read the source.
Register tables and govern their use Unity Catalog Registering a path does not make network access possible.
Define processing logic SQL, Python, or declarative pipeline definitions A saved definition does not automatically run.
Schedule work and handle task dependencies Lakeflow Jobs A successful task state does not prove the data is correct.

An ingestion failure can therefore have different causes: an unreachable storage endpoint, insufficient storage authorization, missing Unity Catalog privileges, incompatible compute, or invalid input. Increasing cluster size addresses none of the first three. The architectural model gives you a way to classify the failure before changing a configuration.

1.2 Account, Workspace, and Metastore

A Databricks account is the organizational management scope for workspaces and account-level identities and configuration. It is not the same thing as an Azure subscription. The subscription contains Azure resources and has its own resource-management authorization model.

A workspace is the development and execution environment containing notebooks, workspace files, jobs, dashboards, and compute configurations. Separate development and production workspaces reduce accidental operational interference, but workspace separation is not automatically data isolation.

A Unity Catalog metastore contains metadata and governance information for registered assets. A workspace attaches to one metastore at a time, and multiple workspaces can attach to the same regional metastore. This allows the same catalog objects to be used from different workspaces, subject to permissions and any workspace bindings that restrict their availability.

For example, if the development and production workspaces share a metastore, sales_prod.gold.daily_revenue refers to the same registered object from either workspace. A naming convention does not prevent a development user from writing to it. Isolation depends on grants, execution identities, workspace bindings where applicable, and storage/network controls, not on the string prod in a name.

Unity Catalog names data objects using catalog.schema.object. A catalog provides a high-level organizational boundary, a schema groups related objects within it, and the final name identifies a table, view, function, or volume. The metastore is above this namespace; it is not a fourth component of the SQL table name.

Legacy Hive metastore objects may appear through hive_metastore.schema.table. Their presence in a workspace does not mean they have acquired all Unity Catalog governance properties. Migration must be treated as a change in the metadata and authorization model, not just a rename.

1.3 Control Plane and Compute Plane

The control plane contains managed services such as workspace interfaces, scheduling, orchestration, and resource-management coordination. The compute plane executes data-processing workloads. This describes responsibilities; it is not a claim that no user information, results, or operational metadata can ever pass through a control-plane service.

In the classic compute model, compute resources run in the customer's Azure subscription. You select runtime and instance configurations and have access to networking options associated with that deployment model. Databricks still manages significant parts of the service: classic does not mean a Spark cluster that you administer independently of Databricks.

In the serverless compute model, Databricks manages compute infrastructure in its service-managed environment rather than provisioning those worker virtual machines in your subscription. You select a supported workload and configure the exposed controls, not individual worker hosts. Feature and network options differ from classic compute and must be checked for the workload and region in question.

Do not infer the compute plane from the age or name of a workspace. A workspace can offer multiple compute choices, and different tasks can use different choices. Ask where the specific workload runs, which identity it uses, and how that compute reaches each dependency.

1.4 Storage Is Independent of Running Compute

Stopping a cluster does not delete a persisted Delta table. Compute reads and writes data in durable storage; it does not need to remain running to keep that data alive. Conversely, a Python variable or a cached DataFrame is not durable storage. It belongs to a running execution context and must be reconstructed when that context disappears.

Workspace storage and analytical data storage also serve different purposes. Workspace assets and system-generated artifacts include notebook files, revisions, results, and operational information. Business tables and governed files are organized through Unity Catalog storage arrangements. The exact physical provisioning depends on the workspace and storage model.

This distinction matters for recovery. Recovering the source code of an orders notebook does not recover deleted source files. Restoring table data does not recover an uncommitted notebook edit. Protect code, durable data, and operational state according to their separate lifecycles.

The older DBFS root and mount patterns should not be the default architecture for new governed workloads. Use tables for tabular data and Unity Catalog volumes for governed file access. A notebook path, a volume path, and a cloud storage URI identify different kinds of resources even when all three are represented as strings.

1.5 Understand What Executes

A notebook is a code and narrative artifact, not a compute engine. Its supported languages and APIs depend on the attached execution environment. A notebook containing a Scala cell does not prove that the selected serverless environment can execute that cell.

Apache Spark distributes work across an execution environment. In a conventional multi-node cluster, the driver coordinates execution and executors perform tasks on partitions of data. A partition is a unit of distributed processing, not necessarily a storage directory. A large table split into many files does not guarantee that every subsequent computation has a balanced partition distribution.

DataFrame transformations normally construct a plan rather than immediately process every row. An action, such as writing a result or collecting it, causes execution. This is why a transformation may appear to succeed while a subsequent write fails: the read, conversion, or join may not have executed yet.

Lazy execution also means that a short source expression is not necessarily inexpensive. A join can require reading large datasets and redistributing records between executors. Conversely, the optimizer may push filters into reads and avoid materializing intermediate results. Diagnose the executed plan and task metrics, not the number of lines in a notebook.

Avoid confusing two uses of the word job. A Lakeflow Job is an orchestrated workflow containing tasks. A Spark job is an execution unit created inside a Spark application, often in response to an action. One Lakeflow notebook task can produce multiple Spark jobs and stages. Their monitoring views answer different questions.

1.6 The Platform Components in Context

Delta Lake supplies table transaction and metadata mechanisms over data files. Unity Catalog registers and governs assets. Spark and Databricks execution engines process queries. Databricks SQL exposes SQL-oriented execution and analytical tooling, typically through SQL warehouses. None is a synonym for the others.

Lakeflow Connect addresses ingestion through supported connectors. Lakeflow Spark Declarative Pipelines lets you describe datasets and their relationships so the service can manage their processing. Lakeflow Jobs orchestrates tasks and dependencies, including notebooks and pipeline updates. A workflow can use all three: ingest customer changes, update derived datasets, and then run a downstream validation task.

Machine learning features such as MLflow coexist with this data engineering environment. Their relevance here is the data contract: training and serving depend on governed, reproducible inputs. This course does not add a separate machine learning curriculum merely because the platform supports it.

1.7 Reason Through the Boundaries

Consider three observations about the orders pipeline:

  1. A developer can open the notebook but receives an authorization error when reading sales_prod.bronze.orders. Workspace access and object access are separate. Inspect the execution principal and data privileges before changing the notebook's folder permissions.
  2. Yesterday's result disappears after a compute restart because it existed only as a temporary view or cached DataFrame. The recovery problem is missing persistence, not a damaged Unity Catalog table.
  3. A scheduled run succeeds under a service principal while an interactive run fails for the developer. The code can be identical while authorization differs. Compare identities and grants instead of assuming the two runs use the same security context.

These are conceptual exercises and require no cloud resources. For practical orientation, use the archived Explore Azure Databricks exercise. Its original setup may require Azure resources; creating them can incur charges.

2. Storage and Unity Catalog Objects

Choose a storage design by deciding who owns the data lifecycle, which systems must access the bytes, and which object should expose them. "Managed", "external", "Delta", and "volume" answer different questions. A managed table and an external table can both use Delta Lake; a volume can contain Parquet files without being a table.

2.1 Establish the Namespace Before Loading Data

For the orders workload, use environment-specific catalogs such as sales_dev and sales_prod, with bronze, silver, and gold schemas. Bronze preserves source-level information, silver applies agreed data contracts, and gold publishes business-level datasets. These layers are processing responsibilities, not automatic platform behavior: creating a schema named silver does not validate anything written into it.

CREATE CATALOG IF NOT EXISTS sales_dev;
CREATE SCHEMA IF NOT EXISTS sales_dev.bronze;
CREATE SCHEMA IF NOT EXISTS sales_dev.silver;
CREATE SCHEMA IF NOT EXISTS sales_dev.gold;

This example assumes the workspace has an appropriate managed storage configuration and the executing principal can create these objects. In an environment requiring explicit managed storage, catalog creation must include the approved storage arrangement. IF NOT EXISTS avoids a duplicate-object error; it does not verify that an existing object's owner, location, or permissions are correct.

Use fully qualified object names in production code. A statement that writes to orders depends on the session's current catalog and schema; sales_prod.silver.orders makes the destination explicit. Parameterize environment selection during deployment rather than relying on an interactive session's last USE statement.

Naming conventions should make ownership, environment, and purpose identifiable. They do not enforce access. Avoid encoding changing state such as final_v7 in a production table name: preserve a stable interface and record versions, descriptions, and lifecycle state in metadata or version control. Unity Catalog normalizes object naming in ways that make case-only distinctions unsafe; check identifier restrictions before generating names from external business labels.

2.2 Managed Storage Resolution

For customer-configured managed storage, Unity Catalog determines the managed location from the most specific applicable setting: schema, then catalog, then metastore fallback. Configuring storage at catalog scope often aligns physical placement with a data domain or environment. A schema-specific location provides a narrower placement rule when required.

The configured storage root is not a table directory that users should construct themselves. Unity Catalog creates and manages object-specific locations beneath its storage arrangement. Do not point a second external table at an internal managed-table directory or manually reorganize those files. You would create overlapping ownership and bypass the mechanism responsible for table metadata and lifecycle.

Storage placement and privilege inheritance are independent. A schema using a particular storage root does not inherit Azure permissions merely because its name matches a storage container. The platform still needs an authorized storage identity, and users still need object privileges.

Default storage is a separate service-managed option. In the archived course, catalogs using default storage require serverless compute, and creation of these catalogs is associated with serverless workspaces. Do not generalize that into a statement that all managed tables require serverless: managed tables can use customer cloud storage in other supported configurations. Check current default-storage availability and access rules before choosing it for a workload that needs classic compute or direct file access.

2.3 Managed Versus External Tables

Decision Managed table External table
Who manages table metadata? Unity Catalog Unity Catalog
Who controls the underlying data lifecycle? Databricks manages it with the table The external storage owner retains responsibility
How is the location selected? The applicable managed storage configuration An explicit registered external location/path
What does dropping the object mean? Metadata removal and managed data deletion according to the supported recovery/lifecycle rules Registration removed; underlying files retained
Why choose it? Databricks is the primary data manager and supported automated maintenance is useful Existing or independently managed data must remain at a controlled external location

Managed does not mean "metadata only in Databricks and no cloud files". External does not mean "ungoverned". An external table is governed when accessed through Unity Catalog, but a principal with direct cloud access may read or modify the underlying files outside that authorization path. The storage permission design must prevent unintended bypass.

A managed-table example is deliberately small:

CREATE TABLE sales_dev.silver.orders (
  order_id BIGINT NOT NULL,
  customer_id BIGINT,
  order_total DECIMAL(18,2),
  order_timestamp TIMESTAMP
) USING DELTA;

No LOCATION is specified, so the example relies on managed storage. An external Delta table instead registers an approved data path:

CREATE TABLE sales_dev.bronze.orders_external
USING DELTA
LOCATION 'abfss://landing@examplestorage.dfs.core.windows.net/orders_delta/';

The URI is illustrative. A suitable storage credential, external location, privileges, and network path must already exist. USING DELTA expects a valid Delta table at that location; it does not convert arbitrary JSON files into a transactional table.

Do not use DROP TABLE as a casual method of refreshing data. For a managed table it has lifecycle consequences; for an external table it leaves files behind. Where supported, CREATE OR REPLACE TABLE replaces the table definition/data under documented semantics and can preserve important table metadata better than a drop-and-create sequence. Evaluate dependencies, permissions, properties, and history before replacing a production object.

2.4 Files Belong in Volumes When the Interface Is File-Based

A Unity Catalog volume governs files using an object at catalog.schema.volume. It is appropriate for landing files, document collections, model artifacts, and other workflows that need paths rather than relational table access. "Non-tabular" describes the interface, not a ban on CSV or Parquet files.

CREATE VOLUME IF NOT EXISTS sales_dev.bronze.order_files;

Files are addressed through /Volumes/sales_dev/bronze/order_files/.... The volume name is a catalog object; the trailing directories are file paths inside that object. Volumes do not provide independent Unity Catalog permissions for each subdirectory. If invoices and public product images need different access boundaries, use different volumes rather than expecting a folder name to enforce isolation.

Managed volumes use managed storage and managed deletion behavior. External volumes register independently managed paths and leave the underlying files when the volume is dropped. Do not assume a table recovery command or table retention window applies to volumes. Check each object's documented deletion and recovery behavior before deleting it.

A storage credential represents the identity used to access cloud storage. An external location associates a path with that credential and a governable boundary. An external table or volume is then created within an appropriate location. These are three different objects: identity, authorized path, and data interface.

2.5 Tables, Views, Materialized Views, and Streaming Tables

A standard view stores a query definition, not a separate persisted result dataset. It is useful for stable projections, reusable business logic, or a governed interface. Querying a view still executes its logical computation against underlying data. Hiding a complicated query behind a short view name does not remove its execution cost.

A materialized view persists the result of a query and maintains it through refreshes. It trades refresh work and storage for less repeated read-time computation. The important question is not simply whether it is faster, but whether its freshness and maintenance behavior fit the consumer's contract. A dashboard allowed to lag by an hour can use a different refresh policy from a fraud response system.

Incremental refresh is an execution capability, not a universal promise for every query. Source features, query shape, and service decisions affect whether a refresh can be incremental or must recompute more data. Check eligibility and actual refresh behavior. Do not assume that enabling one source-table property makes every materialized view incremental.

A streaming table maintains data through incremental processing of a source. Normal refreshes use streaming progress rather than rerunning an arbitrary batch query over every historical source row. If an old source record changes, you need an explicit change-processing design; an append-only stream should not be assumed to repair historical results automatically. Later chapters address CDC, checkpoints, and refresh/recovery decisions.

The underlying persisted storage does not determine the authoring interface. Materialized views and streaming tables are declaratively maintained objects; manually appending to them as though they were ordinary unmanaged result tables can violate the intended lifecycle.

2.6 Foreign Catalogs Are Not External Tables

A foreign catalog exposes supported external-system metadata through a Unity Catalog connection. In query federation, a query can push supported operations into the remote database and retrieve results without first replicating all source data into local tables.

An external table, by contrast, normally registers files at a cloud storage path. Both are "external" in everyday language, but they have different dependencies. A federated query depends on the remote database's availability, credentials, network reachability, execution capacity, and supported pushdown operations. Registering a foreign catalog does not eliminate those dependencies.

Choose federation for exploratory access, limited cross-system queries, or transitions where replication is unnecessary. Choose ingestion when you need a durable local analytical history, predictable processing independent of source availability, or workloads that would impose unacceptable load on an operational database.

A connection and a foreign catalog are also distinct. The connection describes how the remote system is reached and authenticated; the catalog exposes a selected remote namespace. Granting a user access to the catalog should not require giving that user the connection's underlying password.

2.7 Check the Design

For our orders system, the source team owns the incoming files, Databricks owns validated analytical tables, and analysts need a daily summary. A reasonable design is an external landing volume when the files already live in independently managed storage, managed silver/gold tables for Databricks-owned outputs, and a view or materialized view chosen according to query cost and freshness requirements.

Test the design with deletion and access questions before testing performance. If the ingestion registration is removed, should raw files remain? Who can read them outside Databricks? If compute stops, which results persist? If a new workspace attaches to the same metastore, which objects should it be able to use? These answers determine the object types and controls.

The catalog objects lab provides hands-on work. Basic managed objects may fit a supported learning workspace; external storage, connections, and specific refresh capabilities require their own prerequisites.

3. Compute Selection and Configuration

Select compute by compatibility first, execution pattern second, and measured cost/performance third. A low-cost configuration that cannot enforce the required data controls or load the required libraries is not a candidate. Once compatible options are identified, compare complete workload cost, including startup, execution, idle time, and retries.

3.1 Separate the Selection Axes

Compute terminology combines several independent choices:

Axis Question Examples
Infrastructure management Who manages the execution infrastructure and its configuration? Serverless or classic
Workload interface What kind of work is submitted? Notebooks, job tasks, SQL queries, declarative pipeline updates
Access mode on applicable classic compute How are identities and workloads isolated? Standard or dedicated
Resource shape What execution resources are available? Single-node or multi-node, worker family, memory/core ratio
Lifecycle How long does compute exist? Interactive session, job-associated compute, warehouse lifecycle

"Job compute" is not a third infrastructure plane alongside classic and serverless. "Dedicated" is not a synonym for a production job. Keeping these axes separate prevents misleading comparisons between choices that can coexist.

3.2 Match the Workload

Serverless is a suitable first candidate when the workload's APIs, libraries, identity requirements, and connectivity are supported. It removes worker provisioning and much infrastructure configuration. That does not remove the need to manage data size, inefficient queries, dependencies, or budgets.

Classic compute remains relevant when a workload needs controls or APIs unavailable in the applicable serverless environment. Examples can include particular runtime selection, initialization requirements, specialized hardware, or execution APIs. Check the current compatibility matrix for the exact workload, rather than treating every historical serverless limitation as permanent.

A SQL warehouse serves SQL-oriented workloads and BI clients. Serverless, pro, and classic warehouse options differ in infrastructure management and execution capabilities. A Python notebook requiring arbitrary Python execution is not interchangeable with a SQL query simply because both read the same tables.

For production jobs, prefer a lifecycle tied to the workload when feasible. Sharing a long-lived interactive cluster with production tasks introduces competing sessions, mutable dependencies, and unrelated restarts. A job-associated environment reduces those dependencies, although startup time and repeated initialization remain costs.

Serverless performance modes illustrate why blanket startup claims are unreliable. A performance-optimized mode prioritizes startup latency; a standard mode can trade slower startup for lower consumption. Evaluate the selected mode and workload, not a platform-wide promise of "starts in seconds".

3.3 Access Mode Is a Security and Compatibility Decision

Standard access mode supports multiple users with isolation appropriate to supported workloads. Dedicated mode assigns compute to a user or, in supported configurations, a group. The selection affects available APIs and how identity is applied. Do not reuse a legacy no-isolation shared configuration merely because it allows a package to run.

Group-dedicated compute deserves particular care. Work performed in the group's execution context must be designed around the group's permissions and ownership semantics, not a union of every member's personal privileges. A user who can read an additional table in another context should not assume that privilege carries into the group workload.

Language support belongs in the compatibility check. The archived compute unit both excludes Scala notebooks from serverless and later broadly lists Scala among workloads that can run on serverless. Those statements are not sufficient to choose an environment. Determine whether the code is a notebook, a task type, or a library, and consult the current feature-specific documentation. This course does not resolve that contradiction by silently repeating the broader statement.

3.4 Size for the Limiting Resource

Executor cores provide task execution capacity. Memory supports joins, aggregations, state, and caching. Local disk supports intermediate spill, shuffle, and some caching. The driver has separate responsibilities and can fail even when executors have free memory, particularly if application code collects too much data to the driver.

Adding workers can help when there are enough independent tasks and the bottleneck is executor capacity. It does not split a single oversized Python object on the driver, repair a skewed key distribution, or accelerate a throttled source database. First identify whether the limiting factor is CPU, memory, storage I/O, network movement, source capacity, or task imbalance.

Equal total cores and memory do not make two cluster shapes operationally identical. More nodes change network topology, failure domains, and per-node overhead; fewer larger nodes change memory concentration and local resource contention. Do not claim that more smaller nodes inherently provide more task parallelism when the total available cores are the same. Measure the workload under controlled input and concurrency.

A single-node environment can be appropriate for small or non-distributed work. It cannot distribute work over additional machines. A large cluster can cost more and run slower for a small dataset if startup and coordination dominate the computation.

3.5 Autoscaling, Pools, and Termination

Autoscaling changes resource count within configured bounds. It can absorb varying task demand, but it is not instantaneous and cannot fix every partitioning or stateful-streaming problem. A maximum that is too low caps capacity; a minimum that is too high preserves idle cost. Confirm how the selected compute type scales and what is supported for the workload.

An instance pool holds reusable virtual machine instances for classic compute. It reduces repeated provisioning delay by paying for warm infrastructure. Idle pool instances can still incur Azure VM costs even when they are not consuming Databricks processing units. A pool's maximum capacity is a resource boundary, not a guarantee that every request will fit.

Size a pool from expected simultaneous cluster instances, including drivers and workers, rather than the number of notebooks. Several notebooks may share one cluster; one notebook may need many workers. The source course's simple notebook-to-instance example should not be used as a sizing formula.

Automatic termination controls idle interactive compute. Job-associated compute normally follows the job's lifecycle. Pool idle termination controls a third lifecycle, so terminating a cluster does not necessarily remove the minimum warm instances retained by its pool.

Spot workers can reduce acquisition cost but may be reclaimed. They are suitable only when recomputation and interruptions fit the workload's reliability requirements. Protecting the driver and enabling supported decommissioning can reduce risk, but neither turns interruptible capacity into guaranteed capacity. Compare savings against delay and retry costs.

3.6 Runtime, Photon, and Libraries

Databricks Runtime determines the Spark version and packaged execution environment on applicable classic compute. Use a supported version and verify the features your workload needs. LTS is a support-lifecycle choice, not proof that every dependency is compatible. Upgrades need representative correctness and performance tests.

Photon accelerates supported SQL and DataFrame execution using a native execution engine. It is not a general accelerator for arbitrary Python code. If a workload spends most of its time in unsupported operations, network waits, or driver-side logic, enabling Photon may not address the bottleneck. Inspect actual execution and cost before treating the setting as an optimization result.

Machine learning runtimes package ML-related dependencies and support specific execution patterns. Choose them when those capabilities are required, not simply because the dataset will eventually be consumed by an ML team.

Dependency scope determines reproducibility and blast radius:

Scope Consequence Appropriate use
Notebook/session dependency Limited to the supported session environment Exploration with explicit versions
Job/task dependency Declared with the workload Repeatable production execution
Compute-scoped dependency Affects workloads sharing the cluster; installation is reapplied at startup Intentionally shared environment
Initialization script Executes startup configuration and can prevent startup if it fails Required system configuration not handled by normal library mechanisms

Pin production dependencies and record their provenance. A manually repaired interactive session is not a reproducible deployment. Avoid initialization scripts for ordinary Python library installation when a supported dependency mechanism exists.

For standard access mode, approval requirements apply to relevant JARs, Maven coordinates, and initialization scripts. Approval and file-read permission are separate: allowlisting a path does not grant READ VOLUME on its containing volume. Likewise, CAN MANAGE on compute does not automatically grant access to every package location.

3.7 Compute Permissions and Entitlements

For applicable classic compute, CAN ATTACH TO permits workload attachment, CAN RESTART adds lifecycle operations, and CAN MANAGE adds configuration and permission management. These are workspace object permissions, not Azure roles and not Unity Catalog data grants.

A workspace entitlement controls capabilities such as unrestricted cluster creation. A compute policy can constrain allowed configurations. Give a production job permission to use the required compute and data; do not give every developer unrestricted creation merely to solve a single configuration request.

Treat driver logs as potentially sensitive. Secret redaction is not a guarantee that arbitrary derived values or library output cannot reveal information. Restrict log access and avoid printing credentials in the first place.

3.8 Apply the Decision

For a daily orders transformation using supported SQL/Python operations, compare a supported serverless job configuration with classic job compute only after checking source connectivity and dependencies. For interactive BI, evaluate a SQL warehouse separately. For a legacy job depending on an unsupported execution API, plan either compatible classic compute or a code migration; do not assume the BI warehouse solves the incompatibility.

The compute lab needs an environment exposing the selected compute controls. Free Edition cannot demonstrate classic VM sizing, pools, or all access modes. A successful small Free Edition query is not validation of a classic production cluster design.

4. Identity and Authorization

A data access request succeeds only when the relevant identity, object permissions, compute permissions, storage authorization, and network path all permit it. These checks happen at different boundaries. Giving a person Azure Contributor on a resource group does not automatically grant SELECT on a Unity Catalog table, and granting SELECT does not open a storage firewall.

4.1 Identify the Principals in the Request

For the orders pipeline, distinguish at least four identities:

Identity Responsibility Typical authorization surface
Interactive developer Authors and tests code Workspace objects, compute, and Unity Catalog
Deployment principal Creates or updates job and pipeline definitions Workspace APIs and resource permissions
Job execution principal Runs the production workload Input/output objects, secrets, and execution resources
Storage identity Authenticates the governed storage connection to Azure Azure storage data-plane roles and applicable storage controls

They can coincide, but should not be assumed to. A deployment can succeed because the deployer may edit a job while the next run fails because its execution principal cannot read the source. Conversely, a developer can successfully run code interactively while the production identity lacks the same permissions.

Databricks supports Databricks-managed service principals and Microsoft Entra ID-managed service principals. The former provide a platform-managed automation identity; the latter connect to an Entra application identity and may be appropriate when the same automation must also authenticate to Azure services. Choose a supported authentication mechanism for the target API rather than assuming every token is accepted everywhere.

A managed identity is an Azure-managed workload identity whose credential lifecycle is handled by Azure. It is not a human login, and its use for storage access does not automatically make it the identity under which a Databricks job runs.

4.2 Grant the Complete Privilege Combination

Reading a table normally requires three data-access privileges: USE CATALOG on its catalog, USE SCHEMA on its schema, and SELECT on the table. Usage privileges allow the namespace to be used; they do not independently grant the right to read all contained tables.

GRANT USE CATALOG ON CATALOG sales_prod TO `revenue-analysts`;
GRANT USE SCHEMA ON SCHEMA sales_prod.gold TO `revenue-analysts`;
GRANT SELECT ON TABLE sales_prod.gold.daily_revenue TO `revenue-analysts`;

This example assumes the group and objects already exist and the grantor is authorized to manage the grants. It gives a group one analytical interface rather than access to raw customer data.

For a writer, identify its exact operations. MODIFY is a broad table data-write privilege; object creation additionally requires the relevant creation privilege on the container. Reading source tables and writing a target are separate requirements. Do not use ALL PRIVILEGES to hide an incomplete analysis of what a job actually does.

The same distinction applies to files. A volume reader needs namespace usage plus READ VOLUME; a writer needs the supported read/write combination and any operation-specific requirements. Creation of an external object additionally depends on the appropriate external-location privilege.

4.3 Inheritance, Ownership, and Administration

Granting SELECT at schema scope applies to current and future applicable objects in that schema. This reduces repetitive grants but changes the future exposure boundary: tomorrow's newly created table can become readable without a separate approval. Place unrelated sensitive data in a different boundary or choose narrower grants.

Revoking a direct table grant does not remove access still supplied by a group or a parent-scope grant. To explain effective access, examine the principal's group membership, direct grants, inherited grants, ownership, and applicable policies. A table-level grant listing alone may not answer the whole question.

Ownership is lifecycle responsibility and administrative authority over an object, not just a stronger synonym for SELECT. Delegate production ownership to an accountable operational group where appropriate, rather than leaving every critical object dependent on a departing employee.

MANAGE concerns administration of an object, including privilege management under the current model. It must not be mistaken for an automatic data-read grant. Administrators with the ability to grant themselves data access still represent an important trust boundary even when the privilege itself is not SELECT.

ALL PRIVILEGES has explicit exclusions. The current privileges reference excludes MANAGE, EXTERNAL USE SCHEMA, EXTERNAL USE LOCATION, and READ METADATA. It is therefore inaccurate to read the phrase literally as every operation the service supports. Inspect the privilege definition and its applicable object types.

4.4 Workspace Bindings and the Storage Boundary

Workspace bindings restrict where supported catalog or storage objects can be used. They complement principal permissions: the user needs authorization and the request must originate from an allowed workspace where a binding applies. A production catalog should not become usable from a development workspace merely because both attach to the same metastore.

Bindings are not substitutes for cloud storage controls. A user holding direct storage credentials may take a path outside Unity Catalog. Governed object permissions cannot prevent access through an independently authorized external system. Prevent bypass by constraining direct cloud access, not by assuming the catalog intercepts every possible storage request.

For Azure storage, a common managed-identity design is:

  1. Create an Azure Databricks access connector with an appropriate system-assigned or user-assigned managed identity.
  2. Assign the identity the required Azure storage data-plane role at an appropriate scope. Read-only and write workloads need different authority; a management-plane role is not a substitute for data access.
  3. Create a Unity Catalog storage credential referring to the connector and, where applicable, the user-assigned identity.
  4. Create an external location combining the approved path and credential.
  5. Grant object and location privileges according to the operations users need.
  6. Validate network reachability and the intended read/write operations under the actual execution identity.

A system-assigned identity follows its connector's lifecycle. A user-assigned identity has an independent Azure lifecycle. Removing a connector, revoking the identity's storage role, or changing a firewall can break a pipeline even when its Unity Catalog grants are unchanged.

File-event ingestion can require additional cloud resources and permissions beyond basic blob read/write. Validate the documented notification setup; do not assume that adding one queue role alone configures the whole event path.

4.5 Row Filters, Column Masks, and Views

Table-level row filters decide which rows a query may return. Column masks transform protected values according to an applicable policy. These mechanisms are applied through supported query paths and compute; they are not encryption and do not protect against an independent direct read of underlying files.

For example, a mask can reveal customer email only to an authorized account group:

CREATE FUNCTION sales_prod.silver.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('customer-support') THEN email
  ELSE '[masked]'
END;

ALTER TABLE sales_prod.silver.customers
ALTER COLUMN email SET MASK sales_prod.silver.mask_email;

This is an illustrative example requiring the table, function-creation permissions, policy-management permissions, and compatible compute. It demonstrates a type-preserving transformation: a string column receives a string result. Tests must cover authorized users, unauthorized users, null input, and queries that filter or join on the protected column.

A dynamic view expresses a controlled projection and identity-dependent predicates in a view definition. It is useful for a stable consumer interface or a join across objects. If the consumer also has unrestricted access to the base tables, the view does not remove that alternative access path.

View resolution also involves ownership and caller context. Do not infer the identity used by a row-filter function from the view owner's privileges. Verify the documented semantics for the chosen fine-grained access mechanism, especially when combining views with ABAC. Tests should execute as the real consumer, not only as the object creator.

ABAC adds centralized policy selection based on governed attributes; the next chapter explains how it differs from attaching individual masks to individual tables.

4.6 Secrets Are a Separate Authorization Surface

Use secrets when a dependency requires a credential that cannot be replaced by an appropriate identity-based integration. A secret scope controls retrieval; the retrieved value then authenticates to another service. Being authorized to retrieve a database password and being authorized by that database are two distinct checks.

Databricks-backed scopes store secrets in Databricks. Azure Key Vault-backed scopes provide an interface to secrets managed in Key Vault. With the latter, secret creation and rotation occur in the vault rather than by writing through the Databricks scope.

The documented Key Vault-backed scope integration has specific setup requirements, including its supported Key Vault permission model and network configuration. Do not assume it supports every configuration available to an arbitrary application using a Key Vault SDK. Verify those integration requirements before changing an organization's vault authorization model.

Scope access can expose the secrets in the linked vault to authorized scope readers. Separate vaults/scopes when different groups require different credential boundaries. Do not put unrelated production credentials behind a scope broadly readable by development users.

Secret redaction protects against some accidental display, not against a person or program authorized to retrieve and transform the value. Avoid printing secrets, placing them in URLs, or sending them to generic debug logs. Cluster configuration and environment-variable injection can expand who can access a value; verify the sharing boundary before using those mechanisms.

Rotation is incomplete until consumers use the new credential and the old one is retired. Values injected into a running environment may require restart or reload. Test the actual downstream connection after rotation rather than only checking that the vault now contains a new version.

4.7 Diagnose an Authorization Failure

For an orders job that cannot read a landing volume, establish the failing boundary in order:

  1. Confirm which principal executes the failed task, not merely who clicked Run.
  2. Confirm the task can use its compute and required workspace artifacts.
  3. Check catalog/schema usage and volume privileges, including group and inherited access.
  4. Check applicable workspace bindings and compute compatibility.
  5. Validate the storage credential's Azure authorization and network reachability.
  6. If a secret-based connection is involved, check scope access, credential validity, and remote-system permissions without exposing the value.

The security lab should be supplemented with a negative test: an unauthorized principal must fail to access the protected data. A successful admin query alone is not evidence that the restrictions work. Managed identities and Key Vault exercises require Azure resources; account and identity administration are not fully reproducible in Free Edition.

5. Governance, Retention, and Sharing

Governance combines rules about meaning, access, ownership, change, and lifecycle. A catalog containing well-named tables is not sufficient. For the orders dataset, the team must know what an order represents, who may change it, how changes reach consumers, how long historical states remain recoverable, and what is disclosed to partners.

5.1 Metadata Must Explain the Data Contract

A table description should state its grain, source, refresh behavior, and important exclusions. A column description should resolve ambiguity that cannot be inferred from its type. order_total DECIMAL(18,2) does not tell a reader the currency, whether tax is included, or how refunds are represented.

For daily_revenue, define whether a row represents order date or settlement date, which timezone determines the day, which statuses contribute, and whether subsequent cancellations restate prior results. These details are necessary for correct queries and for validating generated SQL in analytical tools.

Preserve metadata through deployment and schema evolution. A pipeline that drops and recreates a table may disrupt descriptions, grants, ownership, or dependencies. Test those properties as part of the deployment contract rather than treating successful data loading as the only postcondition.

AI-generated comments can suggest descriptions, but cannot determine business meaning that was never provided. Review a generated description against the source system and transformation rules before publishing it as authoritative metadata.

5.2 Centralize Attribute-Based Policies Without Hiding Their Logic

Attribute-based access control (ABAC) selects policies using attributes such as governed tags. Instead of attaching an email mask separately to hundreds of columns, define an approved classification and a policy that matches it. Newly classified objects can then receive the intended control without another hand-written table policy.

Separate the responsibilities:

  • The governed tag definition controls allowed classification keys/values and who can assign them.
  • The classification identifies the data to which a policy should apply.
  • The policy establishes scope, relevant principals, and the filter or mask to use.
  • The function defines the transformation or row condition.

A tag by itself is not encryption and does not automatically grant or revoke access. The policy must match the intended objects, and users still need the underlying access privileges. Someone allowed to change policy-relevant tags can affect protection indirectly, so tag-assignment permissions belong in the security review.

Test policy coverage rather than only policy creation. Add a newly tagged column, test a matching and nonmatching principal, and inspect overlapping policies. Conflicting effective filters or masks can cause access errors rather than a convenient merge of all intended rules. Current conflict-resolution and inheritance semantics must be checked for the selected policy feature.

Keep policy functions simple and predictable. A function evaluated in many queries can become a performance dependency, and a complex external lookup may be unsupported or prevent optimization. Keep the decision about who the policy applies to in the policy where that mechanism is supported, rather than duplicating membership logic throughout many functions.

5.3 Retention Has Several Independent Clocks

Do not collapse these questions into one "retention period":

Retained information Why it matters Mechanism to inspect
Current business records Business/legal record retention Explicit lifecycle rules and row-level changes
Older table versions and data files Time travel and recovery Delta log/file retention and maintenance
Streaming progress and state Correct continuation after restart Checkpoint storage and source retention
Audit and lineage evidence Investigation and impact analysis System table/API/export retention
Copies held by consumers or backups Deletion and recovery obligations Separate downstream policies and contracts

Delta time travel requires both metadata describing a historical version and the files needed to read it. Keeping transaction log history longer does not resurrect files already removed by maintenance. If a required recovery window is 30 days, configure a compatible file and log retention policy before maintenance removes the necessary history.

VACUUM removes eligible obsolete files. It does not delete every row whose business date is old, and it is not a substitute for a business retention rule. A file containing old orders can still be part of the current table snapshot and therefore remain necessary.

SHOW TBLPROPERTIES sales_prod.silver.orders;
DESCRIBE HISTORY sales_prod.silver.orders;
VACUUM sales_prod.silver.orders DRY RUN;

These examples inspect configuration, history, and candidate file removal. The dry run is not a deletion command. Before any actual cleanup, account for the longest readers, writer transactions, stream outages, and required rollback window. Disabling retention safeguards to reclaim space quickly can invalidate legitimate work.

5.4 Logical Deletion Is Not Physical Erasure

A DELETE removes rows from the current logical table state. Older versions can still reference their data, and deletion vectors can represent removed rows without immediately rewriting all affected data files.

A deletion process therefore has several steps: identify the subject's data, apply logical deletions, propagate them to derived datasets, physically purge affected content using the supported table maintenance process, allow the required retention interval, and verify the scope of remaining copies. For deletion-vector workloads, the supported rewrite/purge operation and later cleanup serve different purposes.

The archived retention unit suggests skipChangeCommits in a discussion of downstream deletions. That setting skips certain upstream change commits; it does not propagate the deleted records as downstream deletes. Using it as a deletion-propagation strategy leaves a correctness gap. Use a change feed with delete handling, explicit coordinated deletions, or recomputation from the authoritative current state as appropriate.

A refreshed materialized result and an incremental append-only stream also react differently to source changes. Verify each dependent dataset rather than assuming "bronze was deleted" means "all copies are gone". Include exports, checkpoints that may contain sensitive state, shared recipients, and backups in the scope assessment.

This is an engineering process, not a legal compliance guarantee. The required evidence and exceptions must be defined with the organization's legal and data-governance owners.

5.5 Maintenance and Storage Lifecycle Must Agree

Predictive optimization can automate supported maintenance for managed tables, such as compaction, cleanup, and statistics-related work. It reduces manual scheduling but still operates under configuration and retention requirements. Configure the intended recovery window before allowing automated cleanup to use a shorter default.

Cloud lifecycle rules act on storage objects, not on Delta transaction semantics. A policy that deletes an active data file or a checkpoint because of its age can corrupt reads or restart behavior. Moving necessary files into an offline archive tier can make them temporarily unreadable even when the catalog object still exists.

Do not design raw blob lifecycle rules by translating a SQL date filter into a file-age condition. Rewrites and compaction change file organization; file timestamps are not equivalent to business event timestamps. Use a documented table-aware archival pattern or a separately controlled archive dataset when the operational table must remain queryable.

5.6 Lineage, History, and Audit Answer Different Questions

Lineage identifies observed dependencies between data assets and operations. It helps answer which consumers may be affected if order_total changes meaning or type. Table history records transactional changes to a Delta table. Audit events record supported actions and actors across service surfaces.

These are related evidence sources, not interchangeable complete records. A lineage edge does not prove that a transformation was logically correct. A successful table commit does not prove which business user later viewed every row. A metadata lookup event such as getTable does not by itself prove that the complete table data was read.

Use Catalog Explorer to inspect ownership, dependencies, and available history. Use table and column lineage system tables for supported programmatic analysis, and audit tables or delivery destinations for activity investigation. Respect differences in retention, region/account scope, supported execution paths, and permission-based visibility. A masked node or absent event is not sufficient evidence that no dependency or access exists.

Before changing a production column, identify downstream datasets, jobs, views, and dashboards; inspect available lineage; search code and published contracts for references outside captured lineage; then test the proposed change. Lineage narrows the investigation but does not replace it.

Verbose audit logging can record command text, which improves investigation and increases sensitive-data exposure. Protect the logs and define their retention. Exporting diagnostic events to Azure Monitor, storage, or a SIEM is a separate delivery configuration; do not assume access to a system table automatically configures an Azure diagnostic setting.

5.7 Share Deliberately

Delta Sharing uses provider-side shares and recipient objects to expose supported assets. Databricks-to-Databricks sharing uses the recipient's supported Databricks/Unity Catalog identity arrangement. Open sharing supports external clients with its own authentication configuration, such as supported token or federation mechanisms. Recipient capabilities and shareable assets depend on the chosen mode.

Prefer a narrowly defined analytical interface such as approved regional revenue over an entire mutable schema when the recipient needs only that dataset. Sharing a whole schema can include future objects; this is a future disclosure decision, not merely a convenient shorter command.

For token-based access, define secure distribution, expiration, rotation, and revocation. For recipient-dependent views or filters, test from the recipient context. A provider's own query may not reproduce the identity and recipient properties used during sharing.

Revoking a share stops future authorized access through that sharing relationship. It does not remotely delete copies a recipient already exported. State acceptable use, retention, and deletion responsibilities in the sharing agreement and evaluate cross-region/cloud transfer and access costs separately.

5.8 Governance Exercise

For the orders workload, produce four small artifacts: a table contract for daily_revenue, a list of principals allowed to classify sensitive columns, a retention/deletion dependency checklist, and a recipient-specific sharing scope. Each must name concrete objects and conditions.

Then test one change: a customer requests deletion after a revenue report has been published and shared. Identify which datasets should be restated, which history remains recoverable, which consumers need notification, and which evidence proves the requested operations occurred. A successful DELETE statement alone is an incomplete answer.

6. Ingestion, Streaming, and Schema Evolution

An ingestion design must specify what constitutes new information, how progress is recorded, and how the target behaves when the same input is seen again. The source may contain immutable files, an evolving snapshot, or ordered change events. Those inputs require different correctness rules even when all of them eventually populate a Delta table.

6.1 Start With the Source Contract

For the orders workload, distinguish an append-only order-event feed from a current-state order table. An event such as "order cancelled" is new information even when its order_id already exists. A current-state snapshot instead describes the latest known representation of each order.

Record the source key, update/delete behavior, event ordering field, schema contract, and retention/replay window. Also specify whether extraction provides a transactionally consistent snapshot or a moving view while the source is changing. Without these decisions, "incremental load" is only a label.

A full snapshot replaces or reconciles an entire selected source state. A cursor-based extraction reads rows whose update column exceeds a saved position. Log-based CDC captures operations from the source's change mechanism. A cursor does not automatically detect hard-deleted rows or changes whose cursor value was not advanced. It also needs a deliberate strategy for equal cursor values and overlap at batch boundaries.

Source behavior Candidate approach Main correctness question
Small periodic full dataset Snapshot/CTAS/replacement Is the snapshot complete before it is published?
Recurring immutable files COPY INTO or Auto Loader How are already discovered files and duplicated business events distinguished?
Supported operational database changes Managed Lakeflow Connect CDC connector Can the source retain changes through gateway/pipeline outages?
Event bus Structured Streaming with a supported connector Which offsets, event schema, and retention window govern replay?
Unsupported/custom source Notebook or external extraction service Who implements progress, retries, throttling, and delete handling?

Azure Data Factory can orchestrate extraction across systems or run Databricks work as part of a broader workflow. It does not change the target's deduplication or transaction semantics. Decide which service owns scheduling and recovery rather than creating overlapping independent schedules by accident.

6.2 SQL Loading Methods Have Different Repetition Semantics

CTAS creates a table from a query result. It is suitable for an initial load or a deliberate new dataset. IF NOT EXISTS skips creation when the table already exists; it does not update that table to match the source.

CREATE OR REPLACE TABLE ... AS SELECT replaces the target's contents under the supported table semantics. This is appropriate for a complete recomputation, not for appending a new daily file. If the input query accidentally selects only yesterday's records, the replacement can remove every other day from the current target state.

COPY INTO loads supported files into a Delta target and tracks previously loaded files so normal repeated executions do not reload them. This is file-level ingestion idempotency, not a business-key uniqueness guarantee. Two different files containing the same order can still produce duplicate order records.

COPY INTO sales_dev.bronze.order_events
FROM '/Volumes/sales_dev/bronze/order_files/incoming/'
FILEFORMAT = JSON;

The example requires an existing compatible target and a valid volume path. Force-reload options, changed source files, replacement of the target, and changes in ingestion state must be evaluated deliberately. Do not assume a rerun is harmless after resetting the mechanism that remembers what was loaded.

Auto Loader is generally the more suitable option for sustained, large-scale file discovery and richer schema handling. Select it for those capabilities, not because SQL ingestion is inherently incapable of reliable repetition.

6.3 Structured Streaming Is Incremental Execution With State

Structured Streaming represents a source as an incrementally processed dataset. A streaming query defines source, transformations, sink, and checkpoint location. The engine records progress and, where needed, state used by operations such as aggregations or deduplication.

The checkpoint is part of the query's identity. Use a durable, query-specific path, and prevent ordinary storage cleanup from deleting it. Two independent queries must not share a checkpoint. A restarted query with its valid checkpoint continues from recorded progress; a query started with a new checkpoint may behave like a new consumer.

Source replay, checkpoint state, and sink behavior jointly determine recovery guarantees. A transactional Delta sink can participate in exactly-once processing of the supported query, but arbitrary external side effects do not become exactly-once merely because the source is streaming. A callback that sends an email or appends to an external system may execute again after a failure.

Output modes describe what a streaming query emits, not general target-table upsert behavior. append emits newly produced result rows, update emits changed result rows for supported operations, and complete emits the full result. Not every source/operator/sink combination supports every mode. In particular, selecting update is not a substitute for a keyed MERGE into an arbitrary target.

6.4 Auto Loader Separates File Discovery From Row Meaning

Auto Loader is a Structured Streaming source for incremental file ingestion. It tracks discovered files and supports directory listing or supported file-event/notification mechanisms. Event-based discovery can reduce repeated listing overhead, but requires the appropriate source and cloud configuration.

incoming = "/Volumes/sales_dev/bronze/order_files/incoming/"
state_root = "/Volumes/sales_dev/bronze/ingestion_state/orders/"

order_stream = (
    spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", state_root + "schema")
    .load(incoming)
)

query = (
    order_stream.writeStream
    .option("checkpointLocation", state_root + "checkpoint")
    .trigger(availableNow=True)
    .toTable("sales_dev.bronze.order_events")
)
query.awaitTermination()

This illustrative example assumes both volumes exist, the target and permissions are suitable, and the selected runtime supports the options. The input path uses slash-separated volume components; it is not the dot-separated SQL namespace. State is kept outside the input directory so the ingestion query does not discover its own metadata files as business input.

The schema location stores inferred schema information. The checkpoint stores streaming progress and state. They are related operational dependencies, but resetting one does not automatically produce a correct reset of the other or of the target table.

File tracking also does not enforce row uniqueness. If the source writes order event evt-100 into two distinct files, both files can be valid new discoveries. Deduplicate by event identity or source sequence at the layer whose contract requires it.

6.5 Schema Inference, Evolution, and Rescue

Inference examines source data and proposes a schema. It is not proof that all later files follow that schema. Sampling can miss rare values, and strings such as postal codes or account identifiers should not become numbers merely because the sample contains digits.

For common text formats, Auto Loader's conservative inference can use strings unless type inference or schema hints are configured. Explicit schemas and hints express expectations; they do not remove the need to decide what happens to mismatching records.

Separate three changes: a newly added column, a value incompatible with the current type, and a semantic change that leaves the type unchanged. A string field changing from local currency to USD is not detectable by schema enforcement alone.

Evolution policy Expected operating choice Consequence to plan for
Add new columns Accept compatible structural growth Detection can update stored schema and stop the stream; the documented restart procedure is still required.
Rescue unexpected fields Preserve unexpected input without changing the main schema Downstream code must inspect rescued data rather than silently ignore it.
Fail on new columns Require an explicit contract change A restart without fixing the schema/input does not resolve the failure.
Ignore new fields under the selected mode Preserve a stable projection Information may not reach the intended columns; this is a deliberate loss/omission policy.

Type widening is a separate supported capability with runtime and table-feature requirements. Do not treat every type change as additive schema evolution. A string-to-integer conversion and an integer-to-larger-integer widening have different risks.

_rescued_data can retain data that could not be represented under the expected schema. A nonempty rescued column is therefore an observable signal, not automatic evidence that ingestion was fully correct. Define an alert or quality rule for unexpected rescue rates and a process for reprocessing accepted schema changes.

6.6 Triggers Do Not Define Business Correctness

An AvailableNow trigger processes the available increment of a supported source and then stops. A scheduled job can repeatedly run this pattern using the same checkpoint. It combines incremental state with bounded compute activity; it is not a full reload on every schedule.

A processing-time trigger requests recurring micro-batches. If a batch takes longer than the interval, the requested interval does not force it to finish faster. Investigate backlog, batch duration, source rate, and processing rate. Continuous pipeline mode, continuous job scheduling, and Spark's separate continuous-processing terminology should not be treated as synonyms.

Choose latency from a consumer requirement. If daily reporting tolerates a 30-minute delay, an always-running low-latency stream may create cost without changing the result consumers need. Conversely, reducing a scheduled interval does not help if each run has a startup delay and the source provides only hourly snapshots.

6.7 Event Hubs and Kafka-Compatible Ingestion

Azure Event Hubs offers a Kafka-compatible endpoint for supported clients. A Spark Kafka source reads message metadata such as topic, partition, offset, timestamp, and binary key/value fields. Decode and parse the value under an explicit payload schema; preserve enough source metadata to investigate duplicate or malformed events.

Configure the correct endpoint, TLS/authentication mechanism, topic/event-hub name, and permissions. Keep connection credentials in a supported secret or identity configuration rather than source code. Network reachability and authentication remain separate checks. The archived course also shows a native Event Hubs connector; its format, dependency, options, and payload schema are different and should not be mixed with the Kafka source example.

Starting-offset settings govern a new query under the connector's documented rules. A resumed query normally uses its checkpointed progress instead. If the checkpoint refers to data that has aged out of the source retention window, the source cannot replay it simply because a checkpoint exists. Test outage recovery against source retention, not only against the normal steady-state ingestion rate.

6.8 CDC, Delta Change Data Feed, and AUTO CDC

CDC is the general pattern of capturing source inserts, updates, and deletes. Delta Change Data Feed is a table feature that exposes changes in a Delta table over retained versions. AUTO CDC is a managed change-application mechanism in supported Databricks declarative pipelines. One can consume data produced by another, but they are not the same feature.

A usable change record needs a business key, operation meaning, and ordering information. A timestamp can order changes only if the source guarantees sufficient precision or supplies an additional tie-breaker. Ingestion arrival time is usually a poor replacement for the source's change sequence because networks and retries can reorder arrivals.

Managed Lakeflow Connect database connectors can combine initial loading with incremental change capture, while query-based connectors use source queries/cursors. Do not assume every connector uses a gateway or the same database log technology. Source configuration, supported schema changes, and retention requirements are connector-specific.

AUTO CDC applies changes by key and sequence to maintain current state or supported SCD type 2 history. Supply a valid sequence and explicit delete interpretation. A partial update with an omitted field must not be confused with an explicit request to set that field to null; a global "ignore null updates" choice is correct only if it matches the source contract.

For a Delta change feed, distinguish insert/delete records and update preimages/postimages. Loading every feed row as a new fact can double-count changes. Feed retention also limits replay, so a change feed is not automatically an immutable business-history archive.

Test five inputs in the orders pipeline: a new file, the same file presented again, a different file containing the same event, a newly added column, and an out-of-order cancellation. Predict file counts, row counts, rescued records, final order state, and restart behavior before running the test.

Then stop the stream after a partial run and restart with its original checkpoint. Repeat only in a disposable environment with a fresh checkpoint and compare the result. The difference teaches why ingestion state and business deduplication are separate controls.

7. Table Design, Transactions, and History

Define what one row means before choosing a table format or physical layout. A table containing one row per order, one row per order line, and one row per order-state change supports different calculations. No storage optimization can repair a revenue query that joins these grains incorrectly.

7.1 Grain, Keys, and Measures

For order lines, a candidate business key is (order_id, line_id). For order events, it may be an event identifier or a source key plus sequence. A customer dimension uses a customer business key, but a historical dimension needs an additional way to identify each customer version.

State the grain in the table contract. At line grain, quantity and line amount can be aggregated with suitable business rules. An order-level shipping fee repeated on every line cannot be summed without duplication. A status snapshot count is not the count of events that created that status.

Distinguish business keys from surrogate keys. A surrogate key identifies a stored version or warehouse row; it does not replace the rule for determining whether two source records refer to the same business entity. Identity-generated values also have feature and concurrency implications, so they should not be introduced automatically into every table.

Primary and foreign key metadata in Unity Catalog can document relationships, but the informational constraints described by the course do not enforce uniqueness or referential integrity. Validate these properties in the pipeline. An optimizer relying on a declared relationship is not a substitute for proving the relationship holds.

7.2 File Formats and Table Formats Solve Different Problems

CSV and JSON describe serialized records. They are useful for interchange but require decisions about types, escaping, malformed values, and nested structure. Parquet is a columnar file format with typed columns and encoding suitable for analytical reads.

Delta Lake adds a transaction log and table semantics over data files, commonly Parquet. Apache Iceberg is another table format with its own metadata and protocol ecosystem. The choice affects supported readers/writers, schema evolution, transactional behavior, and platform features, not merely compression.

Use Delta for the orders implementation when the required Databricks ingestion, change handling, and maintenance features fit it. Evaluate Iceberg where interoperability and supported multi-engine access require it. Do not infer write compatibility from the ability of another engine to read generated metadata. Reader support, writer support, catalog integration, and table feature versions are separate checks.

The managed/external choice from chapter 2 is independent of this format decision. A raw CSV external table and an external Delta table do not offer identical transaction guarantees just because their storage lifecycle is external.

7.3 Transactions and Concurrent Writers

A Delta table version describes a consistent table snapshot. A supported transaction either commits its table change or does not expose that committed change to readers. This protects a table from partial publication of that transaction; it does not automatically make an arbitrary sequence of statements across several tables one atomic transaction.

For example, updating orders and then appending an audit record are two operations unless an explicitly supported transaction mechanism encloses them. A failure between them can leave the data updated without the expected audit row. Use durable run identifiers, reconciliable state, and documented transaction boundaries.

Concurrent writes may conflict depending on the operations, affected data, isolation behavior, and enabled table features. A retry must re-evaluate the intended update against current state where appropriate. Repeating a previously computed overwrite can discard someone else's work even if the second write succeeds.

Schema enforcement rejects incompatible writes under the configured rules. Schema evolution deliberately permits supported changes. Neither establishes business validity: a negative amount may have a perfectly valid numeric type, and a new nullable field may break a consumer that assumes a fixed projection.

Mechanism Question it answers What it does not guarantee
SCD type 1 What is the current accepted attribute value? Previous business values remain queryable.
SCD type 2 What attribute value was valid for a business entity during an interval? The intervals are correct without sequencing and validation.
Delta time travel What did this table snapshot contain at a retained version/time? Indefinite business history after file cleanup.
Delta Change Data Feed Which row changes occurred in a retained change interval? A permanent independent archive of all past changes.
Persisted change-history table Which captured events/versions have we deliberately retained? Completeness when capture started late or missed source retention.

SCD type 0 retains an original value without overwriting it, and type 3 stores a limited previous value alongside the current one. They are useful only when that reduced historical contract is intentional. Type 2 is appropriate when historical facts must retain the context that was valid at their event time.

Business-effective time and processing time also differ. A customer region change effective on Monday may arrive on Wednesday. A table commit on Wednesday records when the system processed it, not necessarily when the customer changed region. Store the necessary timestamps separately rather than assigning every change current_timestamp() and calling it business history.

7.5 Build SCD Type 2 Around Invariants

Suppose customer C42 changes region from North to South at business time 2026-09-10 09:00:00. The intended history is:

Customer Region Valid from Valid to
C42 North 2026-01-01 00:00:00 2026-09-10 09:00:00
C42 South 2026-09-10 09:00:00 NULL, meaning current

Use half-open intervals: the start belongs to the version and the end does not. At the transition timestamp, exactly the new row matches. A fact-to-dimension lookup becomes:

SELECT fact.order_id, history.region
FROM sales_prod.silver.orders AS fact
JOIN sales_prod.silver.customer_history AS history
  ON fact.customer_id = history.customer_id
 AND fact.order_timestamp >= history.valid_from
 AND (fact.order_timestamp < history.valid_to OR history.valid_to IS NULL);

This query is correct only if history intervals do not overlap and the relevant fact timestamps have a documented timezone/meaning. Check for at most one current version, no unintended overlaps, valid interval ordering, and the expected treatment of deletes and missing customers.

Maintain a deterministic change order per key. If multiple changes arrive in one batch, preserving only the latest record may be appropriate for type 1 but loses intermediate type 2 history. Null-safe attribute comparisons are necessary when null-to-value and value-to-null changes should create versions.

The archived manual SCD example needs correction: a source row matched by MERGE to close its current target version does not then execute that statement's WHEN NOT MATCHED branch. The subsequent INSERT is a separate operation, and matching it by a freshly evaluated current_timestamp() is not a reliable link between statements. A failure can leave an expired row without its successor.

Prefer the supported AUTO CDC history mechanism when its source contract fits. A manual alternative must deliberately stage closing and insertion actions, preserve event identity/time, define the atomicity boundary, and handle replay and concurrent writes. The fact that SQL contains both MERGE and INSERT is not proof that it implements SCD type 2 correctly.

7.6 Persist Operational History When Required

Enable a change feed before the changes you need to capture. Enabling it later does not reconstruct earlier row-level events. Persist the feed to a separate governed history table when the business needs longer retention than the source feed provides.

Retain the change type, source table/version identifiers, source event identity where available, commit time, ingestion time, and relevant record values. Preserve delete events and distinguish update preimages from postimages. An archive containing only postimages cannot answer every question about deletions or previous values.

A temporal/history design in this course means explicitly modeled history on Databricks. It does not imply that enabling a property creates SQL Server-style system-versioned temporal tables with all corresponding syntax and guarantees. Verify completeness by reconciling captured version ranges and investigating gaps before source retention removes the opportunity to replay them.

7.7 Partitioning, Clustering, and Data Skipping

Physical layout reduces unnecessary reads when it aligns with predicates. Traditional partitioning groups storage by partition-column values. It helps when filters can prune substantial data and each partition contains enough data to justify its overhead. Partitioning by a nearly unique order ID usually creates excessive small groups rather than useful pruning.

An unpartitioned Delta table does not necessarily scan every file. Data skipping can use collected statistics to exclude files that cannot satisfy a predicate. Statistics coverage depends on table configuration and features; do not assume every column in every table automatically has all useful statistics.

Liquid clustering organizes data for selected query keys without fixed Hive-style partition boundaries. It is appropriate for many new supported tables, especially where fixed partition choices would be restrictive. Changing clustering keys changes the strategy; it does not instantly rearrange all existing data. Reorganization still consumes compute and may require an explicit supported full optimization.

ALTER TABLE sales_prod.silver.orders
CLUSTER BY (customer_id, order_timestamp);

Use this only on a compatible table and runtime. The keys are illustrative: choose them from actual important predicates and selectivity, not from the example's convenience. Automatic key selection is a separate feature with prerequisites.

Z-ordering colocates values during optimization for applicable existing Delta tables. Do not combine Z-ordering, traditional partitioning, and liquid clustering as if they were independent switches that always stack. Check compatibility and migration requirements. File compaction, clustering, and deletion vectors also address different problems: fewer tiny files, useful value locality, and more efficient representation of row changes.

8. Transformations and Data Quality

The purpose of a transformation is to establish a data contract, not merely to make a query execute. For silver orders, that contract might require a valid event identity, a parseable event time, a nonnegative amount under an agreed refund model, and deterministic handling of repeated or superseded events. Each rule needs a failure policy as well as an expression.

8.1 Profile Before Choosing a Repair

Measure row count, null rates, key multiplicity, value ranges, and distributions before replacing or removing data. Compare them by source, ingestion batch, and time interval; a stable overall average can hide a broken source partition.

SELECT
  COUNT(*) AS total_rows,
  COUNT(*) - COUNT(order_id) AS missing_order_ids,
  COUNT(*) - COUNT(order_total) AS missing_amounts,
  MIN(order_total) AS minimum_amount,
  MAX(order_total) AS maximum_amount
FROM sales_dev.bronze.order_events;

The query assumes the relevant columns are already typed. If amounts are raw strings, lexical minimum and maximum do not measure numeric range. Separate parsing errors from business-range violations before interpreting the result.

Use exact checks where correctness requires exact counts, such as reconciling a fixed batch. Approximate distinct counts can support large-scale exploration but should not be silently treated as proof of uniqueness. Sampling can reveal a defect; failure to see a rare defect in a sample does not prove absence.

8.2 Parse Types Without Concealing Information Loss

Use decimal types for financial quantities when the contract requires fixed precision and scale. Floating-point values have different representation and rounding behavior. Choose precision from the maximum supported amount and the calculations that follow; a column wide enough for one line amount may be too narrow for a yearly aggregate.

Preserve identifiers as strings when formatting has meaning. Converting 00042 to an integer discards information. Parse dates and timestamps with a defined timezone and event-time meaning. A correctly typed timestamp in the wrong timezone can assign revenue to the wrong day.

CAST and tolerant conversions such as TRY_CAST serve different error policies. A tolerant conversion can turn malformed input into null, allowing the query to continue; the pipeline must then identify that null as a conversion failure rather than a genuine missing source value.

SELECT
  order_id,
  amount_text,
  TRY_CAST(amount_text AS DECIMAL(18,2)) AS order_total,
  amount_text IS NOT NULL
    AND TRY_CAST(amount_text AS DECIMAL(18,2)) IS NULL AS invalid_amount
FROM sales_dev.bronze.raw_orders;

This pattern retains the original representation for investigation. It does not resolve whether a negative amount is a valid refund or an invalid order: that is a business rule, not a type rule.

8.3 Null Is Not Zero, and Deduplication Needs an Ordering Rule

SQL predicates use three-valued logic. amount <> 0 does not retain null amounts as "not zero"; the predicate is unknown for them. Use explicit null tests and, where appropriate, null-safe equality. COUNT(*) counts rows, while COUNT(amount) counts nonnull values. These distinctions affect both quality checks and published metrics.

Replacing a missing amount with zero asserts that the amount is known to be zero. It can understate revenue and hide an extraction failure. Keep unknown values, quarantine them, or impute under a documented rule; do not use blanket filling merely to eliminate nulls from a report.

Deduplication requires a key and a survivor policy. Removing identical rows is different from selecting the newest state for an order. A distributed dropDuplicates operation should not be used to promise that the "first" business event or the latest version is retained without an explicit deterministic ordering rule.

SELECT *
FROM sales_dev.bronze.order_updates
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY order_id
  ORDER BY source_sequence DESC, event_id DESC
) = 1;

The ordering is valid only if the source contract defines the sequence and tie-breaker. A random UUID sorting later does not inherently represent a later business change. For SCD type 2, reducing a batch to one row per business key can lose legitimate intermediate history; use the change-processing approach from chapter 7.

Streaming deduplication can require state across batches. A watermark bounds supported stateful processing according to event-time lateness rules; it is not a guarantee that all future duplicates will be recognized forever. Define what happens to events arriving outside the retained state window and how they can be corrected.

8.4 Joins and Set Operations Change Cardinality

A left join preserves left rows but can multiply them when the right key is not unique. An inner join can remove unmatched orders. An anti join is useful for identifying orders whose customer key has no match. Choose the join according to the data contract, then test multiplicity and unmatched counts explicitly.

For historical dimensions, joining only on customer ID multiplies each order by every historical customer version. Include the valid-time predicate shown in chapter 7. Preaggregating before a join is valid only when the reduced grain still contains the information required by the join and final measure.

SQL UNION removes duplicates, while UNION ALL preserves them. PySpark union preserves duplicates and aligns by column position; unionByName aligns by name. Allowing missing columns fills an alignment gap but does not prove that the sources have the same business meaning. Explicitly project compatible types and names before combining datasets.

INTERSECT identifies common rows and EXCEPT identifies rows present on one side but not the other, with distinct-versus-ALL variants changing duplicate treatment. They are useful for reconciliation when both inputs use compatible schemas and the comparison grain is intentional. A row-level set comparison is not necessarily a business-key update comparison.

8.5 Reshaping Must Preserve Meaning

Flattening a struct exposes nested fields without necessarily changing row count. Exploding an array creates rows and therefore changes grain. Exploding both an order's line items and an unrelated list of discounts can accidentally create a Cartesian multiplication unless the intended relationship is defined.

A pivot converts selected attribute values into columns and normally includes aggregation. Specify the expected categories when the consumer needs a stable schema. An unbounded set of pivot values can turn a routine source change into a new output schema.

Unpivoting makes multiple measure columns into rows. Track the units and measure names so values from different meanings are not added together. Null-retention behavior must match the contract; omitting a null measure row and retaining an explicit unknown value are not always equivalent.

Denormalization can simplify frequent analytical queries but duplicates attributes and increases update responsibility. Use it for a measured consumer need, while retaining a documented authoritative source and a strategy for corrections.

8.6 Place Each Quality Rule at the Correct Layer

Mechanism Appropriate rule Important boundary
Parsing/schema checks Expected fields and representable values A compatible schema does not establish semantic correctness.
Enforced table constraints Supported row-level write invariants, such as NOT NULL or CHECK Informational primary/foreign keys do not enforce uniqueness or referential integrity.
Pipeline expectations Supported row expressions with a chosen violation action A row predicate alone cannot prove uniqueness across all batches.
Aggregate/reconciliation tests Key cardinality, totals, referential completeness, source/target balance Define the population, time window, and allowed differences.

Choose NOT NULL explicitly when absence is invalid; do not rely on a comparison predicate to implicitly enforce all null semantics. Adding constraints to an existing dataset also requires that the existing data satisfy the applicable validation.

A uniqueness rule needs a check over the intended key population, not just order_id IS NOT NULL. A check that sees one micro-batch can miss the same key loaded yesterday. State whether uniqueness is per event, per current entity, per historical version, or per batch.

8.7 Expectations and Quarantine

Lakeflow pipeline expectations provide three distinct outcomes:

Action Data outcome Appropriate reason
Warn/default Violating rows continue; quality metrics can be recorded Measure a defect while a downstream consumer tolerates it.
Drop Violating rows are excluded from that output The consumer explicitly accepts omission and omissions are observable.
Fail The affected update/flow fails under the service's semantics Publishing this output with a violation is unacceptable.

Failure of one flow must not be assumed to atomically undo every independent flow in the pipeline. Similarly, dropping records is not quarantine: without another retained path, the rejected data may no longer be available in the validated output for diagnosis.

CREATE OR REFRESH STREAMING TABLE valid_order_events (
  CONSTRAINT required_order_id
    EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(sales_dev.bronze.order_events);

This is a pipeline-definition example, not a generic SQL statement that can be run in every context. Configure the pipeline's target namespace and permissions before using it. The expectation checks nullability only; it does not check uniqueness, event ordering, or amount correctness.

For quarantine, preserve raw data and derive a classified intermediate dataset with explicit rule outcomes. Route valid rows to the accepted target and invalid rows to a quarantine target with event identity, failed-rule identifiers, source reference, and ingestion/run metadata. Use a complete validity condition that handles nulls explicitly so unknown predicate results do not fall into neither branch.

Make acceptance and quarantine mutually exclusive and, for the defined input population, exhaustive. Reconcile input = accepted + quarantined + explicitly accounted exclusions. Counts are evidence only when they refer to the same population and processing boundary. Reprocessing quarantine also needs replay-safe event handling to avoid inserting accepted records twice.

8.8 Load the Target According to Its Contract

Append is appropriate for new immutable records only when duplicate/replay handling has already been established. A repeated INSERT INTO can append the same data again. Deduplicating a batch internally does not prevent duplicating rows already in the target.

MERGE matches source to target and applies defined actions. Ensure the source has the required unambiguous matches and order conditional actions deliberately: a row matching an earlier update branch does not also execute a later delete branch. For current-state data, compare source sequence/version before overwriting newer state with a late event.

An overwrite replaces a defined scope. Do not assume .partitionBy(...) makes a generic overwrite selective: partition layout and overwrite scope are separate settings. Use a supported explicit predicate or replacement-key mechanism when correcting only a subset, and validate that the incoming data covers the intended scope without deleting unrelated rows.

Newer replacement syntax has runtime and compute requirements. Select supported REPLACE WHERE, REPLACE USING, or other documented operations according to their actual matching semantics; do not turn a version-specific example into a universal command.

9. Pipelines, Orchestration, and Recovery

Separate the graph of data dependencies from the graph of operational tasks. A dataset depends on the inputs needed to compute it. A job task may additionally depend on an external export, a validation gate, or a publication step. Declarative pipelines can manage the first graph, while Lakeflow Jobs can coordinate the broader workflow.

9.1 Choose the Appropriate Control Model

Notebook-based processing gives explicit control over reads, writes, branching, and external interactions. You own the ordering, progress handling, and recovery logic that are not supplied by a specific underlying engine. This is appropriate when the workflow contains heterogeneous operations or existing code that does not fit a declarative dataset definition.

Lakeflow Spark Declarative Pipelines defines datasets and flows so the service can resolve supported dependencies and manage their execution. Streaming tables express incremental processing; materialized views express a maintained query result. Use the choice based on update semantics, not merely whether the input happens to arrive often.

For the orders example, a streaming source can land order events, an AUTO CDC flow can maintain current order state, and a materialized result can compute revenue from that current state. Treating all three as append-only tables would mishandle updates or cancellations unless additional logic repaired the derived results.

Apache Spark Declarative Pipelines APIs and the managed Databricks pipeline service are related but not identical surfaces. Databricks-specific features such as particular expectations and CDC capabilities must be checked in the managed runtime. A matching Python namespace does not prove that an open-source environment provides every managed feature.

9.2 Keep Declarative Definitions Free of Uncontrolled Side Effects

A pipeline engine may inspect or evaluate dataset definitions while constructing and planning the graph. A definition should describe and return the intended dataset using the supported API. Do not send notifications, mutate an external application, or issue unrelated writes merely because the definition function is being evaluated.

For example, a materialized revenue result could be defined over an already maintained current-state table:

CREATE OR REFRESH MATERIALIZED VIEW daily_revenue
AS SELECT
  CAST(order_timestamp AS DATE) AS order_date,
  SUM(order_total) AS revenue
FROM sales_prod.silver.orders
GROUP BY CAST(order_timestamp AS DATE);

This example assumes the source represents only the order states that the business includes in revenue, uses one agreed currency, and has a defined timestamp timezone. If cancelled orders remain in the source or amounts mix currencies, the query requires additional business logic. The pipeline definition alone cannot infer those rules.

Configure the pipeline's source files, target namespace, execution identity, compute, and supported run mode. A dry run can identify syntax and dependency problems without processing the full data; it does not demonstrate output correctness, source accessibility throughout a run, or acceptable performance.

9.3 Design a Job as Explicit Dependencies

A practical orders job might contain: extract source data, update current-state orders, validate quality, refresh revenue, and publish a completion record. Publish only after the data and quality gates succeed. A task named validate that always returns success is not a gate.

Serial dependencies are necessary when a task consumes another task's outputs. Independent sources can run in parallel, but publication must use a defined completeness condition. "Both tasks finished" is not equivalent to "both produced the expected batch".

Run-if conditions operate on task states. All succeeded is suitable for a normal downstream transformation; All done is often suitable for cleanup; At least one failed can route an error-handling task. An if/else condition instead branches on data or parameter values, such as an invalid-row count. Keep these two kinds of conditions distinct.

A skipped task can affect downstream conditions differently from a failed task. Test skip, disable, timeout, and failure paths rather than reasoning only about the all-success graph. Disabling a broken task can allow other tasks to run while also removing a required data dependency, so it is not automatically a safe recovery.

For-each tasks apply a nested task to an input collection. Set concurrency from resource capacity and destination safety, not merely the array length. Two parallel iterations writing the same output partition or using the same streaming checkpoint are not independent work.

9.4 Parameters Must Identify the Work, Not Just the Environment

Useful parameters include the target catalog, source identifier, business interval, input batch/version, and stable run or request identifier. Distinguish the scheduled trigger time from the business period being processed. A delayed run should not silently change its input to whatever current_date() happens to be at execution time.

Pass task values for small coordination results such as counts and references, not for transporting entire datasets. Store substantial outputs in governed storage and pass their identifiers. Validate parameters before using them in paths, object names, or SQL; a string supplied as a catalog name should not become arbitrary executable SQL.

Backfills should call the same business transformation with an explicit historical interval and publication policy. Avoid a second ad hoc implementation whose semantics drift from daily processing.

9.5 Choose Triggers According to Availability

Scheduled jobs work when a time-based processing contract is appropriate. Advanced schedules use Quartz-style cron with a seconds field, not an arbitrary five-field Unix cron expression. Specify timezone explicitly. UTC avoids daylight-saving shifts for elapsed-time scheduling; a local timezone may be correct when publication is tied to a local business hour.

File-arrival triggers detect supported new-file events. They do not prove a multi-file delivery is complete and should not be assumed to fire for overwriting an existing filename. Use immutable naming and, where required, a completion manifest or other source contract before publishing a batch.

Table-update triggers indicate changes in monitored tables. Waiting for all monitored tables to change does not by itself establish that the changes belong to the same business batch. Correlate source versions or batch identifiers when coherent multi-source publication matters.

Continuous job scheduling starts another run according to the job's continuous behavior. It differs from a continuously running Spark query and from a declarative pipeline's continuous mode. Supported streaming triggers vary by compute type: the archived material specifically distinguishes bounded AvailableNow jobs on serverless from time-based streaming patterns on other supported compute.

Pausing a trigger prevents future trigger-driven starts; it is not necessarily cancellation of a run already executing. During maintenance, inspect active runs separately. External callers may also be able to start a job independently of its paused schedule.

9.6 Concurrency and Queues Need an Explicit Policy

If two runs update the same dataset, decide whether they can safely overlap. Setting a maximum of one concurrent run can reduce interference, but it does not make the processing logic replay-safe. It also does not coordinate independent jobs writing the same table.

Queueing preserves pending work only within the platform's supported queue behavior and limits. If arrivals are consistently faster than processing, a queue accumulates delay rather than solving capacity. Measure queue age and consumer freshness in addition to task duration.

Choose whether stale runs should execute, coalesce into a newer state refresh, or be deliberately skipped. A daily snapshot publication and an event archive may require different choices. Do not treat default concurrency or queue settings as a documented part of your business contract; inspect the deployed values.

9.7 Retry, Repair, and Replay Are Different Operations

A retry repeats a failed attempt according to configured policy. A repair reruns selected failed or affected parts of an existing job run under supported semantics. A full replay reconstructs an input range or whole dataset. Each can encounter side effects left by earlier successful operations.

Idempotency means that repeating the same logical request has the intended single effect. An append is not idempotent merely because it is inside a job. Use source/event keys, transaction-aware sinks, bounded replacement, or explicit request tracking appropriate to the destination. The same idempotency key must survive the retry; generating a fresh key for every attempt defeats the purpose.

Retry transient network or capacity failures when another attempt can plausibly succeed. A missing grant, invalid schema, or deterministic quality violation requires a configuration or data correction. Endless retries preserve neither correctness nor resources.

Configure per-attempt timeouts and a realistic total operating budget. A timeout applies to an attempt under the task's semantics; retries can extend the complete run well beyond one timeout interval. A warning-duration threshold is a notification, not termination. Continuous jobs and serverless workloads can have automatic retry behavior, so inspect their effective policies as well as explicit settings.

9.8 Report Failure Through the Execution Contract

An exception that is caught and printed can turn a failed transformation into an apparently successful task. Log appropriate context and rethrow or signal failure through the documented task mechanism when the required output was not produced.

Similarly, dbutils.notebook.exit("FAILED: ...") returns a notebook value; the text does not inherently set the task state to Failed. If a parent deliberately interprets returned values, that interpretation must be part of the workflow. Otherwise, propagate the failure rather than encoding it only in a string.

Do not apply the same generic exception wrapper to every operation. A notebook returning normally, a streaming query still running in the background, and a completed table commit are different states. Wait for the relevant completion condition and verify its outcome before publishing success.

Notifications should distinguish a retried transient failure from exhaustion of the retry policy. Route alerts to an owner and include job/run/task identifiers, affected data interval, and a diagnostic link. Avoid credentials and sensitive row contents. Muting intermediate retry notifications can reduce duplicate alerts without removing the final failure signal.

9.9 Recovery Exercise

Inject a failure after the silver table commits but before the publication task succeeds. Repair the failed portion, then rerun the whole logical batch. Verify that revenue does not double, the publication record is consistent, and no new checkpoint was silently created.

Also test an invalid input that cannot succeed on retry and a source outage that can. Their alert and recovery paths should differ. Use the pipeline lab and Jobs lab. Availability of triggers, task types, and concurrency depends on the workspace and selected compute; Free Edition limits must be checked.

10. Testing and Deployment

A release must identify the code, dependencies, configuration, target objects, and execution identity that produce the data. Versioning only a notebook leaves runtime packages, job settings, schedules, and permissions outside the reproducibility boundary. Declarative Automation Bundles help version deployable Databricks resources alongside their code, but data correctness still requires explicit tests.

10.1 Separate Transformation Logic From Interactive State

Keep reusable transformation functions in source modules where practical. Let notebooks coordinate inputs, parameters, and results rather than hide all logic in a long sequence of stateful cells. A notebook that succeeds only because a developer previously ran a setup cell is not a reproducible job artifact.

Use Git branches and pull requests to review the change, including data contracts and deployment configuration. The Databricks-specific concern is the workspace Git folder: changing its branch affects the folder's contents, and a shared folder can affect collaborators. Prefer independent development working copies and explicit production revisions rather than running production against someone's changing feature branch.

Resolve conflicts by preserving intended behavior, not by removing conflict markers mechanically. A merge can be syntactically valid while pairing a new transformation with an old schema or job parameter. Review the complete affected contract and rerun its focused tests.

Avoid committing secrets and unnecessary notebook outputs. A code review does not need production customer rows embedded in an IPYNB output. Reference secure data locations and use synthetic fixtures for tests.

10.2 Match Each Test to a Claim

Test Evidence it should establish What it cannot establish alone
Unit test A transformation maps representative inputs to expected rows/types Workspace identity, storage reachability, or distributed performance
Integration test Real components interact under the intended runtime and identity All scheduled/recovery paths or business acceptance
End-to-end test The workflow produces and publishes the agreed output from controlled input Every production-scale failure and future source change
User acceptance test Business stakeholders accept semantics, totals, and freshness All low-level security and infrastructure properties

For Spark logic, a pandas test is not evidence of identical Spark null, type, ordering, or execution semantics. Use the actual relevant execution engine for claims depending on those behaviors. Keep small deterministic fixtures and isolate external effects.

Compare values and keys as well as schema and row count. Two outputs with identical counts can contain different customers or duplicated revenue. DataFrames have no implicit business ordering; compare by explicit keys or a justified sorted representation. Use tolerances only where the numerical contract requires them, not to conceal unexplained financial differences.

Include invalid and boundary cases: duplicate keys, nulls, malformed values, late changes, empty batches, authorization failures, and a retry after a committed write. At least one test should deliberately violate each critical contract to prove that the gate fails rather than only printing a warning.

10.3 Isolate Test Data and Enforce Failure

Use a dedicated test catalog/schema or another explicit isolated namespace with synthetic data. The archived testing unit warns against production integration tests but later uses a production table in its end-to-end example. This course does not adopt that target. Test code must resolve its destinations from validated test configuration and fail if the target points to production.

Test setup and cleanup need ownership checks. A broad cleanup command based on a guessed prefix can delete unrelated objects. Track the exact objects created for a test run and remove only those disposable objects.

A failing assertion or nonzero test exit code must fail the CI step or job task. A message saying "UAT FAILED" followed by normal process completion can allow deployment to continue. Preserve test results and run identifiers so the release record distinguishes tests actually executed from checks that were merely configured.

10.4 Understand Bundle Configuration

Declarative Automation Bundles, formerly Databricks Asset Bundles, describe code artifacts and supported Databricks resources. The main databricks.yml declares the bundle and can include resource definitions in separate files. Variables supply deployment-time configuration; targets select environment-specific overrides; resources define jobs, pipelines, and other supported objects.

The following is an illustrative shape for supported serverless notebook tasks. The referenced source files, notebook environments, workspace authentication, permissions, and target catalogs must exist; it is not a complete runnable project included with this course.

bundle:
  name: orders_pipeline

variables:
  target_catalog:
    default: sales_dev

resources:
  jobs:
    orders_job:
      name: orders_pipeline
      max_concurrent_runs: 1
      tasks:
        - task_key: transform
          notebook_task:
            notebook_path: ./src/transform.py
            base_parameters:
              target_catalog: ${var.target_catalog}
        - task_key: validate
          depends_on:
            - task_key: transform
          notebook_task:
            notebook_path: ./src/validate.py
            base_parameters:
              target_catalog: ${var.target_catalog}

targets:
  dev:
    default: true
    mode: development
  prod:
    mode: production
    variables:
      target_catalog: sales_prod

The task dependency expresses ordering, while the variable selects the data namespace. Neither grants the job access to that namespace. Configure the production run identity, resource permissions, workspace host, and authentication explicitly in the real deployment.

Development mode can apply naming and schedule presets useful for isolated work. Production mode adds production-oriented validation and behavior, but the label alone does not prove the workspace is correct, privileges are narrow, or tests have passed. Inspect effective configuration rather than relying on the mode name.

Bundle variables and job parameters operate at different times. A bundle variable affects what is deployed; a job parameter can select a business interval at run time. Do not redeploy the whole bundle merely to process a different day if that is naturally a run parameter.

10.5 Validate, Plan, Deploy, Run, and Check Data

With a supported modern Databricks CLI and configured authentication, the stages are distinct:

databricks bundle validate -t dev
databricks bundle plan -t dev
databricks bundle deploy -t dev
databricks bundle summary -t dev
databricks bundle run -t dev orders_job

Validation checks configuration under the CLI's schema and context. Planning shows intended resource changes and can run configured build steps. Deployment uploads artifacts and reconciles managed resources. Summary reports deployed identities/resources. Running executes the workload. Data assertions then determine whether its output satisfies the contract.

Do not interpret successful validation as proof of cloud permissions or analytical correctness. Inspect warnings about unknown properties rather than ignoring them. Pin or otherwise control the deployment toolchain version because configuration features and deployment engines evolve.

A bundle's workspace root path is fundamental to its deployment identity. Defaults incorporate the deployer, bundle name, and target. State tracks resource identifiers, not just display names. Renaming a deployment identity or changing its state path can create a different management relationship instead of updating the intended resources.

Adopting an existing job requires deliberate binding or the documented migration mechanism. Generating a configuration file does not, by itself, prove the next deploy updates that existing job. Verify resource IDs to avoid duplicate schedules that process the same data twice.

10.6 CI/CD Must Control Destructive and Concurrent Changes

Promote a reviewed revision through an isolated environment and production using recorded target configuration. Authenticate automation with a supported noninteractive identity rather than an employee's interactive session. Keep deployment authority separate from data-processing authority where that distinction reduces access.

Review resource removals and target changes in the plan. A resource removed from a bundle can be removed from the managed deployment; deleting a job or pipeline definition is not the same as retaining every data asset it previously produced. Define which data is persistent and how lifecycle settings protect it.

Deployment locks prevent concurrent deployment interference. Use force-lock behavior only after establishing that a prior deployment is no longer active and the lock is stale. Overriding a legitimate active lock can produce competing changes. Similarly, choose an explicit policy for active workload runs rather than assuming the deploy command always blocks or always safely updates them.

Rolling back code does not reverse data already written by that code. A release recovery plan may require restoring a compatible table version, replaying a source range, or applying a compensating correction. Check schema and checkpoint compatibility before running old code against new state.

10.7 REST Automation and Bundle Deployment Are Not Identical

The published October 19 DP-750 objectives mention deploying a bundle using REST APIs. The public documentation inspected for this course establishes the CLI/workspace bundle workflow and the Jobs resource APIs. It does not establish a generally available single REST endpoint that accepts a bundle YAML project and performs the complete bundle deployment. Do not invent such an endpoint or treat job creation as equivalent proof.

At resource level, the documented Jobs API supports operations such as:

A successful run submission is not a completed run. A stable supported idempotency token can prevent duplicate run creation after a retried request; it does not make the workload's internal writes idempotent.

If a system is managed by bundles, direct API edits can create drift that a later deployment overwrites. Choose an ownership model. Automation can invoke a controlled CLI deployment process and use resource APIs for subsequent operations without pretending that those operations reproduce the bundle engine's planning, artifact handling, state, and dependency logic.

This REST objective remains an explicit documentation clarification point for exam preparation. Resource-level REST workflows are covered here; an end-to-end dedicated bundle REST procedure is not claimed as verified.

11. Performance and Observability

Investigate performance as a sequence of measurable questions: where was time spent, which resource or dependency limited progress, what changed, and did the proposed fix preserve results? A shorter runtime is not an improvement if the query silently excludes late records, skips failed input, or produces a different aggregation.

11.1 Separate Waiting, Startup, Execution, and Freshness

End-to-end delay includes source availability, trigger evaluation, queue time, compute startup, processing, and publication. A fast Spark stage does not compensate for an hour waiting in a job queue. A successful nightly job can still publish stale data if the source stopped delivering new records.

Record at least input interval/version, run identifier, queue/start/end timestamps, output freshness, processed and rejected counts, and the code/configuration revision. These make comparisons meaningful. Comparing different source volumes or different business intervals without normalization can produce a misleading performance conclusion.

Use the monitoring surface appropriate to the compute: job/task run details for orchestration, Spark UI for supported Spark execution environments, query profiles/history for SQL and supported serverless analysis, and pipeline event/quality views for declarative processing. Do not assume serverless exposes the same worker-level metrics as classic compute.

11.2 Diagnose From the Executed Plan

Start with the slow or failed task, then locate its expensive query/stage. Inspect scan size, exchange/shuffle operations, join strategy, task count, task-duration distribution, spill, and driver/executor behavior. An explain plan describes intended execution; runtime metrics show what actually happened.

Observation Candidate cause Discriminating check Possible intervention
Few tasks run while capacity is idle Insufficient useful parallelism or serial work Task count and driver activity Change the data/operation parallelism if semantics permit.
One or a few tasks run much longer Skew, unusually large records, or a slow executor Per-task input and duration distribution Address key distribution or the identified node issue.
High spill in expensive stages Partitions or state too large for available execution memory Per-task spill, memory, and partition sizes Reduce per-task data/state or change memory/partition sizing.
Large shuffle volumes Wide joins, aggregations, or repartitioning Exchange nodes and shuffle read/write Reduce data before the exchange or use a suitable join strategy.
Driver failure with mostly idle executors Driver-side collection or coordination pressure Driver logs and code using collect/toPandas Keep computation distributed or bound returned data.
High elapsed time with little computation Remote source, network, startup, or queue delay Timeline and dependency metrics Fix the relevant boundary rather than adding executors.

These are hypotheses, not automatic diagnoses. High input alone does not prove a cache is missing, and a long task alone does not prove skew. Compare the additional metrics that would distinguish competing causes.

11.3 Shuffle and Skew

A shuffle redistributes records, often to bring equal keys together for joins or aggregations. It can require serialization, network transfer, disk activity, and coordination. Avoid unnecessary columns and rows before a wide operation where the transformation remains semantically valid.

Skew occurs when work is unevenly distributed. A very frequent customer key or a large null-key group can make one partition dominate a stage. Doubling worker count may leave the same dominant task running at the end because that task has not been subdivided.

Adaptive Query Execution can adjust supported plans using runtime information, including some skew handling and join changes. Verify the actual resulting plan. Broadcasting a genuinely small join side can avoid a large shuffle, but forcing a large broadcast can exhaust memory. A universal size threshold is unsafe across different configurations and representations.

Salting keys distributes a hot key across subkeys, but joins and aggregations must be adjusted to preserve results. Randomly changing join keys without correctly expanding or reconciling the other side loses matches. Treat salting as an algorithm change with correctness tests, not a generic setting to enable.

11.4 Memory Spill and Partition Sizing

Spill means an operation writes intermediate data to disk when it cannot retain it in the intended memory region. Some spill can be compatible with a successful workload; sustained expensive spill is a signal to investigate rather than a proof of immediate failure.

More appropriately sized shuffle partitions can reduce the data processed by each task. Too many tiny partitions introduce scheduling and metadata overhead. Fewer partitions can reduce overhead when partitions are already small, but can worsen memory pressure when they are large. This is why a blanket recommendation to reduce partitions for an out-of-memory failure is unsound.

Before increasing memory, inspect avoidable wide rows, join multiplication, state growth, cache pressure, and skew. A malformed join that multiplies records by a factor of thousands can consume any reasonable cluster. Scaling resources treats the consequence while retaining the logical defect.

Driver memory and executor memory must also be separated. collect() and conversion to a local pandas DataFrame can move an entire distributed result to the driver. Increasing executor memory does not enlarge that driver's available memory.

11.5 Caching Has a Reuse and Capacity Contract

Spark cache/persist retains supported intermediate results for reuse, while Databricks disk caching and SQL result caching have different scopes and invalidation behavior. They are not interchangeable switches.

Cache when the saved recomputation exceeds the cache's creation, storage, and maintenance cost and the data will actually be reused. A dataset used once can consume memory without saving work. Release explicit Spark caches when their useful lifetime ends, and account for cache loss or warming after compute changes.

For benchmarks, record whether caches are warm or cold and whether the underlying data changed. Comparing a warm cached result to a cold first execution overstates an algorithmic improvement. If production queries rarely reuse the same input, a repeated-query demonstration is not representative.

11.6 Table Maintenance and Query Optimization

Use the physical-design choices from chapter 7 to reduce scan work. Inspect whether predicates actually use useful file statistics or partition/clustering locality. A table being declared clustered does not prove that all historical files have been reorganized or that the chosen keys help the important queries.

OPTIMIZE reorganizes eligible files, including compaction and supported clustering behavior. It is not a command to delete old business rows. VACUUM removes eligible obsolete files under retention rules; it is not a general query-acceleration command. Keep the recovery constraints from chapter 5 when scheduling maintenance.

Statistics help the optimizer estimate row counts and choose execution strategies. Stale or missing statistics can mislead planning, while a selective predicate on an unhelpful column may still require substantial scanning. Predictive optimization can automate supported maintenance, but verify actual operations and cost rather than assuming automation has already run.

Avoid changing compute size, query logic, layout, and cache state simultaneously in an experiment. Change one plausible cause, rerun with a controlled input, confirm result equivalence, and then compare the relevant execution metrics.

11.7 Measure Consumption Without Mislabeling It as Cost

system.billing.usage exposes consumption records. Preserve the SKU and usage unit when aggregating quantities:

SELECT
  usage_date,
  sku_name,
  usage_unit,
  SUM(usage_quantity) AS quantity
FROM system.billing.usage
WHERE usage_date >= CURRENT_DATE() - INTERVAL 7 DAYS
GROUP BY usage_date, sku_name, usage_unit;

This query measures usage under the table's access and data semantics; it does not compute an invoice. Monetary cost depends on applicable prices, effective dates, discounts, and additional cloud charges. Do not sum unlike usage units or assume every SKU is billed at the same price.

Attribute consumption to supported job, workspace, identity, and tag metadata. Handle multiple records per run and corrections according to the billing-table specification. When joining historical cluster metadata, choose the correct keys and time validity so a one-to-many join does not multiply usage quantities.

Compare cost per successfully validated unit of work as well as elapsed time. A configuration that is cheaper per minute can be more expensive per correct batch if it runs longer or retries frequently. Include idle infrastructure and warm pools where relevant. Budgets and notifications report thresholds; they do not necessarily impose a hard shutdown limit.

11.8 Azure Monitor and Log Analytics

Azure diagnostic settings can route selected workspace log categories to destinations such as Log Analytics, storage, or Event Hubs. Configure the correct Azure resource and destination, supported categories, access permissions, and retention. Account events, workspace events, engine logs, and custom application logs do not automatically share one delivery path.

Inspect the actual destination tables and schema before writing a monitoring query. Resource-specific Databricks tables or other configured ingestion layouts can expose different fields. Parse structured request/response information rather than assuming that any JSON string containing error means an operation failed: a successful response can contain a null field named error_message.

Even a failed API operation is not always a failed data run. Correlate the documented action, run/task identifiers, and execution outcome. A job-creation API failure and a runtime transformation failure require different alerts and owners.

For a scheduled-query alert, define the event population, evaluation window, threshold, frequency, and action group. Use ingestion-delay-tolerant windows and test delivery to the actual destination. To detect silence, monitor the absence of expected completions or freshness progress; a failure-only alert will not fire when the schedule never starts.

Log Analytics delivery is asynchronous. A missing recent event can reflect ingestion delay, configuration, permission, or a genuine absence of activity. Validate the delivery path using a known harmless event and its identifiers before relying on an empty result.

11.9 Diagnose Before Restarting

Save relevant run, query, stage, and error evidence before restarting compute. Restarting can clear interactive state and make transient diagnostics harder to recover. It may address an environment problem, but not a deterministic bad cast, a missing grant, or a wrong join.

After intervention, run the smallest representative check that could demonstrate the cause was addressed. Then validate the full affected data interval and restart/recovery semantics as needed. A single successful empty batch does not prove that a previous scale or data-dependent failure is fixed.

The monitoring lab requires suitable monitoring permissions. Azure Monitor delivery needs Azure resources, and classic compute metrics cannot be assumed available in Free Edition. No cost or performance improvement in this chapter is presented as a measured result of these unexecuted exercises.

12. Integrations and Analytical Access

An integration can move data, execute a query, expose metadata, or invoke a tool. Identify which of these occurs and whose identity authorizes it. A connector being available does not prove that the downstream viewer's Unity Catalog permissions are evaluated, that no data is copied, or that lineage remains complete across both systems.

12.1 Use a Boundary Checklist

For each connection, document source and destination, operation, credential owner, effective query identity, copied/persisted data, refresh latency, and downstream access controls. Then test one authorized and one unauthorized consumer.

Pattern What crosses the boundary Main decision
Power BI Import Data copied into a semantic model Freshness and protection of the imported copy
Power BI DirectQuery Queries and results Warehouse capacity, latency, and effective identity/SSO
Fabric catalog mirroring/shortcuts Supported metadata and access to referenced data Connection identity and Fabric-side governance
Databricks writes to OneLake Persisted data and updates Ownership, format compatibility, and two-platform publication
Purview scanning Supported metadata and lineage information Scan permissions, completeness, and discovery policy
VS Code/Databricks Connect Code/artifacts or remote Spark operations, depending on mode Local/remote execution and dependency boundary
Genie or an agent connector Questions, generated queries, and results Business semantics, effective identity, and answer verification

The same workload can use several patterns. For the orders system, Databricks can maintain the analytical tables, Power BI can present approved metrics, and Purview can publish metadata for discovery. This does not require granting each product unrestricted access to raw customer data.

12.2 Power BI: Choose Freshness and Identity Deliberately

Import mode loads data into the Power BI semantic model. Report queries normally use that imported data until refresh. This can reduce repeated Databricks query work, but creates a separate persisted security and freshness boundary. Unity Catalog controls the extraction identity's access; it does not re-evaluate every report viewer against the original table on every imported-model query.

DirectQuery sends supported queries to Databricks, commonly through a SQL warehouse. It avoids the same import-refresh pattern but adds dependence on query latency, connectivity, warehouse availability, and concurrency. "Direct" does not mean an unlimited real-time guarantee: caches, query execution, and application behavior still matter.

The authentication method must be considered alongside the connectivity mode. A fixed service principal or token means Databricks evaluates that principal's permissions. User-specific access requires a supported, correctly configured identity-passthrough/SSO arrangement. Selecting OAuth in one dialog does not by itself prove every Power BI viewer is impersonated downstream.

When configuring a connection, use the selected compute's server hostname and HTTP path, the intended catalog/schema, and the correct authentication mode. Test the published service configuration separately from Power BI Desktop; they can use different credentials and network routes.

Private connectivity may require an appropriate gateway/network arrangement. A working developer laptop connection is not evidence that the Power BI service can reach the workspace. Connector/driver changes also require regression testing of query folding, data types, and semantic models before adoption.

Databricks-to-Power BI publishing can carry supported table descriptions and relationships into a semantic model. Review them: an informational foreign key can describe an intended relationship whose data is not actually valid. Publishing also has capacity, XMLA, tenant, and permission prerequisites that depend on the chosen feature.

For Import consumers, schedule the semantic-model refresh after the upstream data publication gate succeeds. Verify refresh completion and the model's observed data version, not merely that the refresh API accepted the request. A DirectQuery model instead requires checking the current query path and security context.

12.3 Fabric: A Shared File Is Not a Shared Authorization Model

A Mirrored Azure Databricks Catalog can expose supported catalog metadata and create OneLake shortcuts to supported tables. This is distinct from traditional database mirroring that copies change data into a separate replica. Inspect the specific integration rather than inferring behavior from the word "mirrored".

The archived Fabric unit describes access based on the identity configured for the connection, with downstream authorization performed in Fabric. This is a crucial boundary: downstream Fabric users must not be assumed to inherit their individual Unity Catalog row filters, column masks, or grants through a file-access shortcut.

Supported table types, external-access privileges, network restrictions, and downstream OneLake security must be checked for the current connector. If a table's protection depends on per-viewer Unity Catalog evaluation, choose a query path that demonstrably preserves that identity and enforcement, or publish a separately approved dataset with suitable Fabric controls.

Writing curated data from Databricks into OneLake creates another ownership and publication boundary. Specify the target lakehouse location, supported authentication, format, refresh/visibility behavior, and permissions. Writing files into a lakehouse's Files area does not automatically prove that they are registered as a usable table in every Fabric engine.

Avoid competing writers unless the documented table/storage integration supports their concurrency. A shared Delta path alone is not proof that every engine supports the table's enabled features, protocol version, or metadata changes. Likewise, no extra data copy does not mean no compute, capacity, network, or egress cost.

12.4 Power Platform: Distinguish User Access From Automation

Power Apps and Power Automate can use supported Databricks connector operations such as SQL access or job orchestration. A user-facing app, a background flow, and a service-principal connection can have different effective identities even when configured from the same environment.

For an app that exposes orders, decide whether users should see a common approved dataset or their individually authorized subset. If all calls use a service principal, the Databricks query runs with that principal's permissions; implement and verify any additional user-level restriction in the appropriate supported layer.

Delegation and result limits affect correctness. A client-side filter applied only to an initial retrieved subset can return an incomplete answer while appearing to work on a small demonstration. Push supported filtering/aggregation to the data engine and test with a population exceeding any client retrieval boundary.

Connector licensing, throttling, supported clouds, direct connections, and Dataverse virtual-table capabilities differ. These are integration prerequisites, not capabilities to infer from a product logo. Use batching and rate-aware retries where supported, and make repeated write operations replay-safe.

12.5 Purview: Discovery Is Not Query Authorization

Microsoft Purview can register and scan supported Databricks metadata so assets appear alongside other enterprise data sources. Scan capabilities differ between legacy Hive metastore and Unity Catalog integrations and between supported network/authentication arrangements.

Purview's discovery and lineage view does not replace Unity Catalog grants at execution time. A person discovering that a table exists is not necessarily authorized to read its rows. Conversely, adding a classification in a catalog does not automatically configure every downstream enforcement mechanism.

Treat lineage completeness as a measured integration property. Some execution paths, external tools, and complex transformations may not produce the relationships expected by the scanner. Confirm that a known transformation appears, that the metadata is fresh, and that the scanning identity does not expose more metadata than intended.

If scanning or classification requires particular data access under the selected connector, grant and assess that access explicitly. Do not generalize a metadata-only description into a guarantee that every Purview scanning feature never reads data values.

12.6 VS Code and Databricks Connect

The Databricks VS Code extension supports local development workflows connected to a remote workspace. Distinguish file synchronization, remote job execution, and Databricks Connect: they are different paths for developing and running code.

With Databricks Connect, a local client can build Spark operations that execute on remote Databricks compute. Local Python control flow and debugging remain distinct from distributed executor behavior. A breakpoint in the local client is not a guarantee of transparent single-stepping through every worker's execution.

Align supported client/runtime versions and dependencies. A library imported by local orchestration code may need a local installation; a library used by remote execution may need the remote environment. A successful local import proves neither remote availability nor compatible execution.

One-way local-to-workspace synchronization is convenient for iteration but is not a bidirectional source-control workflow. An edit made in the remote copy may not return to the local repository. Use reviewed Git revisions and the bundle workflow from chapter 10 for controlled releases.

12.7 Genie Needs a Business Model, Not More Generic Instructions

A Genie space provides a focused analytical context over selected governed data. Its effectiveness depends on table grain, relationships, descriptions, sample queries, and explicit business definitions. Include the objects needed for a coherent question set rather than every table in the metastore.

For orders, define revenue precisely: which order statuses count, how cancellations/refunds are handled, currency conversion, the relevant date, and the timezone. Define the valid-time relationship for historical customer attributes. Otherwise, a generated SQL statement can execute successfully and still calculate the wrong quantity.

Use the right instruction surface. Table/column descriptions establish meaning; join relationships establish valid combinations; reusable SQL expressions define measures and filters; example questions and SQL demonstrate intended query patterns. General text should supply rules not already represented clearly elsewhere.

Prompt/entity matching can connect user terms to actual values, such as a full region name to a stored code. Review which representative values are exposed and refresh them when necessary. Hiding a column from the space's presentation is not a replacement for an authorization control.

Maintain benchmark questions with expected interpretations and outputs. Include ambiguity, empty results, duplicate-sensitive joins, historical dates, and unauthorized requests. Judge analytical correctness separately from successful SQL execution, permission enforcement, or the presence of a "Trusted" label.

For example, "revenue last month by customer region" has at least two plausible meanings: the customer's current region or the region valid when the order occurred. Either can be legitimate, but the space must apply an agreed convention or request clarification. An answer without an error message is not proof that the intended meaning was selected.

12.8 Copilot Studio and Microsoft Foundry

The archived course describes integrations using table-oriented connectors or Genie spaces exposed as tools, including managed MCP paths. A table lookup, natural-language-to-SQL analysis, and semantic retrieval are distinct operations. Do not label all three "semantic search" merely because the user starts with a natural-language question.

For a Genie tool invocation, the calling application sends a question, Genie interprets it against its configured analytical context, and the result returns to the application. The application can then summarize it. This adds interpretation stages, so preserve query/result provenance and avoid turning an unverified inference into a factual business conclusion.

Verify authentication at every hop. User identity reaches Databricks only if the actual connector and token flow support and use that propagation. A fixed application credential instead produces application-level access. MCP standardizes a tool interaction; it does not, by itself, implement user impersonation or guarantee authorization.

Confirm current preview/GA status, supported warehouses, network access, rate limits, and conversation-state behavior before implementation. If each tool call is independent, a follow-up such as "and for the previous quarter?" needs sufficient authorized context supplied by the caller. Do not assume the tool remembers the agent's entire conversation.

These integrations are covered as consumers of governed analytical data. They do not expand this course into agent implementation or model training. Their relevant data-engineering contract is accurate, authorized, fresh, traceable access to the intended data.

12.9 End-to-End Acceptance Scenario

Publish daily revenue from the orders workload to a BI consumer and prepare a focused Genie space over the same approved data. Run one authorized and one unauthorized identity through each chosen route. Compare a known month's revenue with an independently computed expected result and inspect whether both consumers use the intended data version and business definition.

Then simulate a source correction and a revoked permission. Verify refresh behavior, downstream visibility, and the limits of revocation for already copied data. This closes the course's architectural loop: the correctness and security properties of a pipeline must survive the way its results are consumed.

Power BI, Fabric, Power Platform, Purview, and Foundry can require separate licenses, capacities, resources, or service permissions. Free Databricks course access does not include these environments. The scenario is an acceptance design, not an execution performed during authoring.

Free Edition is a practice environment, not a course. The getting-started documentation describes a serverless-only, quota-limited environment and states that it replaced Community Edition, retired in 2025. It supports learning exercises with notebooks, SQL, and Lakeflow, but is not a substitute for a full Azure Databricks environment.

The documented limitations include no custom compute configurations, no R or Scala, no custom workspace storage locations, no account console or account-level APIs, no private networking configuration, and no SSO or SCIM. Usage quotas can suspend compute until the relevant limit resets. These restrictions determine which labs can run there; account eligibility and actual execution remain untested.

For the future course, classify every exercise as Free Edition-compatible, full-workspace-required, or Azure-specific. Preserve Azure identity, storage, and network topics in the conceptual coverage even when the free environment cannot demonstrate them. Do not conflate a no-cost edition with a time-limited free trial.

Editorial Requirements for the Future Course

  1. Organize by concepts, dependencies, and engineering decisions, not by concatenating the original module sequences.
  2. Explain each concept once in its canonical section. Later sections should link back and add only genuinely new information.
  3. Remove empty, rhetorical, and promotional sentences. Every paragraph must contribute a mechanism, constraint, decision criterion, example, failure mode, or piece of evidence.
  4. Do not introduce topics with generic claims such as "Data is critical to modern organizations", "Unlock the power of your data", or "Robust pipelines are essential for success". Start with what the component does, what problem it solves, or what the reader must decide.
  5. Replace vague advice such as "follow best practices", "ensure scalability", and "optimize performance" with the relevant operation, condition, observable signal, and trade-off. Delete the sentence when no concrete content remains.
  6. Preserve operational depth: permissions and scope, execution identity, checkpoint and schema behavior, retries and idempotency, failure recovery, compute compatibility, and deployment semantics.
  7. Assume basic SQL and Git knowledge. Keep brief reminders or optional references where necessary; explain Databricks-specific differences rather than reteaching the whole prerequisite.
  8. Use one minimal example per distinct behavior. Parallel SQL and Python examples belong together only when their differences teach something; otherwise choose one and provide a short mapping.
  9. Separate conceptual explanations from UI procedures and lab instructions. Retain a procedure when it teaches a configuration choice or verifies an outcome, not merely to repeat a navigation sequence.
  10. Separate general Databricks behavior from Azure-specific integration. Label runtime-dependent, cloud-dependent, preview, and account-dependent behavior; reconcile conflicting sources against current official documentation before writing a definitive rule.
  11. Maintain a coverage map to the original 15 modules and the applicable DP-750 study guide. Removing repetition must not silently remove an assessed objective.
  12. Write the course in English. Keep one physical line per paragraph and one line per list item; do not manually wrap prose.
